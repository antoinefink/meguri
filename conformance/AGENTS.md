# conformance/ (MPL-2.0, shared by spec writers and implementers)

- The format, observations, statuses and catalog are `specs/conformance/dsl.md` and `observations.md`; `schema/*.schema.json` mirror them. Change spec, schema, the testkit model (`core/crates/meguri-testkit/src/scenario/`) and, for a new op or kind, the oracle driver together. `schema/protocol.json` is the only interface to oracle workers.
- `goldens/` is written only by `tools/mg oracle record <filter>` (or `tools/mg conformance --live`, which calls it): never edit a golden by hand or bless Meguri output into one. `tools/mg oracle compare <filter>` re-runs the live oracle against the committed goldens.
- A golden goes stale when its scenario's parsed value or the oracle lock changes; comments, key order and layout do not change scenario_sha256. Re-record stale goldens in the same change as the scenario edit. `tools/mg goldens-check` must pass.
- Scenarios are YAML in the JSON-compatible subset, read with the YAML 1.2 core schema (`yes` and `2030-01-15` are strings): no aliases, merge keys, tags or duplicate keys. A scenario's `id` is its path without suffix; one file per id. They define their own note types and CSS and contain no Anki test code or test data text (R1881, R1959).
- `scenarios/<area>/area.yaml` (one per area) lists `active` scenarios: T0 fails unless Meguri passes them, T1 for live ones. Mark a scenario active in the change that lands its Meguri adapter.
- A scenario with `handoff` steps is live (dsl.md D9.2): T1 runs its segments on Meguri and the oracle in turn and compares with its golden, which the oracle records running every segment. T0 never runs it. T1 fails on any oracle drift or error, active or not.
- A scenario with `actors` is live too (`specs/conformance/sync-ops.md`): its clients sync with a server that the oracle worker runs for it, and the parties executor is its only executor. A scenario never names a host, port or credential (R1876). Under a frozen clock, changes and syncs in the same instant look unchanged to the status check: advance the clock before each actor's block (S4.3). A one-way download leaves `mod` equal to the server's, so the next `normal` syncs nothing until a local change. A receiver stamps incoming graves and tags with its own round's `usn`, which `converge` reports: observe those parties with `db_dump` (S12). Keep one top-level `other` member per blob wherever digests are compared.
- An op Anki refuses records `{<op>: {"error": <kind>}}` and the run goes on (D7.3); kinds are the op's closed list in D7.2, added with the driver op. Never encode a refusal another way.
- `oracle.json` is the current oracle pin; it changes only when adopting a bump, with the lock file and every golden.
- `deviations.yaml`: one entry per deliberate difference, with its requirement and the test that asserts Meguri's behavior. Nothing else may differ from a golden.
- `catalog/harvest.csv` never names an Anki file or test; the id → test link is `oracle/harvest/links.csv` (spec side). Spec writers regenerate both with `tools/mg harvest-inventory [--supplementary]` and classify their area's rows (`supplementary` rows: main-branch tests, in scope only when the behavior exists at the tag), and re-review rows a re-inventory reopens because the test's source changed; `tools/mg harvest-report` reports coverage and runs the leak and inventory-at-pin checks.
- `recordings/sync/<name>/exchanges.jsonl`: Anki-client exchanges with the sync server, bodies decoded (format: `docker/mitm/record_sync.py`), written only by `tools/mg sync-rig up --record <name>` on the spec side, never edited by hand. A probe of the rig is not a recording: delete it. Neither is a run whose `up` or `status` reported `recorder-unhealthy` or `recorder-stopped`: it misses exchanges.
- `recordings/scenarios/<scenario id>/`: the oracle actors' exchanges of an actor scenario, with `actor` and `step` per exchange (sync-ops.md S9), written only by `tools/mg oracle recordings <filter>`, never by hand. Re-recording an unchanged scenario still changes the `anki-sync` session ids (`s`), note guids and collection-file hashes: re-record only when `recording.json` would change.
- `fixtures/`: inputs made by the oracle maintainer, never by hand, by Meguri or from `local-data/`. Oracle workers read them read-only at `$ORACLE_FIXTURES`, which every tool that starts workers mounts and sets (`tools/mg oracle record|compare`, `conformance --live`); a new one must too.
- `fixtures/storage/*.anki2`: collection files at schemas 10 to 19, made once with the Anki releases and recipes of `specs/storage/schema-upgrade.md` U16 (old releases included) by `oracle/fixtures/storage/make.sh`. Remaking them changes every byte (ids and stamps come from the clock), so every storage golden must be re-recorded with them. A scenario that opens one (`open`, `specs/conformance/storage-ops.md` P1) has no `setup`; its golden is stable only if three recordings agree.
- Writing blobs with `db_exec`: SQLite's `||` yields TEXT and Anki refuses a blob column holding TEXT, so append with `CAST(<column> || X'…' AS BLOB)`. A statement that changes rows Anki caches (note types, decks) needs a fresh read before Anki sees it (`specs/conformance/model-ops.md` L1).
- Anki gives new fields and templates random ids and writes several top-level `other` members in no set order: pin ids with `legacy_update` before observing them, and keep at most one surviving top-level `other` member where a scenario reads blob bytes.
- Generated scenarios (`scenarios/<area>/corpus/*.json`) come from the seeded `corpora/<area>/generate.py`: regenerate, never hand-edit, and re-record their goldens in the same change.
- Scenario and golden strings carry U+2028, U+0085 and other line-breaking characters raw: split JSON lines on `\n` only, never with Python's `splitlines()`.
