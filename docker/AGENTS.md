# docker/

- Never push an image to a registry. The one exception is the dev image that hosted CI shares (`.github/dev-image.sh`). It holds only what its `.dockerignore` lets in (`core/rust-toolchain.toml`), never source or data. Pin every base image by digest (`FROM name:tag@sha256:...`); `tools/mg selftest` checks it.
- Every service sets `init: true`, so killing `tools/mg` stops the container; without it bash runs as PID 1 and SIGTERM is dropped. `tools/mg selftest-host` checks it.
- Drive compose through `tools/mg` (`mg_compose`). It sets a per-checkout project name, so worktrees never share an image tag, network or `cargo-target` volume. It also sets `BUILDX_NO_DEFAULT_ATTESTATIONS=1`: with a provenance attestation, every rebuild gets a new image id even when all layers are cached, and compose 5.5 ignores `provenance: false`.
- Every worktree shares the `meguri-cargo-home` volume, mounted as the whole `CARGO_HOME`. Cargo's package-cache lock files live in the `CARGO_HOME` root, so if only `registry/` were shared, parallel containers could unpack the same crate at the same time. Installed cargo tools stay in the image's `/usr/local/cargo/bin`, which is on `PATH`.
- SQLite files and other test scratch go to the container's tmpfs `/tmp` (`TMPDIR`), never to the `/work` bind mount: virtiofs locking is slow and unreliable. Rust output goes to the `cargo-target` volume (`CARGO_TARGET_DIR`), never to `core/target/`, which holds host builds.
- The dev image installs exactly what `core/rust-toolchain.toml` lists, so rustup never needs the network at run time. The `FROM rust:<x.y>` tag must match that file's channel; bump both together. Each Dockerfile has a `<name>.Dockerfile.dockerignore` allowlist, because the build context is the repo root, which holds `local-data/` and `refs/`.
- Pin new tool versions as `ARG`s and install them with `cargo install --locked --version`.
- `cargo install` exits 0 when a binary's required features are off, so check each installed binary runs.
- The `oracle` service is the exception to per-checkout tags: its image is `meguri-oracle:<anki version>-<hash of the image inputs>`, set through `MEGURI_ORACLE_TAG` by `tools/mg oracle`, so identical `oracle/` trees share one image. `pull_policy: never`: build it with `tools/mg oracle build` before starting workers. It runs only on the `oracle-internal` network (`internal: true`, R1876); anything that needs a route out (the lock resolver) is a separate `docker run`, never the oracle.
- The `similarity` service never mounts the corpus itself: its host jobs add `refs/` read-only per run (`-v ...:/refs:ro`), because worktrees have no `refs/` and the corpus must not reach implementer environments.
- The `private` service (U15) never mounts the user's collection itself: `tools/mg private` adds `local-data/anki/` read-only at `/vault` per run, as `similarity` adds `refs/`. It has `network_mode: none`, hides the checkout's `local-data/` behind a tmpfs and runs meguri-cli from the dev service's `cargo-target` volume (read-only), built in `dev` beforehand. Never give it a network, a port or another mount of `local-data/`.
- The sync rig (`syncserver`, `toxiproxy`, `mitmdump`, `sync-edge`; `tools/mg sync-rig`) is for app and simulator end-to-end runs and spec-side recordings, never for conformance (its server is the oracle worker's child, on the scenario clock). `syncserver` and `sync-edge` run the oracle image with its entrypoint replaced, so the server is on the real clock; never give them a `build:` or the oracle's entrypoint. The servers and proxies are only on the `internal` `sync-rig` network, so toxiproxy's API cannot point a proxy beyond the rig (R1876). Docker publishes no port from an internal network: `sync-edge` (`sync-edge/forward.py`, routes fixed in the script) is the only published service, on `sync-rig-edge`, a bridge without masquerade (published loopback ports work, no route out). Publish only on it, as `127.0.0.1::<port>`; never give another rig service `ports:` or a second network. The job fails and stops the rig if anything answers on the LAN address. Rig containers carry no run label: they outlive `up` until `down`.
- Docker Desktop's port publishing turns a TCP reset into a plain close: a client on the Mac sees toxiproxy's `reset_peer` as an empty reply, while a client inside the rig's networks sees the reset (`sync-edge` passes resets on).
- mitmdump keeps proxying when its addon fails to load or to write, so a recorder that answers is no proof of a recording. `mitm/record_sync.py` reports its state in `/tmp/record-sync-health.json`; the `mitmdump` health check and `tools/mg sync-rig` read that path (keep the three in step) and fail unless it says `ok`.
- `sync-faults` and `sync-recorder` (profiles `oracle-sync`, `oracle-record`) serve actor scenarios on `oracle-internal` only, pinned by the rig's digests; never publish a port. `sync-faults` is shared and stays up (workers name their proxies per run). Each recording gets its own `sync-recorder` (`compose run -d --name mg-sync-recorder-<run id>-<n>` with the run label), since a recorder writes one scenario's directory. `record_sync.py` attributes exchanges (`record_actor_steps`) only there; its unit tests (`mitm/tests`) run in that image from `tools/mg selftest-host`.
