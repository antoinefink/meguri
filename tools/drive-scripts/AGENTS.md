# tools/drive-scripts/

Drive scripts for `tools/mg drive <script> [--platform iphone|iphone-small|ipad|ipad-small|foldable|mac] [--device <udid>] [--record]`, run by `app/MeguriUITests/AgentDriver/AgentDriverTests.swift` (parser: `DriveScript.swift`, which rejects anything not listed here).

```json
{"name": "open-sample-sheet", "description": "...", "platforms": ["ios", "mac"],
 "steps": [{"launch": {"route": "sample/sheet", "animations": false}}, {"tap": "sample.sheet.done", "transition": "dismiss-sheet"}]}
```

- The first step is `launch`. Its keys are the U7 launch options (`app/Meguri/TestHooks/LaunchOptions.swift`): `fixture` (relative to the repo root), `now`, `timeZone`, `locale`, `animations`, `reduceMotion`, `reduceTransparency`, `windowSize`, `ankiConnectPort`, `migakuPort`, `route`, `arguments` (raw extras). A later `launch` relaunches.
- Actions, one per step: `tap: <id>`, `type: {id, text}`, `swipe: {id, direction}` (the finger's direction), `scroll: {id, direction}` (the content's), `wait: <id>` or `{id, timeout, gone}`, `snapshot: <name>`, `resize: minimum|default|large|<w>x<h>`.
- Elements require a unique accessibility identifier; taps use the exported hit point. The named macOS D4 replay rule instead requires trusted current host IDs, exact raw AXDOMIdentifier on one owned native link and a press of that same AXUIElement. Raw XCTest/AXIdentifier fields stay distinct; no coordinate fallback. This rule is currently bound by the synthetic replay route only.
- A `launch` captures once the identifiers settle (the identifiers stay unchanged for 1 s, at most 5 s): SwiftUI gives some UIKit views theirs a moment after launch (an iPhone tab bar's buttons lack them in the first hierarchy).
- `resize` resizes the running Mac app's window as the `windowSize` launch option would, without a relaunch: the app keeps its state (a hook build answers the driver's request, app/AGENTS.md). On simulators it is reported `unavailable` (not a failure).
- `"transition": "<name>"` (lowercase letters, digits, `-`) on a step marks it for motion capture. With `--record` the run gets a contact sheet `motion/<NN>-<name>.png` of the frames that change around that step; a sheet that cannot be made makes the drive an error.
- What `--record` captures: simulators, `simctl io recordVideo` around the whole drive. The Mac, in the test VM (every Mac drive but a host run, root `AGENTS.md`): `FrameSampler` screenshots at about 10 per second from the start of the marked action to 1.5 s after it (`frames/`), because the host cannot record the VM's screen; marked launch, resize and snapshot steps are not sampled (`unsampled_transitions` in the manifest), a gap no Mac recording covers until a VM screen recorder exists. A host run (`MEGURI_MAC_UI_ALLOW_HOST=1`) with Screen Recording (user step `screen-recording`) records the main display with `screencapture -v`, cut to the app's window per marked step, and deletes the full-screen movie; that path has not run with the permission yet. Motion checks (U252) on the Mac work from the sampled rate.
- Mac drives with a `tap`, `type`, `swipe` or `scroll` are queued (`blocked: mac-input`) while macOS drops XCUITest's synthesized input (macOS 27.0.1; `docs/process/one-time-setup.md`). A failed step from the first of those on then says nothing about the app; a failed step before it, the script's error and hierarchy issues still fail the drive.
- `platforms` is read by `tools/mg mac-ui`: it runs every example listing `mac`, with `--record` when the script marks a transition. Mac drives run in the test VM: the script and the `fixture` of each `launch` are copied there to the same paths; other files a script needs must sit in a fixture.
- Examples must pass on every platform they list: `hierarchy-check` issues fail a drive.
