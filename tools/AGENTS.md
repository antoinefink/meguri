# tools/

- `tools/mg <job>` is the only documented way to build, test and verify. A run writes `build/mg/<job>/<run-id>/result.json` (schema `mg-result.schema.json`, bump `schema_version` on incompatible changes), points `latest` at it (never for `--dry-run`), prints only the result path on stdout, and exits 0 for pass and warn, 1 for fail, 2 for error. Job output goes to stderr and `log.txt`.
- Add a job by adding or extending a family in `mg.d/<family>.sh`: `mg_job <name> <host|docker:<service>> <fn> <description>`, then record results with `mg_status`, `mg_count`, `mg_failure`, `mg_artifact`, `mg_user_step`, `mg_detail`, `mg_message`. Do not echo JSON yourself. Every job must survive `--dry-run`; `tools/mg selftest` dry-runs them all.
- Placement is the R1952 rule. A `docker:<service>` job runs its whole function inside that compose service (`tools/mg __exec`), so write it as plain commands for that container. A `host` job runs on macOS and may call `mg_compose` itself; a container it starts gets `--label meguri.mg.run-id=$MG_RUN_ID`, so a cancelled run removes it. Host placement is also how a job mounts data from outside the checkout (the similarity corpus) or runs git on a worktree: inside a container a worktree's `.git` file points to a host path.
- `<git dir>/meguri-session.json`, written by `tools/mg worktree new`, is a worktree's role; `mg_session_role` reads it. Jobs that need `refs/` or `oracle/` refuse implementer and fixer worktrees. Session records are committed where they are appended (the new branch, or the current branch for `session record`), never left in a working tree. Append and commit only through `mg_session_store`: it holds `<git common dir>/meguri-session.lock` (mkdir) across both, because parallel records in one checkout collide on git's index.lock.
- `.claude/settings.implementer.json` is rendered by jq (`worktree.sh`), never sed: paths may hold `&`, `|` or `\`. A new `@PLACEHOLDER@` must be added there, or `worktree new` refuses the profile. Bash deny rules match the whole command text, and options or wrappers come before a subcommand (`git -C x show`, `env X=1 docker run`): a rule for a command starts with `*` and has `*` before each word it pins (`*git *show *oracle*`). Add sample commands to the matcher test in `tests/provenance.bats`.
- Check a value against a word list with `mg_word_in`, never `case " $list " in *" $x "*)`: a compound value such as `implementer fixer` matches that pattern.
- Path lists from git are NUL-separated (`-z`) end to end: without it git quotes names with non-ASCII, tab or newline characters, and `grep`/`case` on them miss.
- `tools/mg` and `mg.d/` must run under macOS `/bin/bash` 3.2 with BSD tools: no associative arrays, `mapfile` or `${x,,}`; guard empty arrays under `set -u` with `${a[0]+"${a[@]}"}`, also `${a[*]}` inside a string. The bats suite runs bash 5, so a host job's 3.2 paths are tested only in `mg_host_selftest.sh`. Pass job arguments to jq with `--arg` or `mg_json_array`, never `--args` (jq parses `-E`, `-c` and `--` there).
- SIGINT, SIGTERM or SIGHUP cancel a run: `tools/mg` sends SIGTERM to the job's process tree, waits for it, stops and removes a docker run's container itself (compose does not do it reliably) and writes an `error` result with a `cancelled` failure. Jobs run as a background child of `tools/mg`, so under macOS bash 3.2 they inherit an ignored SIGINT they cannot trap: make jobs stop on SIGTERM.
- Agents never perform `user_steps` (R1969). doctor only reads host state; `tests/mg_selftest.bats` stubs host commands and fails on any call outside a read-only allowlist, so extend that allowlist when doctor learns a new read.
- `scripts/sim-pool.sh` (job `sim`) is the only code that creates simulators: `Meguri-Pool-<kind>-<n>`, never shut down, erased or deleted. Kinds and device types come from `sim-devices.json`, which also pins the runtime build that `sim-setup` checks; `sim-setup` creates missing kinds through the pool. The pool lives in the test VM (U8c, `vm/AGENTS.md`): called here, the script runs itself there over SSH, from a temporary directory per call with the kinds file and `caller.json` (the caller's checkout, directory and pid: never pass identity as command text, the bats fake maps paths in it). Leases are mkdir locks under the VM's `~/Library/Caches/meguri/sim-pool/`, shared by every worktree. Exit 5 is queued (no VM; `MEGURI_SIM_ALLOW_HOST=1` runs the pool here), 6 the VM could not run it. `acquire` and `gc` (not `--list`) create, boot or delete simulators, so they run under the VM's lease: directly when the caller runs under the lease's holder (`mvl_lease_held`: the holder's pid is the caller's or an ancestor's, as for a job's own `mg_sim_lease` and `xcode_project_check.sh`), otherwise through `tools/mg sim <command>` (`mg_sim_pool_take`), which takes it, runs the script again under it and hands back its stdout and exit code (`details.pool`). Release, renew, reset and status take no lease: a job waiting under the lease for a device needs another checkout's release to get through. Once after every boot it checks that SpringBoard applies a change to dark (the style arbiter's line in the simulator's log) and restarts SpringBoard until it does: some SpringBoards ignore appearance changes for good, and a restarted one drops them for some seconds. Its tests fake simctl with `tests/sim_pool_fake_xcrun.sh`; `tests/sim_vm.bats` runs it in a fake VM.
- App jobs (`mg.d/app.sh`, `drive.sh`, `record.sh`; U8, U8c): a simulator job calls `mg_sim_begin` first (`mac-vm.sh`: the pool VM, started when stopped; without one queued, or this Mac's pool with `MEGURI_SIM_ALLOW_HOST=1`), reaches simulators only through `mg_simctl` and `mg_devicectl`, tests through `mg_app_xcodebuild_test` (`mg_vm_xcodebuild_test`: test-without-building of the copied products), and gets what simulators write back with `mg_sim_mkdir` before and `mg_sim_fetch` after. A fixture the app is launched with (a `-MeguriFixture` value, `run`'s launch arguments through `mg_vm_launch_args`; a drive script's `launch.fixture` and raw `arguments`) goes into the VM with `mg_vm_fixture`: one in the checkout to its own path, one outside it under the run directory, with the launch (or a copy of the drive script) naming that path; one that is not here is an error before anything launches. A `--device` must be a pool simulator leased from this checkout (`mg_sim_check_owned`) on the pinned runtime build (`mg_sim_check_runtime`), both checked before building (`mg_sim_check_given`); a device the job leases itself is checked right after the lease. After building, a job that installs, launches, drives, records or resets takes `mg_sim_take` (the VM's lease, with the products copied in; on the host `mg_host_lease`, one lease for every checkout in the main checkout's `build/mg/host.lock`) and checks a device it was given again under it, before touching it (the lease may have changed hands while it queued); `xcode-check` takes it between its `builds` and `devices` phases; its script copies the products and the sources its tests read at their repository paths (`VM_INPUTS`: baselines, hook fixtures, example drive scripts) into the VM, stops a run that lost its SSH session there (`mvl_stop_tests`, shared with `mg__mac_vm_stop_tests`) and starts no further run when it cannot. A job that holds the VM's lease and the host lease takes the VM's first (`xcode-check`, `snapshots` with the Mac): the other order deadlocks against them. `mg_sim_prepare` (the pinned status bar) returns 1 when the override fails: stop the job (`|| return 0`). Mac jobs that launch the app on this Mac (`run`, `screenshot`) call `mg_app_mac_guard`. Mac XCUITest jobs call `mg_mac_ui_begin` before building (the test VM, `MG_MAC_RUNNER=vm`; without one queued, or the host with `MEGURI_MAC_UI_ALLOW_HOST=1`) and `mg_mac_ui_take` after it (`mac-vm.sh`: VM lease, start, copy; host: the host lease, the guard and the hourly `mg_mac_ui_gate`); `mg_app_xcodebuild_test`, `mg_app_log_now` and `mg_app_mac_input_refused` follow `MG_MAC_RUNNER` (`vm/AGENTS.md`). A VM that does not start, answer or copy is error, never a reason to run on the host. A job that cannot run now records status error with `details.blocked` (host, mac-app, screen-recording, mac-input), never fail. After a Mac XCUITest run, `mg_app_mac_input_refused <since>` (unified log) tells whether macOS dropped its synthesized input; such a run is blocked, not failed. A queued run is warn with `details.queued`.
- A process that outlives its job and must keep the lease (the recording worker `scripts/sim-record.sh`; in the VM it records there and copies the video back when it stops) gets the job's slot with `mg_lease_transfer` (the lease the job took, `MG_LEASE_DIR`: the VM's or the host's) and releases it itself. While a recording holds the lease (`kind: recording`), its checkout's jobs take the nested slot `<lease>/inner` (`mg__lease_try`, for the host's and the VMs' leases alike); when the recording stops first, the nested job inherits the lease. Release only the slot whose `holder.json` names your pid (`mg__host_lease_release`). Anything that ends the lease (a release, a dead holder's cleanup) goes through `host_lease_drop`, which hands it to a live nested job: removing `host.lock` with `inner` in it lets another checkout in while that job runs. Every lease change but taking a free lease (mkdir) runs under the lease's mutex (`scripts/host-lease-mutex.sh`, a flock held on fd 6): start no process while holding it, or that process keeps it. A recording's state names its worker by pid and start time; check both (`mg_record__worker_alive`) before signalling it, because a finished worker's pid can be reused.
- A command started with `&` from a script starts with SIGINT ignored, and a shell cannot trap it again: start anything you stop with SIGINT (simctl recordVideo) through `mg_record__start_recorder`, and stop it with a bounded wait (`mg_record__stop_recorder`). In the VM, killing the local SSH client leaves the remote process running: signal it there by the pid it wrote (`<video>.pid`), and clean up with `mg_record__kill_remote`. A detached process gets `</dev/null` and its own log: one holding the job's stderr keeps `tools/mg` waiting.
- A job that was asked for an artifact (a recording, a contact sheet, a sampled frame set) and could not make it ends `error`, never `pass` (`mg_drive_run`). So does a drive whose log lists a capture the export lacks or holds empty, or whose hierarchies were not checked.
- Register cleanup in a job with `mg_on_exit` (`mg.d/host.sh`), never with your own EXIT trap: a second trap would replace the lease release. Its TERM trap makes cancellation run the same cleanup.
- Image and video work (contact sheets, hierarchy-check) runs in the `image-tools` container through `mg_image_tools`, which sees only the checkout at `/work`: convert paths with `mg_container_path`. Its scripts' tests run under `tools/mg image-tools-selftest`.
- Self-tests: `tools/mg selftest` (bats, in the dev container) and `tools/mg selftest-host` (macOS bash, real doctor, Docker from the host). Both run copies of `tools/` in a throwaway repo and never write to the real `build/mg/`. `tools/mg selftest-xcframework` runs `scripts/build-core-xcframework.sh` in a sandbox copy of `core/` and MeguriCore under `build/selftest-xcframework/`; run it after changing the script.
- `scripts/build-core-xcframework.sh` is also the Xcode pre-action: its no-change path must stay under 100 ms (each extra git process costs about 12 ms) and never invoke cargo, and it writes no output or stamp until every check has passed. It marks the stamp `incomplete` while it replaces outputs, so a failed or interrupted replace forces a rebuild. Runs past the no-change check hold flock locks on fds 8 (the outputs) and 9 (the cargo target dir); start any command that may outlive the script with `8>&- 9>&-`, or it keeps the lock. The script runs under `set -e`: call its functions as plain commands, never as `f || die`, which turns errexit off inside them.
- Oracle runs that select actor scenarios call `mg_oracle__sync_faults` before the harness or workers start (`MG_ORACLE_SYNC_FAULTS` feeds `mg_oracle__harness` and the `conformance --live` worker command) and `mg_oracle__sync_stop` after, which removes the run's recorders. `mg_oracle__actor_scenarios` mirrors meguri-cli's filter rules; keep them in step. It reads scenario files only through `meguri-cli conformance to-json`, never by grepping their text: a quoted key or a flow mapping hashes and parses like `actors:`.
- A checkout without `oracle/` builds the main worktree's, except when its branch changed `oracle/` and the main worktree's HEAD lacks it (`mg_oracle__tree`, `oracle-tree-differs`): that branch's oracle runs belong in its spec worktree or after integration.
- `lint-ui` is the first step of any job or gate that builds or verifies the app (AE90): start such a job with `mg_lint_ui_first || return 0` (today `swift-test` and `xcode-check`), so a lint failure ends the run before anything slower starts. It runs lint as its own run and links that result.
- Design verification (U10): `snapshots`, `a11y`, `critic`, `gallery`. Their Python (`scripts/image-diff`, `screen-status`, `critic`, `gallery`) runs in image-tools; tests under each `tests/` run in `image-tools-selftest`, the jobs' wiring in `tests/design_review.bats` with fakes. A container command's stdout may carry compose's build progress: have scripts write results to a file (`--out`, `--report`), never capture `mg_image_tools` stdout as data.
- `mg_host_lease` is not re-entrant: a job that needs it in several steps takes it once (`mg_snapshots__lease`). An `mg_on_exit` registered inside `$(...)` runs when that subshell exits; register cleanup in the job's own shell.
- `snapshots` sets simulator accessibility settings with devicectl per settings group and restores the defaults on exit; it never touches the Mac's own settings. `--platform iphone` leases two kinds (`iphone`, `iphone-small`; `mg_snapshots__kinds`), each run in `<run>/<kind>/<group>/`.
- The status ledger keeps evidence per platform. An a11y run counts only for the app sources it audited: `snapshots` and `a11y` record `details.input` (`mg_app_input_digest`: app/ and core/ as the working tree holds them, baselines left out), and the ledger and `critic` refuse an a11y run whose input differs from the snapshots'. `critic` takes one `--a11y` run per platform and refuses, before the session, a snapshots run that lacks a cell `registry.json` lists (a filter). Gallery decisions lock the checkout they write to (`build/mg/gallery/decisions.lock`), not only their gallery. `critic` starts `claude -p` (or `MEGURI_CRITIC_CMD`) with `--restricted --safe-mode --tools Read,Glob,Grep --settings .claude/settings.critic.json` in a packet copy outside `$HOME`; keep those flags together, `critic --probe-isolation` checks them against the real CLI.
- Performance (U12, `mg.d/perf.sh`): every perf job writes perf results (`perf/perf-result.schema.json`, U241's gate input) and fails only when a suite cannot run, fails its own check, or writes an invalid result; budgets and baselines are U241's. `scripts/perf-compare/perf_compare.py` converts xcresult metrics and gungraun JSON and validates results (python3-jsonschema: dev and image-tools containers; its tests run in `image-tools-selftest`). `perf-ui` refuses any configuration but Profile and runs the `Meguri-Profile` scheme's Performance plan (`MG_APP_TEST_SCHEME`, `MG_APP_TEST_PLAN` steer `mg_app_xcodebuild_test` and the VM's xctestrun lookup). Every suite but `MG_PERF_UI_CHECK_SUITES` (the harness's own checks) must yield a perf result: perf-compare fails a suite with no metrics and a test whose declared intervals (the `meguri.perf.intervals:` activity `PerfTestCase` records, read per test with `xcresulttool get test-results activities`) have no measurements. `bench-mac` is the R1864 Apple-silicon run: host cargo (`core/target`, not the container's volume), collections from the nested `tools/mg fixtures`, every suite built before it takes `mg_host_lease --no-session` (exclusive, but a locked screen does not block it). On simulators `perf-ui` and `metrics` follow the simulator-job rules above (`mg_sim_begin`, build, `mg_sim_take`). In the VM, `metrics` runs xctrace and its `notifyutil` waiter there (Darwin notifications stay on their machine), signals xctrace through its pid file only while that pid still runs xctrace, kills both there on exit, and copies the trace back. A start that does not reach tracing in 60 s gets exactly one more, only once pgrep there shows the first's xctrace and waiter gone: two xctraces must never record one simulator. Such a stall is Instruments' DTServiceHub crashing as it starts ktrace (assertion in `authorized_ktrace_start_fd`, `DTServiceHub-*.ips` under the VM's `/Library/Logs/DiagnosticReports`; the cause of Time Profiler's failure too); on 2026-10-15 it hit 7 of 10 Logging starts, and neither retry recovered. Its default template is Logging: Time Profiler's CPU sampling never starts in the VM (xctrace waits forever and ignores SIGINT). A run in the VM gets its own baseline key (`vm/<name>/<model>/<build>`, the Mac's `vm/<name>`): VM timings never share a baseline with this Mac's. gungraun runs with ASLR on (`GUNGRAUN_ALLOW_ASLR`): Docker's seccomp refuses setarch's personality call.
- Git hooks: `tools/mg hooks install` (and `worktree new`) owns `commit-msg` and `pre-commit` in the shared hooks dir, each a shim running the checkout's own `tools/hooks/<name>`. A test that needs a commit to fail uses another hook (`prepare-commit-msg`).
- Private vault (U15, `mg.d/private.sh`): the only source is `local-data/anki/` of the checkout it runs in; `status`, `copy` and `suite` refuse CI markers (`MG_PRIVATE_CI_MARKERS`, in step with `CI_MARKERS` in meguri-testkit's `private/vault.rs`; `tests/private.bats` compares them) and implementer or fixer worktrees. Results, logs and messages carry counts, sizes, hashes and paths under `build/private/`, never collection text: agents read them. `scripts/private-scan/private_scan.py` is the one matcher for `scan-outputs`, `suite` and `hooks/pre-commit`; keep it runnable by macOS's `/usr/bin/python3` (3.9, stdlib only), since the hook runs there. Its unit tests need git, so `tests/private.bats` runs them in `tools/mg selftest`; never write a private string literally into a test of the build step, because tokens found in tracked files are dropped. `anonymize` (same file) applies the vault's refusals only to its default source (a vault copy); `--source` takes any other directory as is but refuses one under `local-data/`, and `--out`/`--salt-file` must lie under `build/`, the only part of the checkout the `private` service writes that is not committed. Its V3 runs the oracle job nested (`$MG_TOOLS/mg oracle check --schedule`) on the source and the clone with one `--now`/`--tz`, so it inherits that job's tree rule: on a unit branch carrying spec-side oracle changes it is `error` until integration.
