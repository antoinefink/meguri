# tools/vm/

The macOS test VM that runs every Mac XCUITest suite (U8b) and every simulator (U8c) (setup and verification: `docs/process/mac-ui-vm.md`; runner: `tools/mg.d/mac-vm.sh`; helpers shared with scripts outside `tools/mg`: `tools/scripts/mac-vm-lib.sh`).

- The VM lives on the external T9 drive and is named per host, never in the repository: `~/Library/Application Support/meguri/mac-vm.json` (or `$MEGURI_MAC_VM_CONFIG`), `{"tart": <wrapper>, "ssh": <wrapper>, "vms": [<name> | {"name", "ssh", "tart"}]}`. `ssh` runs its arguments as one shell command in that VM; `/Volumes/T9/meguri-vm/bin/vm-ssh` serves `meguri-mac` only, so a second VM (`tart clone`) needs its own wrapper in its entry. Mac UI runs take the first free VM. The simulator pool lives in the first VM that can run (the pool VM); a second VM adds capacity for Mac UI runs only.
- Jobs start a stopped VM headless in a session of their own (perl `setsid`), so it outlives the job. Never stop, delete or re-create a VM from a job; changing things inside the VM is allowed (Antoine, 2026-10-15). Never change the host's settings for it.
- Products, fixtures, drive scripts, snapshot baselines and the inventory go to the same absolute path in the VM, by tar over SSH (`xcode-check`'s script copies its own products and `VM_INPUTS`): the tests read the app, fixtures and baselines at their build or source paths (`BuildUnderTest.swift`, `HostedSnapshot.swift`), and `/Users/antoine` in the VM belongs to its user. A path outside the checkout is not this Mac's in the VM: a launch fixture there goes under the run directory, and the launch names that path (`mg_vm_fixture`); only this checkout's directories are ever replaced there. Captures the simulators write there (screenshots, videos, snapshot output) come back to the same path here and are removed there. Do not use tart's shared folders: virtiofs breaks Xcode's symlinks.
- Start tests or touch a simulator in a VM only while holding its lease (a recording of the same checkout lets its jobs in nested). Creating, booting or deleting a pool simulator counts as touching the VM (`sim-pool.sh` acquire and gc, `sim-setup`). A remote run outlives a lost SSH session or a killed job, so the lease holder stops any `xcodebuild test-without-building` or UI-test runner it finds there (`mvl_stop_tests`): when it takes the VM, right after a lost session (`mg_vm_xcodebuild_test`, `xcode_project_check.sh`) and when a job that started one is cancelled (`MG_MAC_VM_TESTING`, set by `xcode-check` around its devices phase too). A run it cannot stop ends the job's remaining suites (`MG_MAC_VM_LOST`), and the VM gets no new run until a later job stops it.
- The VM's login shell is zsh: build remote commands from single-quoted words (`mvl_q`). `TEST_RUNNER_*` variables do not cross SSH by themselves; `mg_vm_xcodebuild_test` passes them with `env`. A host path is the same path in the VM, but the bats fake (`tests/mac_vm_fake_ssh.sh`) maps every test path in a command: a value that must stay a host path (the pool's caller) travels in a file.
- `log show` in the VM needs `sudo` to see testmanagerd and WindowServer; take `--start` times from the VM's clock (`mg_app_log_now`).
- The host cannot record the VM's screen: Mac `drive --record` in the VM samples frames in the test runner. Simulators record with `simctl io recordVideo` in the VM.
- The VM's simulators need the pinned iOS runtime: `add-sim-runtime.sh` copies this Mac's image of it into the VM and adds it there (no download); doctor warns while it is missing. Some SpringBoards ignore appearance changes for good (seen in the VM after first boots and early restarts): after every boot the pool checks one and restarts SpringBoard until it applies them.
- `setup-guest.sh` is the one-time provisioning, run in the VM's Terminal (it asks for the VM account's password); it changes the VM only.
