# Spike S1: the occluded page and the in-frame swap

Date: 2026-10-16. Unit: U65. Toolchain: Xcode 27.0 (27A266a). Hosts: this Mac (Mac15,9, M3 Max, macOS 27.0.1 26A434), and the test VM `meguri-mac` (macOS 27.0.1 26A434, 60 Hz virtual display), whose pool simulator Meguri-Pool-iphone-1 is an iPhone 17 Pro on iOS 27.0 (24A434). Question (KTD11, swiftui-arch §1.2): can two full-frame, opaque WKWebViews that share one configuration, the idle one beneath, give a swap that shows a fully rendered card in the input's frame (R445, R465, R1807, R1862), raise the keyboard for `#typeans` (R534), and stay flat over a session (R1853)? If S1(b) failed, R1807 and the two-page model would be escalated.

## What was run

- `app/Packages/MeguriKit/Tests/CardRenderingTests/Spikes/OccludedPageSwapSpikeTests.swift` on this Mac (`tools/mg swift-test --package MeguriKit`), in a borderless window that is never on screen: WebKit runs no animation frames there, so these tests check loading, scripts, the message channel, round trips and memory, never frames.
- `app/MeguriUITests/CardSwapTimingSpikeTests.swift` through `tools/mg perf-ui --platform iphone|mac --suite CardSwapTimingSpikeTests` (Profile) in the VM, against the routes `spike/card-swap[/capture|/typein]` (`app/Meguri/TestHooks/CardSwapSpike.swift`). The harness stacks the two pages under a strip holding the baseline (two plain native views). Inputs alternate between a page swap and a baseline swap. Each swap changes z-order in place from the input handler, in the same commit as a SwiftUI label. The next card goes into the page beneath (insert, run its scripts, decode images, wait for fonts, then a double `requestAnimationFrame`) and counts as settled only then. After the commit, Meguri's isolated world in the front page posts the post-swap confirmation through `SwapRecorder` (U12), with `review.answerToNextVisible` and the new baseline interval `probe.nativeSwap`.
- Inputs: XCUITest taps on iOS (the swap runs on touch-down). On the Mac, macOS drops synthesized input on this toolchain, so the app posts mouse-downs to its own window through its event queue, stamped with the posting time, and a page-swap input waits until the next card has settled.
- Frame attribution: each swap draws a Metal drawable into the same commit (`CAMetalLayer.presentsWithTransaction`), whose presented time is the frame that shows the commit. A display link also records the target time of the first frame after the handler. Neither VM platform gives presented times: the iOS simulator SDK has no `addPresentedHandler`, and in the macOS VM every drawable reports presented time 0. All frame numbers below are therefore display-link estimates, which count any main-thread work after a swap as lateness.

## Decision

- The two-page model holds as KTD11 describes it; U66 and U67 start on it unchanged. Occlusion by a sibling view throttles nothing: the page beneath runs animation frames at the display rate, settles fonts, images and scripts, and comes forward with its content (no blank or stale frame on the simulator).
- Swap by reordering subviews in place: `bringSubviewToFront` on iOS, `sortSubviews` on the Mac. Never remove and re-add a page (each page moved into its window once in 1,000 swaps).
- Settled means: the card inserted, its scripts run, its images decoded, fonts ready, then a double `requestAnimationFrame` beneath. The page swap takes no web-content call before it; shown hooks and the confirmation go after the commit (from `CATransaction`'s completion block).
- The post-swap confirmation comes from Meguri's isolated world (`WKContentWorld.world(name:)` with the handler added for that world only), as U12's `VisibleConfirmation` contract says. Pass only the token as an argument and read the card from the DOM.
- R534: make the newly front page first responder in the swap's turn (U67 already plans it), then `focus()` from the shown hook. The fallback (keyboard on first tap) is not needed on the simulator; the device check is a U256 checkpoint.
- `callAsyncJavaScript` costs about 0.1 ms a round trip on this Mac: cheap enough for prepare and present calls, but the swap itself makes none.
- Frame attribution: `presentsWithTransaction` drawables are the frame probe U243 builds on, where presented times exist (devices, this Mac's own screen). On simulators and in the VM, frame numbers are display-link estimates, which count the main-thread work after a page swap (its confirmation, the next card) as lateness, so S1(b) is checked for function only there: `CardSwapTimingSpikeTests` allows one frame of slack at p95 and gates p99 only when every swap had a presented time. VM stalls of up to 1.8 s showed up as p99 and maximum outliers on both kinds of swap.
- S1(b) did not fail anywhere it could run: at p95 the pages land in the baseline's frame on both VM platforms. Its intended evidence, 120 Hz on this Mac's built-in display against an Instruments trace, needs this Mac's screen, which agents may not take (root AGENTS.md), and no `tools/mg` job uses that screen while the test VM exists. It stays open until Antoine runs `CardSwapTimingSpikeTests/testPageSwapFromInputLandsInTheBaselineSwapsFrame` on this Mac (Meguri-Profile scheme, Performance plan, under Instruments' os_signpost), which gives Metal-presented frames and applies the p99 gate. U243 stays report-only until then (perfqa coverage note).
- Open for the U256 device checkpoints: S1(b) at 120 Hz on the iPhone 17 Pro, S1(c) on the Mac, and S1(e) on a device.
