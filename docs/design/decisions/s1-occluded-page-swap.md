# Spike S1: the occluded page and the in-frame swap

Date: 2026-10-16. Unit: U65. Toolchain: Xcode 27.0 (27A266a). Hosts: this Mac (Mac15,9, M3 Max, macOS 27.0.1 26A434), and the test VM `meguri-mac` (macOS 27.0.1 26A434, 60 Hz virtual display), whose pool simulator Meguri-Pool-iphone-1 is an iPhone 17 Pro on iOS 27.0 (24A434). Status: **gate pending; S1(f) failed for web content memory, escalated.** U65's execution note makes S1(b) on this Mac's screen, against an Instruments trace, the check that unblocks U66, U67, U175, U176 and U243's gating; no agent can run it (runbook below). S1(a), (d) and (e) passed; (b) passed for function on the iPhone simulator and in the test VM; (c) passed on the iPhone simulator and in the macOS test VM, and is open on this Mac's own display (same runbook); (f) passed for the pages, the DOM, the app's memory and card retention, and failed for web content memory, on screen as off screen: R1853's web content reading needs a plan decision (Decision below). Question (KTD11, swiftui-arch §1.2): can two full-frame, opaque WKWebViews that share one configuration, the idle one beneath, give a swap that shows a fully rendered card in the input's frame (R445, R465, R1807, R1862), raise the keyboard for `#typeans` (R534), and stay flat over a session (R1853)? If S1(b) failed, R1807 and the two-page model would be escalated.

## What was run

- `app/Packages/MeguriKit/Tests/CardRenderingTests/Spikes/OccludedPageSwapSpikeTests.swift` on this Mac (`tools/mg swift-test --package MeguriKit`), in a borderless window that is never on screen: WebKit runs no animation frames there, so these tests check loading, scripts, the message channel, round trips and memory, never frames. Memory is this process's footprint and that of the pages' web content processes (pid from WebKit's `_webProcessIdentifier`, read in test code only; footprint from `proc_pid_rusage`). S1(f)'s bursts put 1,000 cards through the pair a frame apart, read memory after 3 s of rest at swaps 100 and 1,000 and once the session closed (both pages dropped their card), then make the pages collect their garbage and count the card elements a `FinalizationRegistry` in each page saw collected. The app's burst (below) does the same.
- `app/MeguriUITests/CardSwapTimingSpikeTests.swift` through `tools/mg perf-ui --platform iphone|mac --suite CardSwapTimingGateTests --suite CardSwapTimingSpikeTests` (Profile) in the VM, against the routes `spike/card-swap[/capture|/typein]` (`app/Meguri/TestHooks/CardSwapSpike.swift`). The harness stacks the two pages under a strip holding the baseline (two plain native views). Inputs alternate between a page swap and a baseline swap. Each swap changes z-order in place from the input handler, in the same commit as a SwiftUI label. The next card goes into the page beneath (insert, run its scripts, decode images, wait for fonts, then a double `requestAnimationFrame`) and counts as settled only then. After the commit, Meguri's isolated world in the front page posts the post-swap confirmation through `SwapRecorder` (U12), with `review.answerToNextVisible` and the new baseline interval `probe.nativeSwap`.
- Inputs: XCUITest taps on iOS (the swap runs on touch-down). On the Mac, macOS drops synthesized input on this toolchain, so the app posts mouse-downs to its own window through its event queue, stamped with the posting time, and a page-swap input waits until the next card has settled.
- S1(c), no blank or stale frame: each card carries a marker, a band across the middle of the page whose colour names the card (64 colours, each channel 64, 112, 160 or 208, none near white, black or the page's own background). On iOS the window is rendered (`drawHierarchy`, current frame) at each page swap's frame. On the Mac a ScreenCaptureKit stream takes every frame of the app's own window (`SCShareableContent.currentProcess` offers a process its own windows without the Screen Recording permission); each frame from the first page swap on must show the card of the last swap handled before it (or, until one frame after that swap's frame, the card before), never no card's marker, never an older card. Controls come first, on card 1 before any swap: the check must name the capture `card`, then `stale` against card 2 and card 3, then `blank` with the front page's card hidden, then `card` again. Runs before this round compared one background colour per card parity, so a page still showing its own previous card passed: their S1(c) results are superseded.
- Frame attribution: each swap draws a Metal drawable into the same commit (`CAMetalLayer.presentsWithTransaction`), whose presented time is the frame that shows the commit. A display link also records the target time of the first frame after the handler. Neither VM platform gives presented times: the iOS simulator SDK has no `addPresentedHandler`, and in the macOS VM every drawable reports presented time 0. All frame numbers below are therefore display-link estimates, which count any main-thread work after a swap as lateness.
- The frame gate (`app/MeguriUITests/CardSwapTimingGate.swift`, checked by `CardSwapTimingGateTests`) takes its mode from where the run is, never from the samples: function only on the iOS simulator and wherever `kern.hv_vmm_present` says virtual machine (one frame of slack at p95, nothing more); strict everywhere else, also when that cannot be read. Strict requires the Metal probe, a presented time for every swap and every input resolved, the pages' p95 in the baseline's frame (from the event and from the handler), and p99 at most one frame later. A swap without a presented time therefore fails a strict run instead of relaxing its gate.

## Decision

- Gate: pending until Antoine's run of S1(b) on this Mac passes (runbook below). The plan makes that run, not the VM's function checks, the step that unblocks U66, U67, U175, U176 and U243's gating. If it fails, S1(b) has failed: escalate (R1807 and the two-page model depend on it).
- On every check that could run, the two-page model holds as KTD11 describes it. Occlusion by a sibling view throttles nothing: the page beneath runs animation frames at the display rate, settles fonts, images and scripts, and comes forward with its content (no blank or stale frame on the iPhone simulator or in the macOS VM).
- Swap by reordering subviews in place: `bringSubviewToFront` on iOS, `sortSubviews` on the Mac. Never remove and re-add a page (each page moved into its window once in 1,000 swaps).
- Settled means: the card inserted, its scripts run, its images decoded, fonts ready, then a double `requestAnimationFrame` beneath. The page swap takes no web-content call before it; shown hooks and the confirmation go after the commit (from `CATransaction`'s completion block).
- The post-swap confirmation comes from Meguri's isolated world (`WKContentWorld.world(name:)` with the handler added for that world only), as U12's `VisibleConfirmation` contract says. Pass only the token as an argument and read the card from the DOM.
- R534: make the newly front page first responder in the swap's turn (U67 already plans it), then `focus()` from the shown hook. The fallback (keyboard on first tap) is not needed on the simulator; the device check is a U256 checkpoint.
- `callAsyncJavaScript` costs about 0.1 ms a round trip on this Mac: cheap enough for prepare and present calls, but the swap itself makes none.
- Frame attribution: `presentsWithTransaction` drawables are the frame probe U243 builds on, where presented times exist (devices, this Mac's own screen). On simulators and in the VM, frame numbers are display-link estimates, which count the main-thread work after a page swap (its confirmation, the next card) as lateness, so S1(b) is checked for function only there (`CardSwapTimingGate`). VM stalls of up to 1.8 s showed up as p99 and maximum outliers on both kinds of swap.
- S1(b) did not fail anywhere it could run: at p95 the pages land in the baseline's frame on both VM platforms. Its intended evidence, 120 Hz on this Mac's built-in display against an Instruments trace, needs this Mac's screen, which agents may not take (root AGENTS.md), and no `tools/mg` job uses that screen while the test VM exists. U243 stays report-only until it passes (perfqa coverage note).
- S1(c) on the Mac passed in the test VM (60 Hz virtual display): the app captures its own window with ScreenCaptureKit, which needs no Screen Recording permission for a process's own windows. U176's "no white flash" on the Mac host is the same test on this Mac's display at 120 Hz, in Antoine's run (runbook, step 4); U176 can reuse the capture (`TestHooks.WindowCapture`).
- S1(f) failed for web content memory, and is escalated: R1853 as KTD11 reads it (within 5 MB from card 100 to 1,000, back within 10 MB of the warm level once the session closes, U245) is not met on screen in the iPhone simulator (+10.3 and +13.4 MB, 13.4 and 15.6 MB above warm) nor off screen on this Mac (1.6–19.8 MB, 11–20 MB above warm). It is not the two-page model: no page keeps a card alive (finalization counts; the 64 KB control shows the check sees retention), and one page taking every update with no swap grows the same. It is memory WebKit keeps in its own allocator after DOM writes, given back only to WebKit's memory-pressure release, which no public API lets the app start at session end; dropping the card DOM (KTD11's release) gives none of it back. So U176's session-end release cannot meet that reading as built. The plan must decide before U176 builds the release and U245 gates R1853. Options seen here: hold web content to retention (no card alive, the control's sensitivity) instead of footprint; accept a measured bound per 1,000 cards (here about 10 MB in two processes, linear to at least 3,000); or measure after a system memory-pressure event. U66 and U67 do not depend on the choice. The tests keep the R1853 check for web content as a known issue (`OccludedPageSwapSpikeTests`) and an expected failure (`CardSwapTimingSpikeTests`), labelled failed and escalated, so a run that meets it shows.
- Open for the U256 device checkpoints: S1(b) at 120 Hz on the iPhone 17 Pro, and S1(e) on a device.
