# Test tiers, quarantine and scheduled runs

Every verification job belongs to a tier (R1950). `tools/gate/tiers.yaml` is the one list: each run is a `tools/mg` job with its arguments, tier, the paths that trigger it, where its work happens (R1952) and a time budget. The gate refuses that file when a registered job has neither a run nor a line under `utilities`, so a new job must be placed in a tier in the change that adds it.

## Current verification cadence

Antoine’s updated goal on 2026-10-25 permits coherent batches of 3–5 related units, including Swift/FFI, shared schemas, sync contracts and tooling. Use milestone order and dependency order for integration. Independent task branches can prepare changes in parallel under [the integration workflow](merge.md). Each unit retains focused checks, independent review, its own commit and review log, and provenance/privacy/similarity checks. Pure Rust internals may cover at most 20 units between full gates.

Record the batch base before its first unit, its unit list and each unit’s starting commit. Mark completed units as awaiting the batch gate until that gate passes, then link its shared receipt from every covered review log. Run `tools/mg gate --base <batch-start-commit>` at each coherent integration batch boundary, after at most 20 pure Rust units, and at every milestone boundary. The base precedes the first pending unit and covers every pending change. Resolve required technical failures before crossing the integration boundary.

Individual gates use `tools/mg gate --base <unit-start-commit>`; an open batch always uses its original batch base so every pending change is covered. Focused checks diagnose changed behavior; the full gate’s native suites also provide affected-platform verification. Run separate native checks first only when a platform-specific risk or unresolved failure warrants them. Do not duplicate full gates for isolated Rust changes within an open batch.

Fix known review findings and run affected lint and focused checks before the full gate. Use focused checks to find a failure's cause. Keep unchanged checked build products, run Apple builds one at a time, and use shared receipts only for valid inputs and coverage. Keep failures, assertions and limits; never add retries.

Milestone and final acceptance suites and required human evidence remain mandatory. Gate arguments, path triggers, result validity, quarantine, catch-up and milestone evaluation stay as defined below.

## The gate

`tools/mg gate [--local] [--base <rev>] [--all] [--only <run>,...] [--plan]` measures the change from `--base` (default: where the branch left the main checkout's branch) to `HEAD`, working-tree changes included, and runs in this order:

1. Static stage: `tools/mg static-checks`, every time. It fails when a test, script or scenario names an AnkiWeb host (R1876; only the U116 and U255 binary-scan scripts may be allowed, in `tools/gate/static-checks/ankiweb-allow.txt`), when a commit of the branch lacks its provenance trailers (the commit-msg hook's rules, so a `--no-verify` commit is caught), or when a test plan, nextest configuration or script retries failing tests (R1953).
2. Canary stage: the pin canary (`core-test --canaries`) and the canary scenarios (the 10,000-pair fuzz table, pending until U45; its smoke subset; the unicase collation scenarios). A canary whose failure blocks stops the gate; nothing else starts (AE82: a pin bump fails before anything else). A quarantined canary failure does not block, so it stops nothing.
3. T0 runs whose triggers match a changed path.
4. T1 runs, only when T0 has nothing blocking. The live-oracle run gets the scenario areas of the changed crates (`filters` in tiers.yaml); a change to the runner, the CLI, the lock file or the scenarios selects every area.

Each run is a nested `tools/mg` call: its result is final. Nothing is retried. The gate writes `build/mg/gate/<run>/receipt.json`: the commit, whether the tree was dirty, the base, every run with its outcome, the quarantine state, the receipt-level blockers and the blocking failures. A job that changes the working tree fails the gate (a receipt is for a commit): a receipt-level `tree-changed` blocker, which `tools/mg merge` carries over. A run over its budget is reported, not failed.

Outcomes: `pass`, `warn`, `queued` (the machine's state kept the run from testing, see below), `quarantined`, `fail`, `error`, `needs-oracle-tree`, and for runs that did not start `not-triggered`, `pending` (the job lands with a later unit), `disabled` (the job exists, its run waits for the named unit), `unresolved` (an argument could not be filled in), `skipped-local`, `deferred-main`, `deferred-tip`, `user-step`, `skipped-after-canary`, `skipped-after-t0`. `fail`, `error`, `unresolved` and `needs-oracle-tree` block. A receipt with a `skipped-*` or `deferred-*` run is incomplete and never merges.

- `--local` skips the similarity scan and the oracle-image runs: an implementer worktree has no `refs/` or `oracle/` (U2). Implementers run it during review rounds. Its receipt never merges.
- In a role worktree, `where: main` runs (the similarity scan, the static checks over the whole tree) are `deferred-main`: `tools/mg merge` runs them from the main checkout. `where: tip` runs (the similarity self-test: the branch's scanner with the main checkout's corpus) are `deferred-tip`, and so are oracle-image runs and the runs that read `oracle/` files (`oracle_files`: goldens-check's lock pin, harvest-report's inventory; `--local` included) when the main checkout's `oracle/` is not exactly this branch's: `tools/mg merge` runs them in a full checkout of the tip.
- An oracle job that refuses the `oracle/` it would use (`oracle-tree-differs`, `no-oracle-tree`: `conformance --live` fails with it, `oracle test` errs) is `needs-oracle-tree`; `tools/mg merge` runs it again in that full checkout.
- An argument `{artifact:<run>:<file>}` is a file an earlier run of the same gate wrote: harvest coverage reads the live oracle run's T1 report (`t1-live.json`), so live chains that pass live count as passing.
- `--plan` prints the plan and runs nothing.

### Queued runs (U19b)

A run that cannot test because of the machine's state is `queued` (status warn, `details.queued`), never `error`: there is no test VM (user step `mac-vm`), the host session is locked or its display sleeps (`host-session`: the jobs that launch the app on this Mac), or macOS drops the input XCUITest synthesizes (`mac-input`: macOS 27.0.1 does). Antoine approved this on 2026-10-17 (R1951 as amended). Only these states queue a run. A job keeps every result it did produce and lists each part that did not run in `details.queued_parts` (`user_step`, `part`, `reason`): xcode-check queues its devices phase and keeps its builds, snapshots queues the Mac and keeps the simulators, mac-ui queues the suites whose input was dropped and keeps the others. A failure in a part that ran still makes the run `fail`, and an error `error`; only a run with nothing else wrong is `queued`.

A test VM that is there but cannot be reached is the machine's state too (U19c, user step `mac-vm`, with the reason): it gives no logged-in session over SSH within 240 s, an SSH call to it fails as ssh (exit 255, among them "exec request failed on channel 0") or its command could not start or fork there, or it keeps fewer than 400 free processes. The last is checked before a job starts work in the VM: once the job holds the VM's lease and has stopped any run left there, it waits while the VM is near its process limit, checking again after 10 s, then twice as long each time (at most 120 s apart), for at most 10 minutes, so that concurrent jobs stop pushing it over; still near it, the job is queued. This applies wherever VM jobs run (`perf-ui`, `a11y`, `snapshots`, `mac-ui`, `drive`, `run`, `metrics`, `sim`, `sim-setup`, `xcode-check`'s simulator runs): the part the VM could not take is queued, the parts that ran keep their results. A VM that tart cannot start, a run there that cannot be stopped, and a result the VM answered but that is wrong or missing stay `error`. The build orchestrator added this on 2026-10-18 (U19c) as a follow-up of U19b, which Antoine approved on 2026-10-17, after the merges of U28, U32 and U63 failed only because the VM, up but at about 2,000 of its 2,900 per-user processes under load, could not start SSH sessions.

A queued run does not block. The receipt names, per run, its `user_steps` and `queued_parts`, and lists the queued runs under `queued`; the gate's message names them (`pass with notes (...); queued: xcode-check (host-session)`). After a merge, `tools/mg merge` appends each queued run to the catch-up queue, and `tools/mg catch-up` runs it again on the integration branch once `tools/mg doctor` reports its user step clear (docs/process/merge.md). A milestone gate never accepts a queued result: it counts as missing, awaiting the user step it names, so the Mac checks must pass before M1R closes.

For direct work on `master`, a full `tools/mg gate --base <unit-start-commit>`
also appends queued checks to catch-up when its receipt is complete and clean
and the tip commit carries `Unit:`. Local, partial and dirty runs do not.

The gate's live-oracle job uses `conformance --live-only`: it runs fresh T1
workers after the separate dual-lane T0 job. Its result counts only T1.
Stale or missing goldens fail T1; this mode does not re-record them.
Standalone `conformance --live` still runs both T0 and T1. T0's triggers cover
every live-oracle filter path, including changes to the oracle tooling.

## Quarantine

A flaky test fails the gate until it is fixed or quarantined (R1953). `tools/gate/quarantine.yaml` lists quarantined tests: the tiers run and the failure id its job reports, a class, an owner, a reason, a deadline, `approved_by: antoine` and evidence. A quarantined test still runs and is reported; its failure does not block until the deadline. After the deadline the gate fails, whether the test failed or not.

1. Run the gate twice on one clean commit: the test fails in one run and its run passes in the other. These receipts are the evidence.
2. Record an approval escalation (`tools/mg escalation add --kind approval ...`) and ask Antoine in chat.
3. Only after his approval: `tools/mg quarantine add --run <run> --test <id> --class <class> --owner <owner> --reason <text> --deadline <date> --failed <gate run> --passed <gate run> --approved-by antoine [--escalation <id>]`. It checks the receipts and writes the entry. Commit `tools/gate/quarantine.yaml`.

An entry without the approval or the evidence makes the gate fail. A test of a conformance, sync or data-safety run keeps that class. Every milestone run fails while any conformance, sync or data-safety test is quarantined. `tools/mg quarantine check` validates the file.

## Nightly and weekly

`tools/mg nightly [--weekly] [--seed N]` runs T2 and writes one summary result. It draws one seed per night (or takes `--seed`), passes it to every run that takes `{seed}`, and logs it in the summary, so `tools/mg nightly --seed N` replays a night (R1937). The runs' budgets are in tiers.yaml; the differential fuzzer (U247) runs 30 to 60 minutes.

Local scheduled runs remain available. `tools/mg nightly --print-schedule` writes two launchd entries (nightly at 02:30, weekly on Sundays at 04:00). Installing them is Antoine's step `nightly-scheduler` (docs/process/one-time-setup.md); agents never install them. GitHub Actions runs public synthetic Docker jobs independently of image publication. Hosted receipts identify the exact commit, job, and outcome. Keep the existing batch and release requirements until a hosted run proves equivalent coverage, including the required features, cases, skip policy, platform and architecture. A Docker conformance result supplies its Docker lane.

For warm development feedback, select affected cases with `tools/mg core-test -- -E '<filter>'` and group Swift test filters in one `tools/mg swift-test -- --filter '<pattern>' --filter '<pattern>'` call to share its preparation. `tools/mg core-test --quick` runs the canaries and ordinary Core checks with FFI test hooks. `tools/mg core-test --stress` requires successful reports for exactly the 10,000-session review case and the two 150,000-card sync cases. GitHub runs the quick checks for routine verification and the scale checks on master: nightly, manually and for Core or runner input changes. A bare `tools/mg core-test` leaves the three cases out, as `--quick` does. The gate's `core-test` run passes explicit arguments (`-- --features meguri-ffi/test-hooks`), so it and the local release gate still run all three.

## Milestones and release

Manual device and reference checks are deferred until the final session (Antoine, 2026-10-20). Continue with automated VM tests. Final evidence remains required.

Milestone and release similarity scans cover the full committed tree with `--rev <tip>` and no `--base`. Ordinary unit gates scan their change with the T0 similarity run's `--base <base>`.

`tools/mg milestone <milestone|release>` runs in the main checkout on a clean tree. The milestones are the ids of `docs/process/milestones.yaml`'s `milestones` list, in delivery order (M0, M1R, M1–M5); no tool names them otherwise. A milestone run runs in full (no path triggers) exactly the runs that milestone's gate reads (`milestone_gate.py runs`): its suites and every earlier milestone's, the global suite conditions from their `from` milestone, its deferrals' cells, and the runs whose files those take as `{artifact:...}` arguments; it lists the T4 runs of its user steps' kinds as awaiting Antoine. Nothing of a later milestone runs: M1R never runs M1's `bench-mac`. An invalid manifest runs nothing. `release` runs every T0 and T1 run, then T3, and lists T4. It writes one summary result. It fails when a run fails, while a conformance, sync or data-safety test is quarantined, and on the R1880 rules of its harvest-coverage run: no unclassified harvest row at any milestone, and at release no in-scope or preservation-only scenario that does not pass. Harvest coverage takes the statuses of live chains from the full live-oracle run of the same milestone run; without that report (T1 did not run) it is `unresolved`.

`tools/mg milestone-gate <milestone>` (U240) then decides whether the milestone closes. `docs/process/milestones.yaml` lists, per milestone, its units, its suites (tiers runs of T0, T1 or T3, with scopes and pass rules), the budgets its device runs cover, Antoine's user steps with their evidence and validators, approved deferrals, and the conditions every gate checks. Gates are cumulative: a milestone's suites, units and deferrals include every earlier milestone's. The gate:

- reads the latest result of each suite's run with the milestone's arguments from `build/mg`; every result must be from one clean commit, the gate commit, and a missing result fails; a queued result awaits Antoine, naming the user step it waits for (it never passes); a warn that is not awaiting Antoine (an unavailable lane, a pass with notes) fails unless an approved deferral that still holds covers it, and then only its deferred cells are waived: every other cell and pass rule of the suite must still pass; an `{artifact:...}` argument must be that file of the result the gate reads for its run, on the same commit;
- accepts later commits that touch only evidence paths (`milestone-records/`, `conformance/private/`, the user steps' evidence) and reads the evidence from HEAD's commit, never the working tree;
- needs every unit merged at or before the gate commit (a `Unit:` trailer from an implementing role) with no open escalation;
- fails while a conformance, sync or data-safety test is quarantined or any quarantine entry is invalid or expired.

The outcome is `pass`, `fail`, or `awaiting_user` (status warn) when only Antoine's evidence is missing. Outside the main checkout the gate evaluates but always fails: a unit branch carries its own `Unit:` trailers, so its units look merged there. A pass writes `docs/process/milestone-records/<M>.json` (commit, per-suite counts, user-step results, open quarantine entries with owners, deferrals); commit it. `tools/mg milestone-gate --check`, a T0 run, keeps the manifest equal to the plan's Delivery Milestones table (every row, in order) and Unit Index and its suites on runs that `tools/mg milestone` executes. It also binds the table's text to the definitions that run: every part of a milestone's closing gate and user steps texts must be claimed by the `plan` excerpt of the suite, global condition or user step that implements it, every definition that quotes the text must be needed, definitions that share text bind the same scope items, and the table's wording fixes each user step's validator type, so removing a required suite, scope item, device run or user step, or swapping a user step's validator, fails it (and the evaluation). Device runs are U241's device-run reports (`tools/mg perf-gate --results <dir> --device-run <M> --device <d>`), checked against `tools/perf/budgets.yaml`: every device case recorded and judged again from its values; a case whose measurement waits on a later unit keeps the step pending.

## Changing tiers.yaml

- A job that lands later is listed with `pending: <unit>`. Once the job is registered, the gate refuses the file until that unit wires the run (removes `pending`).
- `disabled: <reason>` holds back a run whose job exists (the critic waits for U254, because a critic run writes `docs/design/screen-status.yaml`).
- `needs` names what a run uses: oracle, sync server, image diff and frame extraction run in Docker; simulators, devices and Mac UI on the host or the test VM (R1952). The gate refuses a placement that breaks this.
- A new conformance area adds its crate to the live-oracle `filters`.
- A run whose job reads files under `oracle/` without starting the oracle (`mg_conf__oracle_file`) sets `oracle_files: true`; otherwise a branch that changes `oracle/` fails it against the main checkout's tree.
