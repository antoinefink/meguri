### A1. The overlay class bounds stabilities by relative 1e-4 or 1e-5 days

- Before: U14's Approach said goldens-check accepts overlay memory entries within 1e-5.
- Why: the probe found 5,549 differing memory values between the Linux and Apple oracles. 12 of them, all stabilities, differ by relative 1.04e-5 to 9.4e-5. Each is one unit in the last place of a math-library result close to 1 that FSRS subtracts 1 from (float-determinism F8.3, F11.1). In absolute terms the 11 again stabilities are at most 4.9e-7 days apart. The spec writer widened F8.3 for stabilities with that evidence (cd1e4b8), and Meguri's class check follows it (55b1911); difficulties keep relative 1e-5.
- Now: the Approach states F8.3's rule. The class covers only the two oracles' differences. Meguri's comparisons with expected values keep R1886's relative 1e-5 (O7, F11.3): on macOS the expected values hold the Apple oracle's exact values, and Meguri-macOS equals them bit for bit.

### A2. The fuzz-table scenario's Meguri run moves from U14 to U45

- Before: U14's Verification asked T0 to pass the FSRS and the fuzz scenarios on both platforms.
- Why U14 cannot meet it: `fp-probe/corpus/fuzz-table` observes the existing `fuzz_table` kind (F4, O4) on a card that the `presets`, `decks`, `notetypes` and `notes` setup sections make. Building those setup sections in the testkit here would write U27-U29's note, deck and preset logic ahead of the core. The plan's M0 row already expects the fuzz-table scenarios pending until U45.
- Now: U14's Verification asks T0 to pass the FSRS scenarios (`fp-probe/next-states-edges`, `fp-probe/corpus/next-states-*`) and the probe's fuzz table to agree on all four sides (F10.2). `meguri-cli fp-probe` computes that table with the same meguri-sched functions T0's adapter will use.
