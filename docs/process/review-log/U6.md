# U6 review log

Unit: U6, FFI crate, XCFramework build and MeguriCore package with CoreBridge.
Review rounds run: 2. Implementation: 5b95473, 21836ed, 3b39c61 (rebased onto feat/meguri-v1 at b165153).

## Round 1 (fixed in 4bffa4d)

- Input hashing could miss content: `git ls-files` quotes non-ASCII and special-character paths, `hash-object` could not open them, and the failure was hidden inside a command substitution, so the hash covered only file names. Paths now stay in git's quoting for `--stdin-paths`, the manifest is built outside any substitution, and the number of content ids must equal the number of inputs.
- Equal `uniffi_*` symbol sets did not prove an equal API (a cfg-gated signature or record field changes no symbol). Every non-Mac slice now also generates its bindings, and they must match the Mac slice's before anything is written.
- A failed `cp` or `rm` in the replace step sat in an `&&` list, so `set -e` ignored it and a new stamp could cover stale outputs. Both now stop the run, and the stamp is marked `incomplete` while outputs are replaced.
- Profile, Release and AppStore share cargo's release archive, so a concurrent Profile build could put test hooks into an AppStore package. Runs past the no-change check now hold locks on the outputs and the cargo target dir, and each slice's archive is cloned right after its build.
- The cache check now also requires each slice's header and modulemap.
- `tools/mg swift-test --package` with no name looped forever; it is now a usage error, with a bats test.

## Open after round 2

- P3 (advisory; reported twice, by the conformance and the correctness lens): concurrent `tools/mg selftest-xcframework` runs in one checkout destroy each other's sandbox. `tools/mg.d/selftest.sh` always passes `build/selftest-xcframework/sandbox` and the same target dir, and `tools/tests/xcframework_selftest.sh` starts with `chmod -R u+w` and `rm -rf` of that sandbox; nothing serializes runs. Observed during review with parallel agents in the U6 worktree: false failures (`build-core-xcframework.sh: No such file or directory`, another run's edits, unexpected "waiting for another run" lines, wrong slice sets); the suite passed when run alone with a private sandbox. Fix: hold a waiting lock on `build/selftest-xcframework/.lock` for the whole run in `mg_selftest_xcframework`, or give each run its own sandbox (for example under `$MG_RUN_DIR`) and share only the cargo-locked target dir.
- P3 (advisory): a dangling symlink under `core/` makes every pre-action, `tools/mg core-xcframework` and `tools/mg swift-test` run fail. `tools/scripts/build-core-xcframework.sh` lists untracked files with `git ls-files -co`, and `git hash-object --stdin-paths` follows symlinks, so a dangling one (Emacs lock files such as `.#lib.rs`) dies with exit 128 and only a cryptic git message. Fix: hash a symlink by its link text, as git stores it (filter `[ -L ]` entries out of the stdin list and add their `readlink` output to the manifest), or skip dangling untracked links; at minimum ignore `.#*` and name the path in the error.
- P3 (advisory): missing or invalid option values report a build failure instead of a usage error. `build-core-xcframework.sh` reads option values with `${2:?}` (exit 1), and an unknown configuration or slice name goes through `die` (exit 1); `tools/mg.d/bridge.sh` maps only exit 2 to a `usage` failure. So `tools/mg core-xcframework --configuration` or `--configuration Relase` is reported as status `fail`, as if the build broke. Fix: check `[ "$#" -ge 2 ]` before reading `$2`, and exit 2 for an unknown configuration or slice name and for `--xcode` with `--slices`.

- P3 (advisory, found at integration, not a rebase regression): the package tests run on an iOS 27 simulator (`xcodebuild test -scheme MeguriCore`, `ARCHS=arm64`) pass 14 of 15. `VersionTests.swiftTestRunsAgainstTheDebugFeatureSet` expects `info.target == "aarch64-apple-darwin"`, so it fails on any slice but the Mac one. The unit's verification is host `swift test`, where it passes; it will fail once U7 runs CoreBridgeTests on simulators. Fix: expect the triple of the platform the test runs on (`#if os(macOS)` / simulator), or limit that expectation to macOS.
