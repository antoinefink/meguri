## Open after round 6

1. P1: `specs/conformance/sync-ops.md` (spec writer). It does not exist. It must define:
   - the `sync` op: login, normal sync, full upload and full download, with result and error kinds, including the clock error kind and a network error;
   - the actors: Meguri clients `meguri`, `meguri_2`, … and oracle clients `client_a`, `client_c`, …, and how a scenario declares them;
   - the convergence observation: normalized `db_dump`s of all parties after a final full download by a fresh client, with each excluded field and the reason it is excluded;
   - the per-scenario proxy of item 5.

   The same change updates `specs/conformance/dsl.md` (its `sync` row is `draft (sync)` with only `client?: <name>`, and it has no actor syntax), `specs/conformance/observations.md` (`db_dump` is `draft (storage)`), `conformance/schema/scenario.schema.json` (no actors), `conformance/schema/observation.schema.json` and `specs/conformance/interop-vocab.txt`. U117, U118 and U248 build on this DSL.
2. P1: Oracle ops (oracle maintainer), behind the protocol of item 1: `oracle/driver/ops/sync_server.py`, `oracle/driver/ops/sync_client.py` and `oracle/driver/observe/db_dump.py`. They must provide:
   - the server as a child of the oracle worker, on the scenario's faked clock;
   - a fresh base directory and fresh users per scenario;
   - a second clock file 301 s ahead (R1932);
   - oracle clients that log in, sync, full-upload and full-download.

   Until they exist, the M0 exit criterion "A two-client full upload and download runs under a frozen clock (U13)" is unmet, and T1's sync smoke has nothing to run.
3. P1: `core/crates/meguri-testkit/src/exec/parties.rs` (implementer, after items 1 and 2). It is the only multi-party executor. It passes every Meguri and oracle-client endpoint through `check_endpoint` before connecting; today `check_endpoint` has no caller outside meguri-sync's own tests, so R1876 guards no harness path. It declares the `sync` capability only when Meguri supports it, so scenarios that need it report `pending`.
4. P1: `conformance/scenarios/smoke/sync/`, with goldens recorded by the oracle (after items 1–3):
   - two-party: client A adds a note and full-uploads, client C full-downloads, and the dumps are equal except the documented fields;
   - three-party;
   - the same scenario with the Meguri executor reported `pending`, not failed;
   - a server on the skewed clock: the oracle client gets the clock error kind;
   - toxiproxy `reset_peer` mid-transfer: the client reports a network error and its collection still opens.

   These are four of U13's six test scenarios and its Verification line, "Two-party and three-party smoke scenarios pass against the child server".
5. P1: Fault injection and recording on the conformance path. The rig's toxiproxy and mitmdump are only on the internal `sync-rig` network, and oracle workers are only on `oracle-internal`. So no oracle client can reach a fault proxy or a recorder in front of the worker's child server. The reset_peer smoke has no proxy to run through, and U105's "mitm recordings of oracle-client traffic" (R1933) have no recorder in reach. `conformance/recordings/` holds no recording; today the only way to make one is an Anki desktop pointed at the rig by hand. sync-ops.md (item 1) must define a per-scenario proxy on `oracle-internal` in front of the child server: toxiproxy for faults and mitmdump with `record_sync.py` for recordings. Its upstream is set per scenario, and only after `check_endpoint` passes. Items 2 and 3 and `docker/compose.yml` then build it. The real-clock rig serves only end-to-end runs and does not replace it.
