## Round 1 (fixer s-20261017T090033Z-1a6a8758; fixed in ef96cac)

- A Mac drive whose input macOS dropped returned `queued` before looking at anything else, so a failed launch, a script error or a hierarchy issue ended non-blocking. Only the driver's failed steps from the first tap, type, swipe or scroll on are now the drop's doing; the others fail or err the drive.
- `catch-up` marked a failed re-run's entries `failed` even when its `blocked-red` escalation could not be recorded, so the escalation was lost. Such entries are now `escalation-pending` and the next catch-up records the escalation from the saved result without re-running the job.
- `catch-up` piped the queue reader into jq, so a truncated or broken line read as an empty queue. A line that is not an entry now stops the run (`queue-unreadable`).
- Two catch-ups at once ran the same entries twice and could escalate twice. A catch-up now holds `build/mg/catch-up/lock` (a dead holder's lock is taken over).

## Round 2 (fixer s-20261017T102229Z-1f5f38d7; fixed in 84c1f04)

- mac-ui, a11y and perf-ui on the Mac turned any failed XCUITest run into `queued` once the unified log showed dropped input, so a failing input-free test beside a dropped tap was non-blocking. The drop now explains a failing test only when the test synthesized input and its first failure came at or after that event; a run is queued only when every failing test is such a test.
- When an escalation's commit failed after the ledger line was appended, the main checkout's ledger stayed dirty and every later catch-up stopped at its clean-tree check; the uncommitted line also counted as recorded. `catch-up` now settles the ledger under its lock first (`mg_ledger_settle`), and an escalation counts only once committed.
