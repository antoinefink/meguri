### A1. The remembered status follows meta-status.md M6.1

- Before: U106's Approach said the online result "is cached in memory for 300 s and invalidated by any ChangeSet that moves `mod`, by a login or server change, and after every sync".
- Why it changed: `specs/sync/meta-status.md` M6.1 gives another lifecycle, and the code follows the spec. Its 299/300 s limit and the outcomes that syncs store come from the oracle (`sync/meta/status`). The differences:
  - A change that moves `mod` past `ls` needs no invalidation: M6 step 1 answers "local changes pending" offline before the remembered answer is read, and the next sync replaces it.
  - A server or account change: the answer serves only the base and host key it came with, so another base or key asks again and replaces it. A new login to the same account (the official server issues the same key) keeps it.
  - A sync: a completed sync job replaces the answer with its own outcome ("no changes" after a one-way download, which the oracle shows without a request). A failed or cancelled job leaves it.
- Now: the Approach bullet describes M6.1's lifecycle and points at the spec, so U113 and U151 get one instruction.
- Reversing A1 means a spec change to M6.1 by a spec writer, then `StatusMemory` (`core/crates/meguri-sync/src/status.rs`) and its tests.
