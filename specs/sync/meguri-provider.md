## MP1. Provider, account and collection are separate

There are two services: **iCloud Sync** and **Meguri Sync**. Local-only use remains supported without either account. One provider can own synchronization of the installed collection on this device. An account can be configured without owning the collection.

Store selected provider, pause/automatic settings and connection references in device-local state, outside the transferable collection. Import, export and bootstrap always include collection and media; these flows offer no media-scope or media-off choice. Store the active provider binding and handoff intent durably through existing guarded metadata seams. The binding names the provider, opaque account reference, collection/publication generation and admission revision. Never treat a UI picker value as admission authority. Present-but-invalid metadata blocks network work; absence alone permits migration defaults.

An upgrade preserves the existing iCloud choice, pause state, binding, pending work and publication fence. Changed 2026-11-19 (MP6.2; decided 2026-11-19 (review F10)): "pause/automatic settings" above and "pause state" here are the Sync Automatically setting alone; an upgrade turns a stored pause into Sync Automatically off (`sync/policy#P25.2`). Devices with no established choice remain local-only. Never infer an account or upload permission from collection stamps. A backup restore, package import, collection replacement or account change invalidates incompatible provider admission before work resumes.

## MP2. Native Settings and credentials

Keep Account & Sync in its existing native Settings location. Its first section uses a standard SwiftUI Picker labelled “Sync Service”, offering iCloud Sync and Meguri Sync. A separate Stop Using action supplies local-only use. Selection opens setup or a switch preview; the displayed active service changes only when its handoff commits. Changed 2026-11-19 (MP6.1, MP6.3, MP6.4): the control is Service, with Off, Meguri Sync and iCloud; Off replaces Stop Using and Sign Out; a Sign In made to set the service up continues into setup.

Keep account, connection and status under the selected service, separate from Collection import/export. Meguri setup uses labelled Server Address, Username and SecureField Password controls, then Sign In. Sign In authenticates only. Test Connection, if offered, is beside the address and performs only its disclosed authentication/metadata check. Opening Settings, editing a field or merely selecting an unconfigured provider starts no Meguri request.

Reuse endpoint normalization; require HTTPS for the native Meguri provider. Plain HTTP remains only a job-owned synthetic test fixture exception, not a relaxation of the generic transport contract. No built-in real endpoint or credential. Do not follow login redirects or forward secrets to a new authority automatically. A changed redirect authority requires explicit connection review and new credentials; keep configured identity distinct from the accepted transport target.

Canonicalize own-server usernames by `servers/meguri-sync-web#W2`; preserve password bytes. Keep username and opaque hostkey in a **separate provider Keychain namespace**, device-only and nonsynchronizable. Do not adopt the hidden manual-transfer slot. Clear the password after the attempt. Endpoint edits invalidate credentials and redirects before another request. A locked/failed Keychain is an actionable storage error, never permission for a plaintext fallback. Persist only opaque account references in operation/history state. Login proves no stronger alias or account equivalence than the protocol returns.

Sign Out/Remove Connection stops admission, drains work and deletes local credentials before reporting completion. It keeps the collection, media, backups and unresolved-operation evidence. It deletes no server data and claims no server-side hostkey revocation; password/reset administration remains the existing browser workflow. No automatic fallback to iCloud follows authentication failure or removal.

Use native Forms, Sections, Buttons, sheets and destructive roles. Retain the existing toolbar/status location and keyboard ownership. Add no custom chrome or restyling. The status identifies the active service; account validity, collection exchange and media progress remain distinct. Use “Last exchange completed”, pending/held work and partial-media state, rather than claiming all devices match.

## MP3. Durable exclusive handoff

Switching is a local handoff, not a migration of remote stores and not a service-to-service bridge. Explain that other devices must choose the intended service themselves. Changes held only by the old remote service are not silently copied. Preserve both services' remote data.

1. Refuse handoff during an active review, editor commit, collection replacement or unsettled recovery/publication operation. The user can continue local review and retry later. Show pending collection/media work and any held changes before confirmation.
2. Record intent naming old binding, proposed service/account, current collection/publication identity and prior decisions. Block new work from both providers. Cancel and join old collection/media jobs and all admitted callbacks through their actual owner boundaries.
3. Preserve completed effects and pending state. For iCloud use its stop/isolation mechanism (`cloudkit-recovery#V16`) without purging tracking, conflict copies, remote epochs or publication fences. Require provider/generation guards on **every** later callback, batch, apply and media install, including old SDK callbacks.
4. Commit the old provider inactive and destination **setup required** in one recoverable metadata transition. Start no destination writer until old admission is closed and drain is proved. Failed durable publication leaves network admission closed; retain the journal for recovery.
5. On restart reconcile the intent before starting either provider. Resume a proven committed selection; otherwise stay stopped with an explicit recovery action. Never choose whichever credential or service responds first.

An upload that may have reached the server retains its existing global exclusion across pause, sign-out, provider changes and restart. Stopping a worker or forgetting a key does not settle remote acceptance. Connection removal may forget credentials but cannot release this exclusion. Local review can continue; a new network writer cannot.

Returning to either provider requires explicit reconnection and current collection-choice validation. Do not restore an old “clean” baseline after work under another service. Reuse iCloud V13–V15 choices and fences on return; never silently republish the Meguri version to an old iCloud epoch. Preserve existing iCloud encryption/key, account, container/environment, unknown-field and recovery protections.

Changed 2026-11-19 (MP6.4): one confirmation covers a switch or Off, and the destination's setup then runs with no separate connection step. Steps 1 to 5, the upload exclusion and the return rule above are unchanged.

## MP4. First connection and full replacement

For a new Meguri account binding, endpoint/account change, provider return, imported/replaced collection or lost baseline, require explicit bootstrap. **Do not run normal sync to discover whether unrelated collections can merge.** Equal stamps, zero cards and `meta.empty` do not prove an empty store or common lineage.

| Observed state | Required action |
|---|---|
| No local collection | Offer Download from Meguri Sync. Stage, validate and activate through existing lifecycle/replacement rules. There is no local file to back up. |
| Any local collection, including zero cards | Show “Use This Device's Collection…” and “Use Server Collection…” plus Cancel. Explain which collection is replaced and that media reconciliation is bidirectional. Neither destructive action is the default. |
| Remote facts unavailable, unsupported or corrupt | Show the typed failure. Keep local data and both providers stopped for setup; never assume remote absence. |
| A baseline is proved for this exact active binding and generation | Admit normal synchronization under MP5; a protocol full-sync requirement returns to the explicit choice. |

Reuse `sync/anki-transfers#M2–M5`, `sync/one-way#O4–O7` and `engine/collection-replace#R6` as the **safety mechanics**, without exposing the old Anki UI or inheriting its automatic-work prohibition for this new provider. Reuse only the narrow admission, drain, backup, replacement and media seams; add no general synchronization framework. Legacy collection-only allowances do not apply to these newly authorized flows.

For download, use owned staging and verified finalization, force the local safety backup before activation, then record intent, atomic replacement and actual resulting generation. Failed backup prevents activation. For upload, take the local safety backup, download and retain the server collection copy even for zero cards, refresh facts after that download's stamp changes, and require final destructive confirmation. Bind confirmation to actual preview/operation, account/endpoint, source generation and artifacts. Changed facts require a refreshed decision.

Changed 2026-11-19 (MP6.3; decided 2026-11-19 (review F10)): "require final destructive confirmation" holds for an upload that replaces a server collection holding user content, or one not proved to hold none (MP6.3 row 4), and for every upload after an endpoint or account change, an import, a restore or a lost baseline (MP6.3). An upload to a server proved to hold no user content, on a first binding, has no confirmation (MP6.3 row 3). The safety backup, the retained server copy, the refresh of facts and the binding of the operation are unchanged for both.

The protocol does not lock the interval between server copy and upload. Explicitly warn that another client's later edits can be replaced, and instruct the user to stop sync on other clients during replacement. Retained backup and fresh metadata are **not** conditional-write guarantees. Never auto-upload a full collection after a mismatch. If strict cross-client exclusion is required, that is a genuine missing server capability; do not invent a lease or silently claim this flow supplies it. Changed 2026-11-19 (MP6.3; decided 2026-11-19 (review F10)): the warning is shown in MP6.3 row 4's sheet; row 3 shows none, since nothing known is replaced.

Changed 2026-11-19 (MP6.3): the table's first two rows are replaced by MP6.3's table. A side proved to hold no user content is replaced with no question; two collections get one sheet, which is this section's final destructive confirmation.

Persist intent before dispatch and exact `OK` before local upload activation. A lost acknowledgement stays “Server acceptance unknown”; preserve candidate, backups and exclusion until existing evidence-based recovery settles it. Report remote acceptance separately from failed local activation. Never clear an iCloud publication fence because a Meguri operation succeeded.

## MP5. Routine sync, reviews and media

Changed 2026-11-19 (MP6.3; decided 2026-11-19 (review F10)), for the paragraph below: the disclosure of automatic synchronization is the text under the sign-in fields, and the sheet where one is shown; "Sign-in alone establishes no baseline" stands, and "transfers nothing" is replaced by MP6.3, where a Sign In made to set the service up continues into setup.

Only a completed collection-and-media bootstrap establishes the provider's ready binding. Its explicit confirmation discloses subsequent automatic synchronization of both. Persist completion against the actual binding and resulting generation, then enable Meguri automatic sync without another setup step. Until then, Sync Now continues the explicit setup/recovery flow and performs no speculative normal exchange. Sign-in alone establishes no baseline and transfers nothing.

After successful bootstrap, Sync Now uses the retained **normal** job through a new provider-specific core/FFI adapter. Meguri automatic sync is ON after that explicit consent. Coalesce flushed local changes and foreground/reachability events; review completion can request a round. Use existing background/quit budgets; do not promise continuous execution on iOS. Existing Pause behavior closes network admission for collection and media, keeps pending work and makes Sync Now unavailable while paused. Resume reopens the same valid binding; it does not require another media choice. Any later Automatic Sync setting retains existing semantics: off stops automatic scheduling, while Sync Now still includes media. Preserve iCloud's existing scheduling defaults and semantics.

Normal work retains `sync/hold-back` barriers, durable answer writes, latest-answer undo hold-back, staged incoming changes and conflict rules. No review answer waits for the network. No replacement runs during a review. Recheck generation, schema admission and provider authority before mutation/finish; a late structural change requires an explicit full-sync decision. Authentication failure stops that binding and asks for sign-in; failed/cancelled/lost-ack rounds retain pending work and do not claim convergence.

Media is required for every import, export and bootstrap. Bootstrap discloses reconciliation of both sides separately from the chosen collection direction, including possible replacements, deletions and retained unreferenced files (`anki-transfers#M5`). Use the retained media reconciler with its own admitted owner and fresh baseline epoch after a provider/account/collection change. Do not reuse CloudKit cursors, USNs, keys, tombstones, pending downloads or “clean” marks. Rebinding retains physical live files and scans them; it grants no consent by itself.

**Unsupported/excluded media:** preserve and explicitly report every file the reused media path cannot transfer, including empty files and files over its 100 MiB limit. These files cannot count as completed all-media bootstrap or enable automatic normal sync. File import/export must account for every promised media file from the actual source/package inventory; a syncable-only journal inventory is insufficient. Classify each promised file as transferred, pending or unsupported/excluded. Any pending or unsupported/excluded file prevents whole-operation completion. Keep an actionable media-blocked phase with Show Affected Files and Retry; local study remains available. Retry retains existing binding, artifact and resume guards and cannot clear the block merely by omitting a file. Never automatically delete or convert excluded files, weaken limits, or infer a new server capability.

Serialize provider collection rounds and media phases initially. Reuse existing media-job exclusion, exact-name/hash checks, trash-before-replace, bounded streams and durable batch acknowledgement. Report collection and media progress/failure separately. “Collection transferred; media incomplete” describes retained effects, not successful completion of a smaller scope. Local study remains available while media retries, showing missing media honestly. Bootstrap remains incomplete until media finishes; automatic normal work does not bypass its retained admission. Routine media pauses with the service and resumes pending work without changing the promised scope. Resume validates the same binding and artifacts; changed ownership requires a new setup decision.

Changed 2026-11-19 (MP6.2): Pause and Resume are removed. Sync Automatically, on unless the user turned it off, and Sync Now are the only controls of routine sync.

## MP6. One Service control, setup without a Connect step (2026-11-19)

Decided by Antoine on 2026-11-19 (`docs/design/decisions.md`: `settings.accountSync`, `sync.connect`, `sync.serviceSwitch`, `sync.status`; `docs/design/native-interface-contract.md` N15). Where MP2, MP4 and MP5 differ, this section wins; the lines marked "Changed 2026-11-19" point here. MP1, MP3's five steps, MP3's upload exclusion, MP4's safety mechanics and MP5's media rules are unchanged. The iCloud side of the same decisions is `sync/cloudkit-recovery#V27` and `sync/policy#P25`; the text is `sync/status-strings#T19`.

### MP6.1 The Service control

- One control labelled Service, with three values in this order: Off, Meguri Sync, iCloud. iCloud carries a Beta label. It replaces MP2's two-option picker and its separate Stop Using action.
- Off is local-only use (MP1). The control shows the service that owns synchronization of this device's collection, or the destination of a handoff once MP3 step 4 has committed it as setup required; never a value the user merely tapped.
- Choosing a value starts no Meguri request by itself. For Meguri Sync it shows the Server Address, Username and Password fields and Sign In (MP2); requests start at Sign In.

### MP6.2 Sync Automatically; no Pause

- Meguri Sync has no Pause and no Resume. The one device-local Sync Automatically setting of `sync/policy#P25.3` applies to whichever service is selected: on unless the user turned it off; off stops automatic scheduling, and Sync Now still runs a round with its media.
- A device whose Meguri Sync was paused when it updates gets Sync Automatically off (`sync/policy#P25.2`; decided 2026-11-19 (review F11): no hidden hold applies to Meguri Sync). Pending work is kept, nothing is scheduled automatically, and Sync Now runs a round for the same valid binding. The status shows Sync Automatically off, never Paused.
- **Connected** is `sync/policy#P25.3`'s term: Meguri Sync is selected and MP5's ready binding exists. Until then the Sync Automatically control is disabled and shows its stored value (decided 2026-11-19 (review F8)).
- Media is never a separate choice or scope (MP1, MP5; `sync/policy#P25.1`).

### MP6.3 Setup runs after sign-in

Choosing Meguri Sync and signing in is the consent to set it up. There is no further step between a successful Sign In and setup, and no collection choice unless both sides hold one.

- **Sign In.** While this device has no ready binding for the entered endpoint and account, a successful Sign In continues into preparation below. The text under the fields says so; it never says that signing in sends or changes nothing. A Sign In that only renews a refused sign-in for a binding whose baseline is proved continues routine sync and transfers nothing else.
- **Preparation**, with Cancel, changes nothing on either side: read the remote facts; when a local collection exists, download and retain the server collection copy, as MP4 already requires before an upload, and read the server's media facts.
- **No user content** is `sync/cloudkit-recovery#V27.1`'s test. The server side is proved empty only by the retained server copy passing that test and the server reporting no media file. `meta.empty`, equal stamps and zero cards prove nothing (MP4); remote facts that are unavailable, unsupported or corrupt prove nothing.

| 2 | a collection with no user content | any readable collection | the local safety backup, then download and activate (MP4); a failed backup prevents activation | none |

Row 3 reads the server facts again immediately before dispatch; any change from the retained copy stops the upload and returns to preparation.
- **A changed endpoint or account** (decided 2026-11-19 (review F3)). Row 3 applies only to a first binding. When this device's provider binding metadata (MP1) records another endpoint or another account than the one signed in to, an empty server is not enough to upload: the sheet of `sync/cloudkit-recovery#V27.4` is shown in its one-direction form (upload this device's collection, or Cancel), naming the server and account, before any upload.
- **After an import, a restore or a lost baseline** (decided 2026-11-19 (review F9)). On a device that has, or had, a Meguri Sync binding, a package import, a backup restore, a collection replacement or a baseline that cannot be proved always leads to row 4's sheet, whatever the two sides hold. Rows 2 and 3 are never taken there.
- **Precedence** (decided 2026-11-19 (re-review R2)). Where the two rules above both apply, the changed endpoint or account wins: the one-direction sheet. Otherwise an import, a restore or a baseline that cannot be proved gives row 4.
- **Row 3 and other clients.** MP4's warning stands: the protocol does not lock the interval between the last read of the server facts and the server's acceptance. Row 3 shows no warning first, because nothing known is replaced; an upload from another client inside that interval is replaced and is not in the retained copy. Row 4's sheet keeps the warning.
- **The sheet is MP4's final destructive confirmation.** Each button is bound to the preview shown, the account and endpoint, the source generation and the artifacts; changed facts reload the sheet and need a new choice. It shows both sides' counts and last change, this device's unsent work when the server collection is kept, the local safety backup and the retained server copy, MP4's other-clients warning when this device's collection is kept, and MP5's media reconciliation line. Neither button is the default.
- **Media.** Rows 2 and 3 complete with media as MP5 requires. The side they overwrite is proved to hold no media file, so the reconciliation can replace or delete nothing of the user's there; MP5's disclosure of replacements and deletions is shown in row 4's sheet, where it can apply.
- **Automatic sync is disclosed without a confirmation.** MP5 required the bootstrap's confirmation to say that automatic synchronization follows. Rows 1 to 3 have no confirmation, so the text under the sign-in fields says it, and the Sync Automatically switch shows the stored value. The sheet says it only while the setting reads on.
- **A protocol full-sync requirement** in routine sync returns to row 4's sheet through the status action; nothing is uploaded or downloaded in full automatically (MP4).
- **Cancel** during preparation or in the sheet, while no binding is ready, leaves the service Off as MP6.4 says. A failure keeps Meguri Sync selected and signed in, with its reason and Try Again.

### MP6.4 Off and switching

- **Off** asks once, then runs MP2's Sign Out/Remove Connection inside MP3's handoff to local-only: admission stops, work drains, this device's sign-in is deleted, and the collection, media, backups and unresolved-operation evidence stay. Nothing on the server is deleted. It replaces Sign Out and Stop Using Meguri Sync; there is no separate Sign Out.
- **Switching** to iCloud asks once, then runs MP3 and, when its step 4 has committed, iCloud's setup (`sync/cloudkit-recovery#V27.2`) with no further connection step. A switch to Meguri Sync shows the sign-in fields after its step 4.
- The one confirmation is MP3 step 1's: it shows the pending collection and media work and any held changes, and says what stays with the old service. A choice made from Off has no old service and no confirmation (`sync/status-strings#T18.1`).
- MP3 step 1's refusals stand: during a review, an editor commit, a collection replacement or an unsettled recovery or publication operation the control does not change, and says why.
- An upload that may have reached the server keeps its exclusion through Off and a switch (MP3).

### MP6.5 When a change fails halfway

- **Handoff recovery** (MP3 step 5) is shown as needs you: one sentence and the action Keep on This Device Only…, which after its confirmation leaves the service Off. From Off the user chooses a service again.
- **A blocked provider phase** (MP1: present but invalid metadata) is shown as needs you with the action Copy Debug Info. The core has no command that repairs or discards that metadata, and this section adds none: discarding it could release an upload exclusion (MP3).
- **What still works while blocked** (decided 2026-11-19 (review F5)). The Service control stays enabled: the user can choose the other service or Off, through MP6.4's one confirmation; an upload exclusion that is held survives that change (MP3). Study, backups, import and export keep working, since none of them needs a provider. The documented way out is Export Collection (`package/file-export`), which saves the whole collection with its media whatever the provider's state; the needs-you sentence names it (`sync/status-strings#T19.5`). Copy Debug Info stays.
- Changed 2026-11-20 (first-run fix). **Setup is not a blocked phase.** MP4's setup transfer keeps network admission closed from its preview until its media finishes. That closure is the setup's own: while Meguri Sync is selected, no handoff is recorded and that transfer is active, the provider phase is setup required and the status shows the setup's stage. Admission stays closed; no other network work starts. Every other closure, and metadata that cannot be read or published (MP1), is the blocked phase.
- Changed 2026-11-20 (first-run fix). **A blocked phase stops running work.** When the phase becomes blocked while the setup's media step or a round runs, that work is stopped, keeping its pending work as a failed or cancelled round does (MP5); a collection step is left to its replacement's exclusive phase (MP4). Preparation, which changes nothing on either side (MP6.3), is left to end; no confirmation or later step starts while the phase is blocked. The status then shows the blocked sentence alone: no media count and no progress beside it.
- Changed 2026-11-20 (first-run fix). **One progress indicator.** While Meguri work runs, the Account row shows one progress bar. During the media step its value is this run's files transferred over those files and the files left; it is indeterminate until the first count, and it never follows one request's bytes.
- Changed 2026-11-20 (first-run fix). **Copy Debug Info says why.** The copied text starts with a short summary (app and system versions, the selected service, the provider phase, and for a blocked phase its source and the failure's kind; Meguri's connection, setup stage and routine; the status keys; event counts by component and outcome, and the failures), then the safe export pretty-printed with sorted keys, its timeline last. Every added value is a name from a fixed list: the source is `metadataUnreadable`, `admissionClosed`, or the call that failed (`migration`, `settingsWrite`, `publicationRetry`, `authorityRefresh`, `adoptionRestore`); the kind is `busy`, `unavailable`, `cancelled`, `unsupported`, `invalidArgument`, `internalFailure` or `other`. No error text, address, account or content.

### MP6.7 Troubleshooting

Replace This Device's Collection… and Replace the Meguri Sync Collection… are MP4's download and upload for a signed-in binding. Each opens MP4's preview and its one destructive confirmation, unchanged, with the retained copies and the other-clients warning.

### MP6.8 For the owner

- **Sign In now starts setup** (MP6.3). MP2 said "Sign In authenticates only", so that signing in could never move data. "No separate Connect step" removes the step that came after it. What is kept: no request before Sign In, the text under the fields says that setup follows, and nothing that holds user content is replaced without the sheet.
- **Emptiness of the server needs a download** (MP6.3). MP4 forbids trusting `meta.empty` or zero cards, so preparation downloads the server collection before it can decide that there is no question. On a large server collection the question appears after that download.
- **Row 3's unlocked interval** (MP6.3) is MP4's known gap, now without a warning shown first. Closing it needs a server capability that does not exist.
- **Cancel removes the sign-in** (MP6.3, MP6.4), because Off always does. The reading not taken keeps the sign-in after a cancelled sheet, so that the user need not type the password again; it would leave a signed-in account behind an Off control.

### MP6.9 Settling an unknown acceptance

Decided 2026-11-19 (review F4). MP4 keeps "Server acceptance unknown" until evidence settles it; this is the step that gets the evidence.

- **The step**: read the server's facts again and compare them with the retained candidate (the collection this device sent) and with the retained server copy or the last proved baseline. It starts no upload and changes nothing on either side.
- **When**: automatically at the start of the next round or setup attempt, before anything else of it, and when the user chooses Try Again in the status. While the state lasts, the upload exclusion of MP3 stands and no writer starts.
- **Accepted** (the server's facts are the candidate's): the exact acceptance is recorded, local upload activation completes, the exclusion is released, and setup or routine sync goes on as normal.
- **Not accepted** (the server's facts are still those of the retained copy or baseline): nothing reached the server. For a routine round the pending changes stay pending and the next round sends them. For a setup upload the confirmed upload is offered again as Try Again under the same bound decision, as MP4 allows while the facts are unchanged.
- **Neither** (the server holds something else): another client changed it. MP4's "changed facts require a refreshed decision" applies: the keep-collection sheet (MP6.3 row 4) is shown, and nothing is uploaded before its answer.
- **Not readable** (offline, a server error): the state stays unknown and waiting; the step runs again at the next attempt or Try Again.
- Changed 2026-11-20 (as built and reviewed). **Accepted, and this device changed since the upload.** Local activation completes by itself only while this device's collection is still the one the upload sent, tested inside the replacement's exclusive phase. ## MP7. Note type structure saves (2026-11-20, round 9 option 3C)

New 2026-11-20. A schema-classified local save of note types (`notetypes/schema-changes` G2: `fields_changed`, `sort_field_changed`, `templates_changed`, `notetype_removed`, `notetype_restored`, `notes_notetype_changed`) while Meguri Sync is the service and its binding is ready (MP5) runs as one job, after the user accepted `notetypes/draft-save` D4's sheet, Change Note Type's sheet, or the question of Restore to Default or Delete Note Type, each with D4's sync paragraph (`notetypes/draft-save` D3). That sheet or question is the final destructive confirmation of MP4 for this upload; no second question is asked. Other structural edits (`preset_removed` from Deck Options) are not covered: their next round meets the full-sync requirement and MP6.3's choice, as today.

1. **Admission.** The job takes the provider's exclusive handoff (MP3) for its whole length, so no automatic round starts in between; a review in progress does not stop it (answers stay local and are uploaded with the collection).
2. **Normal round first.** When the reachability check made as the sheet opened found the server unreachable (`notetypes/draft-save` D4's unreachable case), this step and step 4 are skipped: the save runs (step 3) and the upload is left pending (step 5). Otherwise one MP5 normal round. When it reports that the server requires a full sync already, the job stops before saving and shows MP6.3's collection choice: the draft stays (`notetypes/draft-save` D6 step 1). When the round applies an incoming change to the note type being saved, the save meets `Stale`. A failed, cancelled or lost-acknowledgement round stops the job with nothing saved.
3. **Save.** For Change Note Type and a note type save, the loss counts are read again after the round (`notetypes/change-notetype` M5 and M6, `notetypes/draft-save` D2); when they differ from the ones the user accepted, the job stops before writing and shows the sheet again with the new counts. The same holds for Delete Note Type (its notes and cards) and Restore to Default (its losses). Each op also receives the counts the user confirmed as a precondition (`notetypes/draft-save` D8's rule), so a change between this read and the commit returns `LossesChanged`. Then the local op with its safety backup (`package/backup-triggers#T6.1`), as when no service is set.
4. **Upload.** MP4's upload with its safety mechanics: the local safety backup is the one of step 3 when T6.1's coalescing covers it, otherwise a new one; the server collection is downloaded and retained first (MP4); facts are refreshed, and when they differ from the binding's last proved baseline (the one step 2's round recorded; after an offline save, whose round was skipped, the one the last completed bootstrap or round recorded, as step 5 says), because another client synced in between, the job stops before uploading and shows MP6.3's collection choice, since the consent was given for other facts (MP4: changed facts require a refreshed decision); the save stays and the pending state of step 5 is recorded; otherwise the upload, which records its stamps exactly as MP4's existing upload does (this section adds no stamp rule). Media is reconciled as MP5 requires before the binding counts as clean.
5. **After a failed or impossible upload** (no network, the server down, a lost acknowledgement): the save stays committed. The provider records "structure upload pending" for this binding and generation. While it is recorded it replaces MP6.3's collection choice for this binding: the sync status shows the needs-you line `sync.needsYou.meguri.structureUpload`, "Upload this collection to finish your note type changes.", with the action `sync.needsYou.meguri.action.upload`, "Upload…". Upload… runs step 1's admission, reads the server's facts (no normal round, since local `scm > ls` would only report the full-sync requirement), and runs step 4, with no further question. The facts are compared with the binding's last proved baseline (MP4, MP6.9): the record a completed bootstrap (MP5) or a completed normal round writes for this binding and generation. When the facts differ from it, or no baseline is recorded, Upload… instead shows MP6.3's choice, since this device cannot show it holds everything the server has. A lost acknowledgement stays MP6.9's acceptance unknown first. Automatic rounds do not run while the upload is pending. These two keys and texts are added to `sync/status-strings` T19.4's needs-you rows by the implementing unit (U269).
6. **Undo.** A completed upload clears the collection's undo and redo history (`notetypes/draft-save` D7). Undoing the save before the upload withdraws the pending state when `scm <= ls` again.

Without a ready binding (Meguri Sync chosen but not set up), or with iCloud or Off, the save runs alone (`notetypes/draft-save` D5); with Meguri Sync not set up, the next setup handles the collection as MP6.3 does.
