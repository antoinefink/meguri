# Meguri Sync publication and recovery

Spec: sync/server-lifecycle
Requirements: Meguri Sync U2; R9, R12–R18, R24–R30; F4, F5; AE3, AE6–AE8; KTD4, KTD7–KTD13, KTD16
Anki: 26.09.3
Scenarios: conformance/scenarios/sync/server/ (planned; contract conformance/meguri-sync-server#C6,C8)

## L1. Ownership and durable state

Fact classes B/M/P are `server-transport#T1`. All publication, storage layout and operational recovery rules in this file are **M**, except explicitly labeled B/P statements. They are independently chosen service policy, not descriptions of a reference server's internal design.

One process holds a stable exclusive data-root lock for initialization, serving/startup, stopped backup, restore or local recovery. Its lock identity is outside any replaceable restore contents; replacing a lock pathname while another process owns it must not create a second owner. Refuse a second process. `serve` refuses missing or inconsistent expected initialization state; it never silently creates a new administrator or collection root.

`accounts.sqlite` contains account identity and state, credential/hash revisions, sessions, hostkeys, capabilities and per-account media metadata/USNs. Each opaque account ID selects its collection generations and private blob storage. Remote usernames, filenames and archive members never select storage paths. IDs are generated by the service and cannot alias another account or escape the data root. One ready account owns exactly one current collection generation. Supported collection files contain none of this metadata.

All writable SQLite connections use WAL and `synchronous=FULL`, a bounded busy wait (default five seconds), and the collection collation where needed; shared account connections enable foreign keys. Use bounded connection capacity (default eight shared metadata connections and sixteen collection connections), with explicit unavailable/busy results when exhausted. These are admission limits, not cross-database transactions. Temporary storage has an operator-set positive byte budget (default 2 GiB shared across in-flight requests), reserved before writes and released on cleanup; exhausting it rejects before publication. Startup and steady state must not delete anything merely because a remote input resembles a staging filename.

## L2. Normal rounds and method admission

**B:** A normal round runs `start`, zero or more `applyGraves`, `applyChanges`, server `chunk` requests through done, client `applyChunk` requests through done, `sanityCheck2`, `finish`; state binding and abort are `sync/transport#T4`, `normal-sync#N3,N10`. **P:** C5 measures exact current-server admission, repeated-phase behavior, wrong session, same-key restart, error retirement and full-transfer overlap. Strict order beyond observed client behavior is not a new reference fact.

**M:** An admitted `start` replaces an unfinished normal round on that account, rolling it back first, including a start with the same session key. A retained dedicated SQLite transaction owns uncommitted state until finish. Its identity includes account ID, credential generation, current collection generation and nonempty native session key. No process-wide collection mutex is held across network waits. Round operations recheck all identity components before mutations. A request with no live matching round returns 409; it never attaches to a new transaction silently.

Use the normal order above as the required client lane. Reject an out-of-phase mutator with 409 and retire its matching round; a request on a different session cannot retire the legitimate round. `meta`, native authentication and media are independent of a normal round. `abort` with the owning session rolls back and returns null; no round or a different session produces 409 without cancelling another owner's round. A decoding/storage/merge failure during a matching round rolls it back; failed authentication alone cannot mutate another account's state. A round expires after 120 seconds idle, measured monotonically since its last completed round request. Expiry, process restart and shutdown roll back. There is no transaction resurrection from a session string.

Only a successful sanity check allows finish. Finish rechecks ownership under L4, durably commits collection state before returning T, then retires the round. Once committed, a failed/lost response does not roll it back. A stale connection cannot finish into a retired collection generation.

## L3. Full collection generations

Stream a full upload into a private same-filesystem staging generation. No active-generation overwrite occurs while bytes arrive. Bound decompression and disk use; verify SQLite integrity, supported schema, required file structure and codec readability through hardened connections before publication. Disable trusted schema behavior, extension loading and execution of untrusted schema programs; never run a supplied trigger as part of validation. Refuse unsupported/corrupt/unsafe input before activation, preserving the prior file.

Preparation makes the candidate file and its directory durable. Under L4's account barrier, recheck authority, close/roll back the unfinished normal round and close all old writable handles, then atomically switch a small current-generation manifest. Make the manifest and containing directory durable before `OK`. Retain the prior generation until manifest durability and reader release. A crash before publication resolves to the old complete generation; after durable publication it resolves to the new complete one. Never acknowledge an in-between state. An I/O error at the switch is resolved by reopening durable state; do not silently continue serving a guessed generation.

A full download first resolves any unfinished normal round under the same barrier, applies the verified required download stamps, commits, and creates/pins a self-contained committed snapshot. It can then stream outside the barrier. A replacement after that point cannot alter its bytes. **B:** download changes mod/USN (`one-way#O7.4`); **P:** C4/C6 seals exact stamps and current full-transfer admission behavior before compatibility credit. A lost download response may leave advanced stamps but must leave a valid collection. Upload and download never replace media.

At startup, recover SQLite transactions and resolve the durable current manifest first. Remove only unreferenced service-owned staging generations and blobs while holding exclusive offline ownership. Current/pinned generations and uncertain publications are never treated as disposable on filename pattern alone. Contradictory or damaged manifests stop serving with a diagnostic; no automatic empty replacement is allowed.

## L4. Revocation and lock order

Streaming, archive decoding, hashing, slow password verification and bulk validation occur outside account publication barriers and shared metadata write transactions. An operation then acquires its account barrier before short collection/media state locks and before the shared metadata writer. Never wait for a barrier or client/network activity while owning the shared writer. A retained round is coordinator-owned state, not a held network-duration mutex. Separate collection and media state permit independent work until their short publication points.

Password change/reset, local recovery and disable use the target account barrier. Revalidate the actor, its original session/generation/administrator authority, target state and capability authority within the committing transaction. Do not acquire a second account barrier while holding the shared writer. Close the target's unfinished normal round rather than waiting for its next request. Increment credential generation, invalidate its applicable credentials, and commit before acknowledgement. Reject disabling the sole enabled ready administrator.

| Publication phase at revocation | Required result |
|---|---|
| Password verification, collection/media decode, stream or validation outside barrier | Recheck fails after revocation; candidate remains unpublished and is cleaned up |
| Waiting to enter barrier | Revocation may commit first; old authority then cannot publish |
| Publication already owns barrier | Publication can commit first; revocation waits, then revokes; its reply never precedes that older publication |
| Normal round open across network | Roll back/retire it before revocation acknowledges |
| Committed response lost/in flight | Committed state stays valid; a reply is no new authority; future requests fail old credentials |
| Pinned download already authorized/committed | Bytes already released cannot be recalled; no later request or stamp mutation is authorized by the old credentials |

After revocation acknowledges, old-generation requests cannot publish collection/media, issue credentials, redeem a capability or commit administration. A password proof computed against an older hash revision may never issue credentials for a newer generation. Fault coverage must exercise both linearization orders, rather than assume any request already started is valid forever.

## L5. Backup and restore admission

Backup requires the service stopped and exclusive L1 ownership. Recover/checkpoint and close every database, retaining required journal state if any remains. Snapshot account metadata, current collection generations, media metadata and all referenced durable blobs together. Record a manifest of relative owned paths, sizes and SHA-256 hashes and the format version; include no secret values in ordinary logs. Verify the manifest before accepting the backup as complete. A backup interrupted before completion is not a usable backup.

Restore requires an empty target and exclusive stable lock ownership. Reject absolute paths, traversal, links, duplicate paths, missing/hash-mismatched files, unsupported versions and references to absent blobs/generations before admitting the restored state. Partial failure leaves serving closed. Verify all database integrity and metadata references. Invalidate restored sessions, hostkeys, outstanding setup/invite/reset bearer capabilities and other redeemable links; they cannot regain authority after rollback. Keep collection state and media cursor history intact as snapshot data. Retain the restored password hashes and enabled states for explicit operator review; do not claim post-backup revocations survived rollback.

Persist a restore-admission closure before any service can expose restored accounts. A local administrator recovery operation supplies new credentials and records the operator's review of restored identities, enabled states and password state. Normal serve remains closed until that local process explicitly opens admission; restart cannot bypass the closure. No anonymous remote endpoint can open it. Local recovery uses the same generation/revocation/data-preservation guarantees as remote reset, without requiring a usable old browser session. No data deletion or automatic empty account is part of recovery.

## L6. Client recovery and claim limits

Every participating client, including a delayed reconnecting one, needs renewed credentials and an explicit operator/client decision to perform a full collection transfer with the restored authoritative copy, then the verified media reset/rescan procedure. Full-transfer direction must preserve the chosen authoritative state; it is never guessed from zero cards. Verify content, review history, scheduling and media hashes afterwards before marking that client recovered. Keep a recovery checklist per client outside transferable collections. Opening service admission and completing client recovery are separate outcomes.

**B:** `meta-status#M3` gives equal-mod precedence over scm; `media-sync#Y11` describes cursor/count limitations. **M:** A changed scm, cursor ahead/behind/equal, matching USNs, equal file counts or HTTP success cannot prove restore reconciliation. No invented wire signal, automatic transparent restore claim, online backup scheduler or external authentication journal is introduced.

**P:** C8 must seal the exact Desktop 26.09.4 explicit full-transfer/media-reset procedure, then the exact AnkiMobile 26.10 procedure in its device lane. Test equal mod with different scm, cursor reused or overtaken after restore, equal counts with different bytes, offline local edits and delayed reconnect with revoked credentials. If a supported client procedure cannot be verified, the affected restore acceptance remains incomplete even if service storage recovery passes.
