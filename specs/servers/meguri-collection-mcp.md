Spec: servers/meguri-collection-mcp

## M1. Endpoint and ownership

The configured HTTPS origin serves one Streamable HTTP endpoint at `/mcp`. Its canonical resource URI is the exact public origin followed by `/mcp`. Each request acts on the current synced collection of the account that authorized its grant. MCP never selects an account, device, or collection from the request body. Use separate bearer credentials for MCP, the existing browser session for consent and grant management, and native credentials for sync.

Support the stateless `2026-07-28` lifecycle on POST, including `server/discover`, and the `2025-11-25` initialize lifecycle and its initialized notification on the same endpoint. Follow each negotiated revision's version, headers, status and JSON-RPC rules. Advertise tools only and return ordinary request results directly. GET returns 405. Reject a present invalid or different `Origin` with 403. The approved HTTPS origin is the only accepted browser origin. Record the revision needed by each real hosted client and verify any additional revision before admitting it. [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) [Prior transport revision](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

Use 12 global nonqueued MCP transport admission slots, acquired before reading the body and retained through dispatch and response ownership. Preserve the 1 MiB body cap and ten-second body-read deadline, capacity overflow's HTTP 503 with `Retry-After: 1`, cancellation ownership and graceful draining. Transport admission bounds all MCP queue waiters; do not raise global metadata or native sync capacity.

## M3. Consent, tokens, and revocation

Continue the validated request through the existing browser sign-in using the opaque, expiring pending request in [W10](meguri-sync-web.md#w10-mcp-consent-and-connections). A pending request expires after ten minutes. Only an authenticated same-origin approval can issue a code. Bind the code to the account and its credential generation, validated client, exact redirect, canonical resource, approved scopes and PKCE challenge. Denial issues no code or grant. Consent replay cannot create another code or grant. Each code lasts at most 60 seconds and can be exchanged once, including concurrent attempts.

`POST /oauth/token` accepts form-encoded OAuth requests for authorization code exchange and refresh rotation. It requires the exact bound resource. Code exchange requires the public client ID. On refresh, use the client bound to the credential and reject a supplied client ID that differs. Code exchange requires a matching S256 verifier. If a `redirect_uri` is supplied for OAuth 2.0 compatibility, it must exactly match the bound redirect. OAuth 2.1 may omit it. Consume the code and establish an independent grant with access and refresh credentials in one metadata transaction. The response contains a Bearer access token, `expires_in`, a refresh token and the granted scope. An access token lasts at most 15 minutes. A grant's rotating refresh family expires 30 days after code exchange. A valid refresh consumes its old credential and returns its single replacement in the same transaction. It cannot expand the grant or change its account, client or resource. A replay of a consumed refresh credential from that same client and resource invalidates its family. An expired, revoked or consumed credential fails with the standard OAuth error. [RFC 6749](https://www.rfc-editor.org/rfc/rfc6749) [OAuth security guidance](https://www.rfc-editor.org/rfc/rfc9700)

Store only digests of high-entropy opaque codes and token secrets in account metadata. Keep the grant, credential generation, scope, resource, client binding, lifetimes and replay state outside the transferable collection. Serve private authorization pages, redirects and token responses with no caching or Referrer disclosure. Keep codes, tokens, pending handles, client state, note contents, and proposed edits out of application logs, proxy request logs, and error text.

At every tool call resolve the account from the bearer and verify its scope, resource, grant, expiration, and credential generation. Recheck that exact grant at the account's collection admission boundary and immediately before a collection write commits. Check the original authority and publication before releasing read results. An ended grant cannot begin new work. Revoke a selected grant through W10, including outstanding access and refresh credentials. Password change/reset, disable, deletion and recovery or restore invalidate affected older grants and outstanding codes under the same account authority rules as [W2, W6](meguri-sync-web.md). Browser logout revokes the browser session. An ordinary full collection replacement for the same account retains its connections. Any request already pinned to the replaced publication and all revision/page handles for that publication become stale.

Browser grant revocation and invalidation on replay of a valid authorization code or refresh token take the same per-account publication barrier as a collection write. Keep a bounded consumed-code correlation to the issued grant. A still-valid code replay with the original client, verifier and resource, and an exact redirect if supplied, returns `invalid_grant` and revokes the grant issued from that code. A replay with mismatched bindings leaves the grant active. Follow `sync/server-lifecycle#L4`. Resolve the target first, release any metadata lock, acquire the account barrier, and then take the metadata writer. Under that order, revalidate the original authority or replay binding and commit the invalidation. Retain the barrier from the collection write's final authority check through its durable commit. If invalidation obtains the barrier first, the write fails its authority check and changes nothing. If the write commits first, its changes stay committed and invalidation applies to subsequent work.

## M4. Tool shapes and results

Expose the four collection tools below, the upload preparation tool in M8, and the download tool in M9. Inputs are JSON objects with the stated members. IDs are positive decimal strings in signed 64-bit range, preserving IDs past the exact JSON-number limit. Names, note contents and error details are data. Do not render HTML, fetch links or resources, or execute strings found in a collection. Attach read-only annotations to the read tools. Write tools identify their change in their descriptions. Publish per-tool OAuth `securitySchemes` with type `oauth2` and that tool's required scopes. Mirror the descriptor in `_meta.securitySchemes` for older clients. A note result contains `note_id`, `note_type_id`, `fields`, `tags` and `revision`. Tool fields are maps from exact note type field names to strings. Tag arrays contain tag names. Each deck result has `deck_id` and `name` and indicates whether it is `filtered`; each note type result has `note_type_id`, `name` and `field_names` in stored field order. Use the same JSON data in structured content and text for client compatibility. Reject unexpected and duplicate members and enforce request/result byte and item limits before unbounded work. Preserve complete note field values and field lists within those limits. Return a size-limit error when one requested result cannot fit.

An exact ID search returning no row returns an empty list. An edit to a missing note reports `not_found`. Return `conflict` for a changed note, layout or publication. Other collection outcomes include `invalid_input`, `result_too_large`, `unsupported_collection` and `busy`. Mark them as tool errors. A `busy` result includes `retryable: true` and `retry_after_ms: 1000`. For a write, preserve the message "The collection is busy. The write did not commit. Retry after one second." and `write_committed: false`. For a read, use "The collection is busy. Try again after one second." and omit `write_committed`. Select this behavior from the parsed call's actual Read or Write access, never the route or the client's granted permissions. Use JSON-RPC errors for invalid protocol operations. Keep OAuth and transport errors at their HTTP boundary.

## M5. Bounded reads and exact revisions

`note_id` alone performs a primary-key lookup with keyed reads for its note type and field layout. It rejects other filters and pagination parameters. A paged search requires at least one other filter, combines filters with AND, and returns distinct notes ordered by increasing ID. Text is a case-insensitive literal substring over stored field values with no query operators or regular expressions. A tag matches the whole canonical tag case-insensitively. A deck matches a card's home deck by exact ID. Query filters, input lengths, examined candidates and result bytes have fixed limits. The default page limit is 20 records and the maximum is 50. A page may return fewer matches, including zero, and a continuation cursor if its examination budget ended first. Every paged search driver returns `scan_incomplete: true` when a work limit ends a page before filling its requested size and more candidates remain; this always implies `next_cursor`. Clients continue from `next_cursor` as `cursor` with the same filters and limit to find remaining matches. Omit `scan_incomplete` when false. An empty ordinary result means exhausted. A full requested page or a stop because an already confirmed next match did not fit the result-byte budget keeps normal continuation behavior without the flag, including the existing full-page cursor behavior. The cursor advances past all examined candidates that could be returned or ruled out within the result budget. It never silently skips a match omitted for fit.

For a search without a deck filter and without a usable candidate posting for its text-only, tag-only or combined filters, stream notes in increasing ID strictly after the authenticated position using one bounded SELECT/cursor in the authoritative transaction. Select ID, raw logical record lengths and text/tags guarded by byte limits before text materialization or copying. Preserve the 128 KiB text-plus-tag record cap and 512 KiB raw logical object cap, including bytes after embedded NULs. Filter per-field case-insensitive literal regex text and UniCase whole tags with AND before loading full records, hashing or reading note types; actual matches use the existing stored-note, note-type and result shaping. Stop at 150,000 examined candidates, 128 MiB examined text-plus-tag bytes, or a cooperative 500 ms scan deadline checked after each bounded row, or earlier for requested matches/result fit. The deadline covers this scan, separately from the publication-barrier wait. Always allow one bounded row to be examined so a resumable page progresses. Retain one candidate lookahead to distinguish exhausted from incomplete; keep the cursor before unexamined or non-fitting matches. Keep authority rechecks, transaction fences, lock release and cursor shape/lifetime. Preserve existing deck-path limits, cache capacities, exact ID lookup, schema, connections and dependencies.

For a paged search with `deck_id`, select deck candidates before applying text or tag filters, including when both are present. A card's home deck is its nonzero saved original deck (`odid`), otherwise its ordinary deck (`did`). The cold/fallback scoped selector uses two indexed card branches: `did` equal to the requested deck with zero `odid`, and nonzero `odid` equal to the requested deck. Join surviving notes, deduplicate and order their IDs strictly after the authenticated note-ID position, and retain at most 200 candidates plus one lookahead. Multiple matching cards and cards in other decks never duplicate a note; orphan cards do not consume candidate slots. Temporarily filtered cards match their home deck only. Do not expand subdecks. Keep structural/index refusal, note reads, result shaping, literal text and canonical tag matching, and existing candidate, byte and result caps. Validate note/card record details, including scheduling values, only after establishing requested deck membership in cold, warm and global fallback searches. For a selected matching note, keep the full existing sibling validation and read, including siblings in other decks. An empty deck exhausts immediately when scoped selection succeeds. A combined-filter page may be empty and resumable. Its continuation reflects remaining scoped candidates, including a candidate omitted for byte fit, and uses the existing authenticated after-note-ID format and query shape.

Prefer checked native `ix_cards_sched` and `idx_cards_odid` indexes when suitable; imported index names or definitions do not establish a work bound. A result LIMIT alone cannot bound a scan, deduplication or sort. Bound this candidate statement with rusqlite's safe `hooks` progress handler on the request-owned connection: a 100,000 SQLite VM-instruction budget, checked every 1,000 instructions. Install the callback before opening the single authoritative search transaction; if installation fails, use the existing bounded global path. Arm its shared budget only for the bounded candidate statement and disarm it on every exit before ordinary reads, fallback or commit; the callback may remain dormant until the request-owned connection drops. Discard partial candidates on local budget interruption and use the existing global note-ID keyset path from the original cursor. Unavailable or unsuitable indexes may skip the optimization and use that same path. When the existing sibling index `ix_cards_nid` qualifies, global fallback first probes home-deck membership by note ID through that index, materializing only computed home/equality (`CASE` nonzero `odid`, otherwise `did`). Inspect at most the existing 2,048 siblings plus one lookahead; stop on a match and retain full sibling validation for that note. If the bound prevents safely establishing membership, return `result_too_large`. Do not prevalidate scheduling for unrelated notes or introduce an unbounded scan. If sibling-index qualification fails, retain the existing global path: a remaining global note returns the authoritative missing/wrong/partial-index error, while an exhausted global search stays empty. Preserve structural, corruption and unsupported-collection errors within this validation scope; do not treat those errors as local budget interruption. This is a candidate optimization only: no private schema writes, index creation, rebuild, unsafe raw SQLite pointers, new assets or network activity. Exact ID lookup, native reads and writes, package identity, dependency versions, OAuth, and catalog ordering and result caps remain unchanged.

The catalog reads existing supported decks and note types in kind order, decks first, then by increasing ID within kind. It retains the same result limits. Search and catalog cursors share the following epoch/generation binding. Authenticate page cursors or keep them server-owned. Bind them to the account, validated OAuth data epoch and credential generation, published collection generation, tool and query shape. Encode epoch/generation in the existing publication context without changing the outer token schema. Ordinary content stamps and candidate drivers do not bind cursor lifetime. Use a key position, not a growing SQL offset. Each page uses committed state. Changes made between pages can affect what a later page observes. Abort old-publication cursors with `conflict`. Use a bounded read transaction and close it before returning. No collection copy or independent search index build occurs on a request.

A service may retain two disposable derived candidate snapshots and reserve one asynchronous blocking build, with no pending-key queue. Match the exact account, OAuth data epoch, selected publication path and committed `(col.usn,col.mod)` inside the authoritative page transaction. Use complete deck membership first for every deck-bearing combination. Otherwise use an available canonical UniCase tag posting or a literal-text gram posting using regex simple-fold equivalence. All supplied predicates, keyed size-checked reads, byte budgets and authority rechecks remain authoritative. Use the existing note-ID position and exact next-candidate check, including a candidate that did not fit. Capacity, deadline, setup and scan failures fall back to existing search. Epoch and publication matching fence resets, replacements and obsolete completions.

## M6. Note creation and patching

Resolve creation's deck and note type in the live transaction and require an existing usable normal deck. Validate the exact field names against that note type. Unspecified creation fields start empty. Save fields and tags using the collection's creation rules. Use [C7](../sync/server-collection.md#c7-standalone-mcp-note-writes) for canonical persisted rows and stamp rules. Reject ambiguous add/remove overlap. Preserve GUID, identity, note type, flags, data and existing cards. Validate the complete patch before effects. A stale revision conflicts even for a no-op. A valid patch with no effective change returns the same revision and writes nothing.

## M8. Attach media and PDFs to notes

Both note write tools optionally accept `files` and `file_fields`, or `uploads`. The `files` array follows [ChatGPT file inputs](https://developers.openai.com/plugins/reference#define-file-inputs). Each object requires `download_url` and `file_id` and may include `file_name` and `mime_type`. The same-length `file_fields` array gives the exact note type field name for each file. Advertise `files` with `_meta["openai/fileParams"]` for ChatGPT discovery. `uploads` is an array of `{upload_id, field}` populated by the automatic binary transfer below. Accept both sources in one call, in that order. Require one to four attachments when attachment arguments are supplied, with at most 8 MiB per file and 16 MiB total. Cap URLs at 4096 bytes and file IDs at 256 bytes. Existing collection request and result limits remain in force. `edit_note` accepts an attachment-only patch with a valid note revision. A supplied replacement field is the base text for appending. Otherwise use existing text on edit or an empty field on create. Append each new reference in order, separated from prior content by `<br>` when needed. Skip appending an exact reference already in that field. Enforce normal field limits on the complete result.

Use `files` with `file_fields` first where supported. Only a write-authorized ChatGPT grant can request a direct file download.
