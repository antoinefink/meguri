# Meguri Sync collection MCP

Spec: servers/meguri-collection-mcp
Requirements: Meguri Sync Collection MCP R1–R17, AE1–AE4
Anki: none
Scenarios: server/tests/mcp_protocol.rs, server/tests/mcp_oauth.rs, server/tests/mcp_collection.rs, server/tests/mcp_performance.rs (planned)

## M1. Endpoint and ownership

The configured HTTPS origin serves one Streamable HTTP endpoint at `/mcp`. Its canonical resource URI is the exact public origin followed by `/mcp`. Each request acts on the current synced collection of the account that authorized its grant. MCP never selects an account, device, or collection from the request body. Use separate bearer credentials for MCP, the existing browser session for consent and grant management, and native credentials for sync.

Support the stateless `2026-07-28` lifecycle on POST, including `server/discover`, and the `2025-11-25` initialize lifecycle and its initialized notification on the same endpoint. Follow each negotiated revision's version, headers, status and JSON-RPC rules. Advertise tools only and return ordinary request results directly. GET returns 405. Reject a present invalid or different `Origin` with 403. The approved HTTPS origin is the only accepted browser origin. Record the revision needed by each real hosted client and verify any additional revision before admitting it. [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) [Prior transport revision](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

## M2. Discovery, client identity, and authorization

Serve public RFC 9728 protected resource metadata at `/.well-known/oauth-protected-resource/mcp`. Advertise the exact canonical resource, the single authorization issuer and both collection scopes. Use the configured HTTPS origin as the issuer and serve RFC 8414 issuer metadata at `/.well-known/oauth-authorization-server`. Publish `/oauth/authorize` and `/oauth/token` as absolute URLs. Advertise `response_types_supported: ["code"]`, `grant_types_supported: ["authorization_code", "refresh_token"]`, `code_challenge_methods_supported: ["S256"]`, `token_endpoint_auth_methods_supported: ["none"]`, `client_id_metadata_document_supported: true`, and `authorization_response_iss_parameter_supported: true`. [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)

Missing and invalid credentials receive HTTP 401 with a Bearer challenge naming the protected resource metadata URL. A first connection challenge advertises `scope="collection:read collection:write"` so the consent page can offer both modes and default to read. Send `invalid_token` for invalid credentials. The read and write tools require `collection:read` and `collection:read collection:write`, respectively. Scope denial for a valid bearer defaults to HTTP 403 with `insufficient_scope`, the metadata pointer and the complete scope set required for the attempted operation. Claude requires this transport challenge for scope step-up. [OpenAI authentication](https://developers.openai.com/plugins/build/auth) [Claude authentication](https://claude.com/docs/connectors/building/authentication) [Claude scope step-up](https://claude.com/docs/connectors/building/lazy-authentication)

Verify whether hosted ChatGPT connects and gains write access from these transport challenges. Verify its tool-level challenge for an attempted write using a valid read grant. The tool-level format is a denied result with `isError: true` and a Bearer challenge array in `_meta["mcp/www_authenticate"]`. Include `resource_metadata`, `scope`, `error` and a generic `error_description`. If the hosted integration needs this response, select it by the server-owned ChatGPT grant binding. Refusal occurs before collection mutation for either response format. [ChatGPT tool-level authentication](https://developers.openai.com/plugins/build/auth#triggering-authentication-ui)

Accept published Client ID Metadata Document (CIMD) identities through a server-owned table of reviewed records. Each record binds an exact client ID, the allowed exact redirect URI, the consent name and public-client code/refresh support. Review the values against the publisher's documentation or public metadata before changing a record and verify them with a hosted connection. A request selecting a table entry performs no outbound lookup. Unknown identifiers and redirects fail locally, including lookalike hosts, unlisted paths, redirect URI prefixes, userinfo and fragments. URL strings supplied by the client never determine a fetch. The identity is a public client registration. The user session, exact callback and PKCE protect code delivery and exchange. Reserve generated fixture identities for the disposable harness.

## M3. Consent, tokens, and revocation

Continue the validated request through the existing browser sign-in using the opaque, expiring pending request in [W10](meguri-sync-web.md#w10-mcp-consent-and-connections). A pending request expires after ten minutes. Only an authenticated same-origin approval can issue a code. Bind the code to the account and its credential generation, validated client, exact redirect, canonical resource, approved scopes and PKCE challenge. Denial issues no code or grant. Consent replay cannot create another code or grant. Each code lasts at most 60 seconds and can be exchanged once, including concurrent attempts.

`POST /oauth/token` accepts form-encoded OAuth requests for authorization code exchange and refresh rotation. It requires the exact bound resource. Code exchange requires the public client ID. On refresh, use the client bound to the credential and reject a supplied client ID that differs. Code exchange requires a matching S256 verifier. If a `redirect_uri` is supplied for OAuth 2.0 compatibility, it must exactly match the bound redirect. OAuth 2.1 may omit it. Consume the code and establish an independent grant with access and refresh credentials in one metadata transaction. The response contains a Bearer access token, `expires_in`, a refresh token and the granted scope. An access token lasts at most 15 minutes. A grant's rotating refresh family expires 30 days after code exchange. A valid refresh consumes its old credential and returns its single replacement in the same transaction. It cannot expand the grant or change its account, client or resource. A replay of a consumed refresh credential from that same client and resource invalidates its family. An expired, revoked or consumed credential fails with the standard OAuth error. [RFC 6749](https://www.rfc-editor.org/rfc/rfc6749) [OAuth security guidance](https://www.rfc-editor.org/rfc/rfc9700)

Store only digests of high-entropy opaque codes and token secrets in account metadata. Keep the grant, credential generation, scope, resource, client binding, lifetimes and replay state outside the transferable collection. Serve private authorization pages, redirects and token responses with no caching or Referrer disclosure. Keep codes, tokens, pending handles, client state, note contents, and proposed edits out of application logs, proxy request logs, and error text.

At every tool call resolve the account from the bearer and verify its scope, resource, grant, expiration, and credential generation. Recheck that exact grant at the account's collection admission boundary and immediately before a collection write commits. Check the original authority and publication before releasing read results. An ended grant cannot begin new work. Revoke a selected grant through W10, including outstanding access and refresh credentials. Password change/reset, disable, deletion and recovery or restore invalidate affected older grants and outstanding codes under the same account authority rules as [W2, W6](meguri-sync-web.md). Browser logout revokes the browser session. An ordinary full collection replacement for the same account retains its connections. Any request already pinned to the replaced publication and all revision/page handles for that publication become stale.

Browser grant revocation and invalidation on replay of a valid authorization code or refresh token take the same per-account publication barrier as a collection write. Keep a bounded consumed-code correlation to the issued grant. A still-valid code replay with the original client, verifier and resource, and an exact redirect if supplied, returns `invalid_grant` and revokes the grant issued from that code. A replay with mismatched bindings leaves the grant active. Follow `sync/server-lifecycle#L4`. Resolve the target first, release any metadata lock, acquire the account barrier, and then take the metadata writer. Under that order, revalidate the original authority or replay binding and commit the invalidation. Retain the barrier from the collection write's final authority check through its durable commit. If invalidation obtains the barrier first, the write fails its authority check and changes nothing. If the write commits first, its changes stay committed and invalidation applies to subsequent work.

## M4. Tool shapes and results

Expose exactly these four tools. Inputs are JSON objects with the stated members. IDs are positive decimal strings in signed 64-bit range, preserving IDs past the exact JSON-number limit. Names, note contents and error details are data. Do not render HTML, fetch links or resources, or execute strings found in a collection. Attach read-only annotations to the two read tools. Write tools identify their change in their descriptions. Publish per-tool OAuth `securitySchemes` with type `oauth2` and that tool's required scopes. Mirror the descriptor in `_meta.securitySchemes` for older clients. [OpenAI tool metadata](https://developers.openai.com/plugins/reference)

| Tool | Input | Successful result |
|---|---|---|
| `search_notes` | Any of `query`, `deck_id`, `tag`, `note_id`. Optional `limit`, `cursor` on paged searches. | `notes` and nullable `next_cursor`. |
| `list_decks_and_note_types` | Optional `kind` (`all`, `deck`, or `note_type`, default `all`), `limit`, `cursor`. | `decks`, `note_types`, and nullable `next_cursor`. |
| `create_note` | `deck_id`, `note_type_id`, `fields`; optional `tags`. | `note_id`, `revision`. |
| `edit_note` | `note_id`, `revision`; at least one of `fields`, `add_tags`, `remove_tags`. | `note_id`, `revision`. |

A note result contains `note_id`, `note_type_id`, `fields`, `tags` and `revision`. Tool fields are maps from exact note type field names to strings. Tag arrays contain tag names. Each deck result has `deck_id` and `name` and indicates whether it is `filtered`; each note type result has `note_type_id`, `name` and `field_names` in stored field order. Use the same JSON data in structured content and text for client compatibility. Reject unexpected and duplicate members and enforce request/result byte and item limits before unbounded work. Preserve complete note field values and field lists within those limits. Return a size-limit error when one requested result cannot fit.

An exact ID search returning no row returns an empty list. An edit to a missing note reports `not_found`. Return `conflict` for a changed note, layout or publication. Other collection outcomes include `invalid_input`, `result_too_large`, `unsupported_collection` and `busy`. Mark them as tool errors. A `busy` result includes a retry indication and certifies that the write did not commit. Use JSON-RPC errors for invalid protocol operations. Keep OAuth and transport errors at their HTTP boundary.

## M5. Bounded reads and exact revisions

`note_id` alone performs a primary-key lookup with keyed reads for its note type and field layout. It rejects other filters and pagination parameters. A paged search requires at least one other filter, combines filters with AND, and returns distinct notes ordered by increasing ID. Text is a case-insensitive literal substring over stored field values with no query operators or regular expressions. A tag matches the whole canonical tag case-insensitively. A deck matches a card's home deck by exact ID. Query filters, input lengths, examined candidates and result bytes have fixed limits. The default page limit is 20 records and the maximum is 50. A page may return fewer matches, including zero, and a continuation cursor if its examination budget ended first. The cursor advances past all examined candidates that could be returned or ruled out within the result budget. It never silently skips a match omitted for fit.

The catalog reads existing supported decks and note types in kind order, decks first, then by increasing ID within kind. It uses the same result limits. Authenticate page cursors or keep them server-owned. Bind them to the account, published collection generation, tool and query shape. Use a key position, not a growing SQL offset. Each page uses committed state. Changes made between pages can affect what a later page observes. Abort old-publication cursors with `conflict`. Use a bounded read transaction and close it before returning. No collection copy or independent search index build occurs on a request.

Treat `revision` as an opaque equality value. Bind it to the account, publication generation, note identity and persisted state, with the note type field layout in ordinal order. Include persisted change stamps and content so that same-second changes are detectable. A revision for a different note or account gives no information about that note or account. Compare the token against the current row and layout inside the write transaction before applying any patch. Rechecking an unchanged note yields the same revision. A revision is useful only while that state remains current.

## M6. Note creation and patching

Resolve creation's deck and note type in the live transaction and require an existing usable normal deck. Validate the exact field names against that note type. Unspecified creation fields start empty. Save fields and tags using the collection's creation rules. Use [C7](../sync/server-collection.md#c7-standalone-mcp-note-writes) for canonical persisted rows and stamp rules. Return the allocated note ID and committed revision only after the entire change, including generated cards, is durable.

For an edit, named fields are replacements and omitted fields keep their exact stored values. `add_tags` and `remove_tags` change only the named tags against the canonical tag registry. Reject ambiguous add/remove overlap. Preserve GUID, identity, note type, flags, data and existing cards. Validate the complete patch before effects. A stale revision conflicts even for a no-op. A valid patch with no effective change returns the same revision and writes nothing.

## M7. Acceptance

Use disposable generated accounts and collections. Verify both supported lifecycles, wrong-scope and other-account requests, stale revisions and pagination, denial, code replay, permission lifecycle transitions, active writer contention, and native incremental delivery. Verify sign-in, read, edit, create and native sync in real hosted ChatGPT and Claude before claiming their compatibility. Record their negotiated revisions separately from local protocol fixtures.

For both browser revocation and refresh-replay invalidation, order a write and invalidation deterministically with test barriers. First commit invalidation while the write waits to take the account barrier. Verify that the write fails and note, card and stamp state remains unchanged. Then pause the write after its final check while it owns the barrier and start invalidation. Verify invalidation cannot complete before the collection commits, the committed change survives, and the next tool call and refresh fail.

Compare exact lookups, creation and one-field edits at fixed payload sizes on equivalent approximately 20 MB and 200 MB fixtures. Use a release Docker runner with two CPUs, 2 GiB of memory, local SSD and WAL durability. Record page I/O, peak incremental memory, fixture/cache state and warm and cold latency. Report bounded text search and checkpoint work separately. The initial acceptance budgets are 150 ms idle p95 per single-note operation and 250 ms server-side for a retryable busy response while a native sync owns the writer. A point operation must show no whole-file work or growth proportional to total file size. See C7 for native stamp and incremental delivery checks and existing same-ID sync behavior.
