# FSRS optimizer

Spec: sched/optimizer
Requirements: R691, R692, R693, R694, R695, R696, R697, R698, R699, R700, R701, R1850, R1852, R1904, R1905; supports R704, R1468, R1486, R2052; AE28
Anki: 26.09.3
Scenarios: conformance/scenarios/sched/optimizer/ (inactive; the oracle runs their ops, Meguri's executor does not yet: O17)
Status: Approved 2026-10-27 (R2066) for O12 and O13; settle the open items of O19 first. Every other section is in force.

How Meguri re-optimizes each preset's FSRS parameters (U47): which presets and cards it trains on, when it adopts a result, what the adoption writes, when a run starts, and how a run stays safe beside review sessions and CloudKit. The training items are `sched/fsrs-items#I7`; the memory-state refresh is `sched/memory-state#M4`; the preset view is `sched/presets`. "Optimize" here is FSRS parameter fitting only, not the SQLite optimize of U132 (`maintenance/optimize-integrity`).

Terms from other specs:

- home deck, home preset, parameter list in use, decay: `sched/presets#V1`, `#V6`; desired retention in force: `#V7`;
- unsupported preset: `sched/fsrs-policy#U1`, `#U2` (U45's `UnsupportedParams`, `sched/fsrs-transitions#T13`);
- today's day number: the day query of `sched/day-clock#D5` (`days_elapsed`); `next_day_at`: `sched/fsrs-items#I1.2`;
- ops, sources, snapshots and preconditions: `engine/op-model` O1, O6, O7; jobs, cancel tokens and progress: `engine/jobs` J1, J4, J5;
- the CloudKit policy, its inputs, actions and gate: `sync/policy` P3, P4, P6, P17.

## O1. Anki's two optimizer paths (reference)

Anki 26.09.3 optimizes only when the user asks, from the deck options screen. It has two paths, and they differ:

| | Optimize (one preset, the screen's button) | Save and optimize all presets |
|---|---|---|
| Presets | the preset being edited | every row of `deck_config`, the screen's current preset last |
| Card search | `param_search` when it is not the empty string, else the text `preset:"<name>" -is:suspended` with `\` and `"` in the name escaped with `\`. White space alone counts as a search: it parses as the whole collection (`search/grammar#G1`), and training then reads every review-log row, rows of cards that no longer exist included | `param_search` when it is not empty after trimming white space, else the same two terms written by Anki's search writer, which escapes `"` but not `\` |
| Relearning step count passed to training | the leading relearning steps whose running total stays below 1440 minutes (O4) | the number of relearning steps |
| Health check | when `fsrsHealthCheck` is on and the preset has more than 300 items | never |
| Minimum item count | none (the crate's own fallbacks, O3) | none |
| A preset whose computation fails | error dialog | its `fsrs_params_6` is unchanged and the run goes on; when that list is empty, the save then clears `fsrs_params_5` and `fsrs_params_4` too, so a preset that holds only an older list loses it and falls back to the defaults. The screen fills an empty `fsrs_params_6` from the older list in every preset it loads, but the path takes the presets the screen did not send straight from storage, so this hits an unmodified FSRS-5-only or FSRS-4-only preset |
| Cutoff date | the screen turns the stored text into milliseconds with the web view's date parser, not with `sched/fsrs-items#I1.3`: the two parsers accept different texts (that parser takes forms such as `2024/01/05`, which I1.3 refuses) and may read one text as different instants; a text it cannot read is an error | read with `sched/fsrs-items#I1.3`; a refused text fails the whole save, nothing written |
| Result | the screen shows the new list; the user must save | every preset's `fsrs_params_6` is set to the result, which is the list in use when nothing better was found, so a preset with only an FSRS-5 list gets that list copied into `fsrs_params_6`; then the deck options save runs as usual |
| `lastFsrsOptimize` | not written | set to today's day number |
| Memory states | the save recomputes decks whose list in use changed, and reschedules them when the screen's "Reschedule cards on change" is on | the same |
| Undo | the save is one undoable step, "Deck Options" | the same |
| Cancel | aborts training; nothing is written | aborts the whole save; nothing is written |

Both paths use the same training items (`sched/fsrs-items#I7`), the same training settings apart from the relearning step count, and the same adoption rule (O4, O5). The screen warns when `lastFsrsOptimize` is positive and more than 30 days before today.

Meguri has no optimizer UI (R691) and runs one automatic all-preset path. It follows the one-preset path where the plan names that path's rules (R694, R700) and decides the rest below; O16 lists the differences.

## O2. Presets and their card sets (R694; settles `sched/fsrs-items#I7`)

- A run visits every row of `deck_config` in ascending `id` order. `n` in the progress (O15) is that count.
- **Default card set.** When the preset's `param_search` (schema-11 `weightSearch`) is empty after removing leading and trailing white space (Unicode White_Space), the set is the cards whose `did` or `odid` is a normal deck whose preset id is this preset's `id`, and whose `queue` is not -1 (suspended). Buried cards, new cards and cards in filtered decks (through `odid`) are in the set. No card is left out for its `type` or for a `queue` other than -1: its items come from its rows alone (`sched/fsrs-items#I3`), so a new card that was never answered gives none, a card that Forget reset gives none until it is learned again (its Reset marker ends its history), and a card stored as new over rows with no Reset marker gives its items like any other.
- **Custom card set.** Otherwise U80 runs the stored `param_search` text as stored (untrimmed), and the set is the cards it finds. A text U80 refuses skips the preset (O3).
- The rows read are those of `sched/fsrs-items#I1.1` for the set's cards. Review-log rows of cards that no longer exist are never read.
- Decided 2026-10-27: Meguri selects the default set by preset id, not through a `preset:` search text. Anki's two paths both find a preset by name with the escapes still in the value (`search/names-and-ids#N3.6`), so Anki's set differs in these cases:

  | Preset name | Anki, one-preset path | Anki, all-preset path | Meguri |
  |---|---|---|---|
  | holds `"` | no card | no card | the preset's cards |
  | holds `\`, not as its last character | no card | the preset's cards | the preset's cards |
  | ends in `\` | no card | search refused: `fsrs_params_6` unchanged, and an empty one also clears `fsrs_params_5` and `fsrs_params_4` (O1), so a preset that holds only an older list loses it | the preset's cards |
  | holds white space other than U+0020 (a tab, a line break, U+00A0, U+3000: the set of `search/grammar#G1`) | no card | U+3000, or a name that also holds U+0020, `(` or `)`: no card. Any other such character in a name without those: the search splits there (below) | the preset's cards |
  | equal under unicase to an earlier preset's name | the earlier preset's cards | the earlier preset's cards | the preset's cards |

  The white-space row holds because the search parser turns every such character into U+0020 before it parses, inside quotes too (`search/grammar#G1`). In a quoted value the value then no longer equals the stored name; when the name with U+0020 in those places is another preset's name, Anki finds that preset's cards instead (the unicase row). The one-preset path always quotes the name. Anki's search writer, which the all-preset path uses, quotes the term only when `preset:<name>` holds U+0020, U+3000, `(` or `)`. Unquoted, any other white-space character becomes a separator: the search is `preset:<the name's text before it>`, then the rest of the name as further terms (`search/grammar#G3`), then `-is:suspended`. So with presets `a<TAB>b` and `a`, the all-preset path trains `a<TAB>b` on the unsuspended cards of preset `a` that match the text `b`, and a name `x<TAB>OR` gives `preset:x OR -is:suspended`, every unsuspended card of the collection. Training a preset on its own cards is the purpose of the default search, and a name never changes which cards a preset schedules. For every other name the sets are equal. The all-preset column is read from Anki's search writer and parser; scenario `sched/optimizer/preset-names` (O17) confirms it on the oracle. The count of `sched/memory-state#M5` already counts such a preset's cards (`sched/memory-state#M10`).
- Decided 2026-10-27: white space alone in `param_search` means the default set, as in Anki's all-preset path. Anki's one-preset path trains on the whole collection's review log instead, rows of cards that no longer exist included (O1); Meguri never reads those rows (above, O16). The M5 count reads it as a search (`sched/memory-state#M5`); the two features stay as Anki has them.
- `sched/fsrs-items#I7`'s card-set bullet states this section's default set (O18 item 2, made).

## O3. Presets a run skips

A preset is checked in this order. The first rule that applies records its outcome (O14), and the preset is not written; its cards keep their rows. The run goes on with the next preset.

| Order | Condition | Outcome |
|---|---|---|
| 1 | the preset is unsupported (R704): nothing of it is read, built, trained or written | `unsupported` |
| 2 | its stored `ignore_revlogs_before_date` is refused (`sched/fsrs-items#I1.3`) | `invalidCutoff` |
| 3 | U80 refuses its `param_search` | `searchFailed` |
| 4 | fewer than 64 training items (R693): the item count of `sched/fsrs-items#I7` | `tooFewItems` |
| 5 | the crate fails in training (O4) or in the adoption rule (O5), or the adopted list fails validation (O5); a failed health check is no failure (O6) | `failed` |

- Decided 2026-10-27: a refused cutoff skips that preset only. Anki's all-preset save fails whole; skipping keeps the other presets' results and writes nothing for the broken one. The typed error of `sched/fsrs-items#I1.3` names the preset in the outcome.
- The 64-item minimum is Meguri's (R693). Anki has none: with no item it returns the list in use without training or comparing. Otherwise the crate fits on a training set it prepares from the items, which can be smaller than the I7 item count: with fewer than 8 of those it returns its default parameters, and with fewer than 64, or when every one of them is an initialization item, it fits only the first four values and returns the defaults for the rest. This can also happen to a Meguri preset that passes rule 4; it is the crate's result, not a failure. The adoption rule (O5) then compares it as any other.
- **The crate's preparation** (informative: Meguri calls the crate and does not implement it; stated so that tests and scenarios can be designed). A card's *first item* is its item whose history holds exactly one review on a day after the learning start; its *key* is the rating of the history's first entry and the day count to that review from the entry before it (its interval). Within one first rating, the crate takes the groups of equal key from the smallest (at equal size, the shorter interval first) and drops each one while the first items dropped so far, that group's included, stay below the larger of 20 and that rating's count of first items divided by 20, rounded down. From the first group that would bring the count to that mark or past it, each group is kept only when it holds at least 6 first items and its interval is at most 100 days (365 days for a first rating of 4), and dropped otherwise. Every item of a card whose key was dropped leaves the training set, and the kept first items are the initialization items. So a first rating with fewer than 20 first items loses all of its cards' items. Consequences used by O17: one to 19 cards whose histories start with the same rating lose all of their items, so a preset with only such cards gets the crate's defaults; 20 or more cards that share one key with an interval of at most 100 days, and no other card of that first rating, keep every item.

## O4. Training (R694)

For a preset that passes O3, the items, card ids and counts are `sched/fsrs-items#I7`'s, with `next_day_at` of the run's start (O8). The crate call is `compute_parameters` with this `ComputeParametersInput`:

| Member | Value |
|---|---|
| `train_set`, `card_ids` | the preset's items and card ids, in I7's order |
| `enable_short_term` | true |
| `num_relearning_steps` | `Some(count)`, with the relearning step count below, `Some(0)` included (the crate reads `None` as 1) |
| `training_config` | `TrainingConfig` with `num_epochs` 8 and every other member at the crate's default (the crate's default epoch count is 5) |
| `progress` | a `CombinedProgressState`; the run's cancel token sets its `want_abort` (O15) |

**Relearning step count.** Walk the preset's `relearn_steps` (minutes, `sched/presets#V5`) in order, adding each step to a running total computed in f64 from the stored f32 values. The walk stops at the first step whose running total, that step included, is 1440 or more; that step and those after it do not count, and every step before it counts. A NaN total is never 1440 or more, so a NaN step counts and the walk goes on (the total stays NaN, so every later step counts too).

| `relearn_steps` | Count |
|---|---|
| `[]` | 0 |
| `[10]` | 1 |
| `[10, 60]` | 2 |
| `[10, 1440]` | 1 |
| `[1440]`, `[2880, 10]` | 0 |
| `[1000, 439.5, 0.5]` | 2 (1000, 1439.5; the third reaches 1440) |
| `[10, NaN, 2000]` | 3 (the totals from the second step on are NaN) |

The same count goes to the adoption rule (O5).

- Training runs on the optimizer's own rayon pool, built through the thread registry at utility QoS (`engine/jobs#J2`, `#J6`); nothing uses rayon's global pool (KTD8).
- A preset's items are dropped before the next preset's are built (R1852, `sched/fsrs-items#I7`). What a run keeps between presets is only each preset's result (a list of 21 values or none), its outcome, counts and health result.

## O5. The adoption rule (R695, R1905)

Let `current` be the preset's parameter list in use (`sched/presets#V6`; empty means the crate's defaults, as `FSRS::new` builds them) and `new` the list `compute_parameters` returned. On the preset's items:

1. `loss(current)` and `loss(new)` are the `log_loss` members (f32) of `FSRS::evaluate` on all of the preset's items, with each list's model.
2. When `loss(new)` < `loss(current)`, adopt `new`.
3. Otherwise, when the relearning step count (O4) is 0 or 1, keep `current`.
4. Otherwise run the short-term check on `current`'s model: from the memory state (stability 1.0, difficulty 1.0), take the Again state of `next_states` with desired retention 0.9 and 2 elapsed days; from it, take the Good state of `next_states` with retention 0.9 and 0 elapsed days, as many times as the relearning step count. When the stability reached is below 1.0, keep `current`; otherwise adopt `new`.

- Step 4 is Anki's: `current` lets stability grow through a lapse's same-day relearning steps, a fault that log loss does not measure, so a list trained with that step count replaces it. Decided 2026-10-27: Meguri keeps step 4 (R695 names it, and R1904 compares results with the oracle's). For R1905, a list "fits better" when step 2 or step 4 adopts it; the R1905 test shows that a `new` with `loss(new)` ≥ `loss(current)` is never adopted when step 3 applies, or when the check of step 4 finds a stability below 1.0. Plan correction: O18.
- **Validation (R696).** An adopted list must have 21 values, all finite, and `FSRS::new` must accept it (the crate that Anki 26.09.3 uses is the same 6.6.2). A list that fails is not adopted; the outcome is `failed`.
- A crate error in step 1 or step 4 fails the preset (`failed`). The case where `current` cannot be built does not occur: such a preset is unsupported (O3 rule 1). Anki adopts `new` without comparing in that case.
- Outcomes: `adopted` or `notBetter` (steps 3 and 4 keeping `current`).

| Relearning step count | `loss(new)` vs `loss(current)` | Short-term check on `current` | Result |
|---|---|---|---|
| any | lower | not run | adopted |
| 0 or 1 | equal or higher | not run | `notBetter` |
| 2 or more | equal or higher | stability below 1.0 | `notBetter` |
| 2 or more | equal or higher | stability 1.0 or above | adopted |

## O6. The health check (R700)

- It runs only for a preset whose O5 outcome is `adopted` or `notBetter`, whichever, when `fsrsHealthCheck` reads on (`sched/config-keys#G2`: bool reader, default true) and the preset has more than 300 items. Otherwise the preset has no health result: a preset whose outcome is `failed` has none, as in Anki, where such an error ends the computation before the check.
- The crate call is `evaluate_with_time_series_splits` with the same `ComputeParametersInput` as O4 (`num_relearning_steps` `Some(count)` included). Its progress callback returns false once the cancel token is set.
- With `c` the item count, `r` the share of items whose last review has a rating above 1, `L` and `E` the `log_loss` and `rmse_bins` it returns, all in f32:
  - adjusted log loss = `L` / (0.623 × (4 × `r` × (1 − `r`))^0.738);
  - adjusted RMSE = `E` / (0.0135 / (`r`^0.504 − 1.14) + 0.176 / ((`c` / 1000)^0.825 + 2.22) + 0.101);
  - the result is `good` when the adjusted log loss is at most 1.11 or the adjusted RMSE is at most 1.53, and `bad` otherwise.
- A crate error gives no result; it does not fail the preset. An `Interrupted` error is the run's cancellation (O15).
- The result is recorded for the diagnostics view (O14). Meguri shows no dialog (R700) and the result never changes the adoption.

## O7. The job (R698)

One optimizer job at a time per engine (KTD9). States:

`Idle → Training{preset k of n} → AwaitingGate{jobId, adopted} → Committing → Done{adopted, skipped}`, and the ends `Cancelled`, `Abandoned{reason}`, with reasons `inputChanged`, `sessionActive`, `superseded`, `gateFailed` and `collectionClosed`, and `Failed{error}`.

| Call | Effect |
|---|---|
| `optimizer_start(trigger, guard, start)`, trigger `automatic` or `optimizeNow`; `guard` is the P4 guard of its `StartOptimizer` (O12); `start` is the start id of that `StartOptimizer` (O12), which the core copies onto the job's `OptimizerJob{Training}` (decided 2026-10-27, O19 review) | refuses, writing nothing, with the first that applies: `staleGuard` (the guard is not current, `sync/policy#P4`), `notReady` (lifecycle not `Ready`), `fsrsOff` (`fsrsPolicyStatus()` is not `ok`, `sched/fsrs-policy#S1`), `sessionActive` (a review session is admitted, `sched/review-session#C2`), `running` (a job is in `Training` or `Committing`), `notDue` (trigger `automatic` and O11's cadence is not due). Decided 2026-10-27: a start that the engine itself refuses maps to `notReady`: a control call holds the lane (`engine/suspend` S1, open, close, suspend or resume) or a lifecycle error such as `CollectionUnavailable` or `StaleGeneration`; these are the only other refusals, so the coordinator always has an O7 reason to report. A refused start changes nothing, a job in `AwaitingGate` included. When no refusal applies and a job is in `AwaitingGate`, that job is ended `Abandoned{superseded}` before the new job starts. Otherwise starts a J1 job and returns its handle. A handle that suspend's registry gate returns already cancelled (S1's final quiesce) is a started job: it is reported as `OptimizerJob{Training}` and ends once, `Cancelled` |
| `optimizer_commit(jobId, guard)`; `guard` is the P4 guard of its `OptimizerGate` (O12) | for a job that is not in `AwaitingGate` (unknown, `Committing` or ended): refuses with `notAwaitingGate`, writes nothing and publishes no end. A guard that is not current at the call refuses with `StaleGuard` and ends the job `Abandoned{inputChanged}` with nothing written. Otherwise it moves the job to `Committing` at once, queues O9's op and returns `Accepted` without waiting for the op; the op runs O8's checks, and the job ends `Done`, `Cancelled`, `Abandoned{reason}` or `Failed{error}`, reported only through `OptimizerEnded` and `OptimizerJob{Ended}`. A guard that turns stale before O8's checks ends the job `Abandoned{inputChanged}` with nothing written; the call has already returned `Accepted`. Decided 2026-10-27: these three, `Accepted`, `notAwaitingGate` and `StaleGuard`, are the call's only results |
| `optimizer_abandon(jobId)` | ends a job in `AwaitingGate` as `Abandoned{gateFailed}`; writes nothing. For a job not in `AwaitingGate` (a `Committing` job included): refuses with `notAwaitingGate` and changes nothing |
| `cancel_job(jobId)` (`engine/jobs#J1`) | O15. Decided 2026-10-27: for an optimizer job id it looks the job up in the optimizer's own state, also after its J1 job has finished at `AwaitingGate`, and returns true when the job had not ended (`Training`, `AwaitingGate` or `Committing`: it requested the cancel), false for an ended or unknown id. The job's end, which may still be `Done` (O15), comes only from `OptimizerEnded` |
| `optimizer_diagnostics()` | O14 |

- The training job finishes (`JobFinished{Succeeded}`) when it reaches `AwaitingGate`. Decided 2026-10-27: an end reached during `Training` finishes it with `JobFinished{Cancelled}` for `Cancelled` and `Abandoned{collectionClosed}`, and with `JobFinished{Failed{error}}`, the same error, for `Failed{error}`; no other end occurs in `Training`. Ends after `AwaitingGate` publish no `JobFinished`. Its results stay in the engine, keyed by job id, until `optimizer_commit` or `optimizer_abandon` ends them. Results are kept in memory only: a close or a replacement ends the job (below), a relaunch drops them, and the next run starts again.
- Every run that is not cancelled and does not fail reaches `AwaitingGate`, also when no preset was adopted: its commit still writes `lastFsrsOptimize` (R692).
- Decided 2026-10-27: every job that `optimizer_start` started publishes exactly one end, whatever stops it (as `engine/jobs#J1` for `JobFinished`). Besides the calls above:
  - a close (`engine/lifecycle#L10`) or a replacement (`#L8`) ends a job in `Training` or `AwaitingGate` as `Abandoned{collectionClosed}` with nothing written: training stops, and a snapshot that fails with `CollectionUnavailable` or `StaleGeneration` gives this end, not a failure. A job in `Committing` takes its op's result: an op queued before the close or the replacement's drain commits (L10, `#L7` step 3) and ends the job as O8 and O9 say, and an op refused because the collection closed or changed ends it `Abandoned{collectionClosed}`;
  - any other error outside a preset's training ends the job `Failed{error}` with nothing written: a `Failed` end of the training work (a panic is `Failed{Internal}`, J1), a snapshot read error, or a commit op that ends with an error other than a precondition (O8) or a cancel, such as `Panicked` or an I/O error, after which the op has rolled back (`engine/op-model#O3`). A crate error inside one preset stays that preset's `failed` outcome (O3 rule 5).
  After such an end, `optimizer_commit` and `optimizer_abandon` for that id refuse with `notAwaitingGate`, as for every ended job.
- Each end publishes `OptimizerEnded{jobId, outcome}` on the change stream. The core reports the job to the policy as `OptimizerJob{jobId, state}` (O12 Inputs): `Training` inside `optimizer_start`, before the job's work can run and before the call returns (decided 2026-10-27, review of the O19 corrections: every other `OptimizerJob` input of that job comes after it, in the order of its states, `Training`, then `AwaitingGate`, then `Ended`, on the one queue that carries the policy's core inputs; an already cancelled handle is reported `Training` before its `Ended{Cancelled}`), `AwaitingGate` when it reaches `AwaitingGate` (the point of its `JobFinished{Succeeded}`), and `Ended{outcome}` for its `OptimizerEnded`, with the same outcome. An end that follows the commit op is published and reported only after that op's observers have run (`engine/change-stream#S2`), so the policy gets the commit's `TrackingChanged` before it (O12 rule 6).
- The optimizer takes no long-operation slot (`engine/lifecycle` L9 table).

## O8. The revision gate (R699, KTD8)

At start the job records, before reading anything: the collection generation; the binding (`sync/policy#P1`: its id, its epoch, and its state, `active` or `isolated` with the V2.2 reason) or none; today's day number and `next_day_at`; and the seq `S` of its first snapshot (`engine/op-model#O6`). Each preset's items are read from a snapshot of their own, taken when that preset's turn comes, so no read transaction stays open during training. All snapshots are at `S` or later.

`optimizer_commit` runs its checks inside the commit op's write transaction, before anything is written. The job ends `Abandoned{inputChanged}` and nothing is written when any of these holds:

- the generation differs (a replacement, a close and reopen);
- the binding differs from the recorded one (another binding, a first connection, a disconnect), or its state or isolation reason does (an isolation such as K18.4's `epoch_switched`, which keeps the id and epoch, or a V9.2 Resume);
- the guard of the `OptimizerGate` that called the commit is no longer current (`sync/policy#P4`; O7): this ends the job as above. The call returned `Accepted` when it queued the op, so only `OptimizerEnded` and `OptimizerJob{Ended}` report it; a guard already stale at the call is refused there with `StaleGuard` (O7);
- today's day number differs;
- an op with a seq above `S` changed a row of `revlog`, `cards`, `decks` or `deck_config`, or the config row of `fsrs`, `lastFsrsOptimize`, `fsrsHealthCheck`, `rollover`, `creationOffset` or `localOffset`: the preconditions `TableUntouched{table, S}` and `Untouched{config, key, S}` (`engine/op-model#O7`). Any source counts: local edits, answers, `CloudIncoming` applies (the gate's fetch included) and maintenance;
- when the set of at least one visited preset came from U80 (O2, custom set): an op with a seq above `S` changed a row of `notes`, `notetypes`, `fields` or `templates`, or the config row of `collapseTime`, `curDeck`, `normalize_note_text` or `ignoreAccentsInSearch` (what a search reads, `search/query-model#Q3`, `#Q8`), with the same two preconditions. Decided 2026-10-27: these are watched only then. The default set and the items read none of them (O2, `sched/fsrs-items#I1.1`), so a note edit never abandons a run that used no custom set, while a retag or a note type change that can move cards in or out of a custom set always does. The clock that `is:due` and `prop:r` read is not watched: such a set is the one found at its preset's snapshot.

It ends `Abandoned{sessionActive}` when a review session is admitted, or was admitted at any time since the job started, even if that session has ended (U43's session-start hook marks the job, O10). Decided 2026-10-27: this check comes first, so a marked job ends `Abandoned{sessionActive}` also when a change above holds too, such as the review-log row that an answer in that session added.

- A failing precondition here ends the job; it never re-plans (`engine/op-model#O6`'s retry does not apply).
- Since every snapshot is at `S` or later and nothing that the card sets (O2) and the items (O4) were read from changed after `S`, all presets were trained on one state of the collection.
- The core never calls the network for the optimizer. A CloudKit fetch before the commit is the policy's (O12); a fetch is not a lock (O13).

## O9. The commit (R692, R696, R697)

One op, source `Optimizer` (`engine/op-model` O1), catalog entry `optimizer_commit`: not destructive, not undoable, long write, write cancellable between batches (`engine/op-model` O9; O18 lists the entry). In its one transaction:

1. For each adopted preset: `fsrs_params_6` is set to the adopted list through the optimizer's setter (`decks/deck-presets#P10`). Nothing else in the record changes: `fsrs_params_5`, `fsrs_params_4`, later lists, `other` and unknown fields keep their bytes (R1486, `conformance/normalized-dump#N11.5`). The record is stamped (`usn` -1, `mtime_secs` now); a list equal to the stored one writes nothing.
2. For each adopted preset: the memory states of its cards are refreshed with `sched/memory-state#M4` (caller `#M7.3`): the cards whose home preset is this preset, processed as M4.1 says (suspended and buried included, new cards not), with the new list. Only `s`, `d`, `dr` and `decay` change, and only on cards whose values change (M4.2). No due date, interval, queue, type or review-log row changes (R697).
3. `lastFsrsOptimize` = today's day number (config write, `storage/config-table#C4`), also when no preset was adopted.

- Undo: source `Optimizer` clears the undo history (`engine/undo#M2`, reason `ClearedByNonUndoableOp`). No session is open at the commit (O8), so no answer loses its undo.
- Cancel points (decided 2026-10-27, O19 review): the op checks its token when the writer takes it (`engine/op-model#O5`), after O8's checks, between the batches of step 2, and after step 3, just before COMMIT. A cancel seen at one of them rolls the whole op back: nothing is written, and the job ends `Abandoned{sessionActive}` when a session hook requested the cancel (O10), `Cancelled` otherwise. Decided 2026-10-27 (review of the O19 corrections): two requests can reach one op, the submission hook's (`sessionActive`) and a `CancelOptimizer` (from `BackgroundExpiring`) or a suspend's cancel (O15). The first request recorded on the op's token decides the reason; the token ignores the reason of a later one. C2 step 2's mark of a `Committing` job whose op has not started (O10) is recorded on the op's token at that moment as a request with reason `sessionActive` (decided 2026-10-27, review of the O19 corrections), so a mark before a `CancelOptimizer` ends the job `Abandoned{sessionActive}` and a mark after it ends the job `Cancelled`. So the job has one end, and O14's `lastRun` records that end. A cancel requested after the last cancel point is ignored (`past_cancel_point`): the op commits and the job ends `Done` (O15). An end the op has already decided (an O8 precondition, an error) stands.
- Progress: phase `Committing`, cards visited out of the cards step 2 selects.
- Result `Done{adopted, skipped}`: the adopted preset ids, and every other preset id with its O3 or O5 outcome.
- Unsupported presets and their cards keep their bytes (`sched/fsrs-policy#U4`, K3 step 4).

Example (AE28, core part): `lastFsrsOptimize` 31 days before today; preset A trains but `notBetter`; preset B is adopted. Training ends in `AwaitingGate` with nothing written. `optimizer_commit` with nothing changed since `S`: A's record is not written; B's `fsrs_params_6` holds the new list; B's cards with changed values have new `s`, `d` and `decay` (the new list's decay, `sched/presets#V6`); no card's `due`, `ivl`, `queue` or `type` changes; `lastFsrsOptimize` = today.

## O10. Review sessions (R699)

- `startSession`'s optimizer hook (`sched/review-session#C2` step 2) requests cancellation of a job in `Training` without waiting: the job ends `Cancelled` and writes nothing. It marks a job in `AwaitingGate`, or in `Committing` whose op has not started (O7 moves the job before it queues the op), whose commit then ends `Abandoned{sessionActive}` (O8). C2 step 2 does not yet name the `Committing` case; O18 lists the correction for its owner, and this section decides until then.
- **Submission hook.** The commit op holds the writer, and C2's admission (step 1) runs on the writer, so a hook after admission would make the start wait for the whole commit. So `startSession` has a second optimizer hook, at submission, before the start is queued for the writer and before admission: when an optimizer commit op is queued or runs (decided 2026-10-27, review of the O19 corrections: the writer may take a queued commit between the hook and the start's enqueue), it requests that op's cancellation with reason `sessionActive`, without waiting, and does nothing else (it marks no job and cancels no training; C2 step 2 does that after admission). The commit rolls back at its next cancel point, the writer's take of a queued op included (O9), and ends `Abandoned{sessionActive}`, or commits and ends `Done` when it had passed its last one (O19 review); then the writer takes the start and C2 runs as usual. So a session never waits for more than one commit batch.
- Decided 2026-10-27: the submission hook fires for every submitted start, also one that admission then refuses (`FsrsPolicyPending`, `PresetUnsupported`). Admission can be decided only on the writer, after the commit, so predicting the refusal would mean waiting for the commit. A refused start therefore still costs that run: nothing is written, and the next arming input (O12 rule 2) runs it again. Data stays safe either way, since a cancelled commit writes nothing. C2 needs this hook as a new step before step 1; O18 lists the correction for its owner.
- `optimizer_start` refuses while a session is admitted (O7). The policy starts no run during a session (O12).
- Answers never wait for training: training reads snapshots and writes nothing.

## O11. Cadence (R692)

- The core computes **due**: `lastFsrsOptimize` (i32 reader, `sched/config-keys#G2`) is 0, or today's day number minus it is 30 or more (computed in i64). A value above today is not due. A value that does not read as i32 reads as 0 (never optimized), so it is due.
- The core reports `OptimizerCadence{due, fsrsOk}` to the policy (O12) when the collection becomes `Ready`, after every committed op that changes `lastFsrsOptimize` or `fsrs`, whatever its source (local edits, the optimizer's commit, `CloudIncoming`, the `SyncIncoming` merge of a manual Anki sync, `Maintenance`, …; a replacement reaches `Ready` again), and at every day rollover (`sched/day-clock#D9`). `fsrsOk` is `fsrsPolicyStatus()` = `ok`.
- Trigger `automatic` needs due; `optimizeNow` (R701's Optimize now) bypasses only due (O7).
- After one device's commit syncs, `lastFsrsOptimize` holds that device's day number on every device, at most a day or so from each device's own, so the others are not due (R692).

- **Order.** `OptimizerCoordinator` runs the optimizer actions of an action list after the list's core actions (`sync/policy#P4`), in list order, and does not wait for `SyncCoordinator`'s actions of that list, which skip them. - **The optimizer's fetch call.** A `RequestFetch{root, collection}` that a rule below emits carries a call id (`call`) from a counter of the optimizer state. A drain that carries the id read the database changes after the call started (`sync/policy#P3` `FetchDrained`), and P4 runs one call of an instance at a time, so it cannot be the drain of a fetch that started before the rule asked.
- **Deadlines.** `OptimizerCoordinator` holds two deadlines, each of one operation (`sync/policy#P2`): Optimize now's (rule 4) and the gate's (rule 5). It starts the gate's when the job it started reaches `AwaitingGate` (the job's progress, `engine/jobs#J5`, O15), which is the input at which the policy emits the gate's fetch, and disarms it when it executes `OptimizerGate` or `AbandonOptimizer` for that job or the job ends. When it passes still armed, it calls `optimizer_abandon`; a job that `optimizer_commit` has moved to `Committing` is refused there and goes on (O7).

**Rules.**

1. **Eligible**: lifecycle `Ready`, no active session, no job (State), `fsrsOk`, and the platform allows: on macOS while the app is open; on iOS and iPadOS in the foreground or while the optimizer processing task runs (R698). **Applies settled**: the tracking summary of the last `TrackingChanged` (`sync/policy#P3`) shows no `ready` inbox entry and no `applyInProgress`. Waiting inbox entries do not count (O13). A drain's fetched records are applied by `ApplyReady`, a core action that submits `CloudIncoming` ops only after `step` returns (`sync/policy#P4`), so a run that started at the drain itself would take its first snapshot (O8) before those applies commit, train on a state not yet reconciled, and then always abandon with `inputChanged`. Every connected start and the gate therefore wait until the applies have settled. Decided 2026-10-27: an `ApplyReady{retryFailed}` in the same list (an event trigger with an `apply_failed` entry waiting, P10.1) does not hold a start or the gate back. Its ops are queued before the optimizer's call (Order, above), so a retried apply that commits does so before the commit's checks, which then abandon `inputChanged`, and one that fails writes nothing. Waiting for it would stall: after its fifth failure an entry is retried only once per collection open (`sync/cloudkit-records#K13.2`), and an `ApplyReady{retryFailed}` that retries nothing makes no `TrackingChanged`. The cost is at most one unused run per retried entry that applies.
2. **Arming.** These inputs set `armed` when the cadence is due: `Lifecycle{Ready}` with a new generation, `SessionEnded`, `Foreground`, the launch decision of `ProcessingTaskLaunched{optimizer}` (below), and an `OptimizerCadence` whose `due` turns from false to true (from empty too, State). So at launch the run is armed whichever of `Lifecycle{Ready}` and the first `OptimizerCadence` comes first. In mode connected, auto, arming also emits `RequestFetch{root, collection}` with a new call id, the arming call (or gives the call id to the one the list already holds: the P10.1 and P11.1 rows, above). Setting or clearing `armed` clears `drainedSinceArmed`, and so does the mode entering connected, auto; when it enters it while armed, the `RequestFetch{root, collection}` of that input (P10.1's opening rows and `DeviceSettings{automatic: on}` row hold one) becomes the arming call. Mode connected, manual arms nothing: with Sync automatically off, the optimizer runs only through Optimize now. Starting a run clears `armed`; `SessionStarted` and a gate that closes clear it too. Decided 2026-10-27 (review of the O19 corrections): while a processing task runs, `Lifecycle{Failed}`, `Lifecycle{NoCollection}` and a move of the mode to connected, manual clear it too, since no run can start from them (rule 8 then ends the task). Decided 2026-10-27: `ProcessingTaskLaunched{optimizer}` sets the processing-task flag at once, and its launch decision waits until lifecycle is `Ready` and the cadence is current (State; O11 reports one at each `Ready`, before or after the `Lifecycle{Ready}` input; decided 2026-10-27, O19 review), since a cold launch reports the task while the collection still opens and the cadence is still empty. At the first input at which both hold, or at the launch input itself when they already hold, the decision is taken: when the cadence is due, `fsrsOk` holds and the mode is local-only or connected, auto, that input arms (as the inputs above, with its `RequestFetch` in mode connected, auto); when the cadence is not due, `fsrsOk` is false or the mode is connected, manual, it emits `EndProcessingTask{optimizer}` (rule 8); while the mode is blocked, the decision keeps waiting, because a launch reads the account and the binding after `Ready` and the gate may open only then, and `BackgroundExpiring` ends a task whose mode stays blocked (rule 8). A `Lifecycle{Failed}` or `Lifecycle{NoCollection}` while the decision waits emits `EndProcessingTask{optimizer}` (O19 review).
3. **Automatic start.** When armed and eligible and due, emit `StartOptimizer{automatic}`: in mode local-only at once; in mode connected, auto once `drainedSinceArmed` is set and the applies have settled (rule 1). `drainedSinceArmed` is set only by an input that comes while `armed` is set and the mode is connected, auto: a `FetchDrained{collection}` of the arming call (either `fetched`), or the `ExchangeEnded{succeeded}` of an exchange the policy started after arming. The policy checks at that input and again at every later input while armed, `TrackingChanged` included, so the start comes at the `TrackingChanged` whose summary shows the drain's applies settled. Blocked: none. Decided 2026-10-27 (O19 review): while a processing task runs and the policy holds no job, an `EngineActivity{zone, fetch, ended}` that carries the arming call id and ends `failed`, before `drainedSinceArmed` is set, clears `armed` and emits `EndProcessingTask{optimizer}`. Likewise (decided 2026-10-27, review of the O19 corrections), while a processing task runs and the policy holds no job, a `FetchCallEnded` of the arming call that comes before `drainedSinceArmed` is set clears `armed` (rule 8 then ends the task). Decided 2026-10-27 (fourth review of the O19 items): when the policy holds a job at that `FetchCallEnded` (one started before the launch, for example a start that suspend cancelled and whose `Ended` comes after `resume()`), it sets the arming-call-ended flag instead (State), and at the first later input after which the policy holds no job, `armed` is cleared when that flag is still set (rule 8's general end then ends the task at that input). So an arming call that never drains and never fails (both its calls joined a running fetch, its guard was stale, or the call failed before the engine started an operation) does not hold the task until `BackgroundExpiring`. So a run on a connected collection starts from a state that a fetch made after arming reconciled with CloudKit, with the fetched records applied (R699), and retries after an abandon wait for the next arming input, never for a timer. When rules 3 and 4 would both start a run at one input, only `StartOptimizer{optimizeNow}` is emitted; it clears `armed` and the pending request.
4. **Optimize now.** `OptimizeNowRequested` emits `OptimizeNowRefused{reason}` with the first that applies: `notReady`, `fsrsOff`, `sessionActive`, `running` (a job, or an Optimize now already pending), `cloudBlocked` (mode blocked). Otherwise, in mode local-only, `StartOptimizer{optimizeNow}`; in either connected mode, `RequestFetch{root, collection}` with a new call id, and the request is pending. While it is pending, `StartOptimizer{optimizeNow}` is emitted, and the request cleared, once a `FetchDrained{collection}` of that call has come, the applies have settled (rule 1) and the conditions still hold; the policy checks at every input, `TrackingChanged` included, as in rule 3. The pending request is cleared with `OptimizeNowRefused{reason}` when a refusal condition above starts to hold (a session start, a blocked mode, …), with `OptimizeNowRefused{fetchFailed}` at an `EngineActivity{collection, fetch, ended}` that carries the request's call id and whose outcome is `failed`, before the drain (a failed fetch with no call id or another one, such as a fetch the engine scheduled itself, changes nothing), and with `OptimizeNowRefused{fetchFailed}` at `OptimizeNowExpired`: `OptimizerCoordinator` holds a 5-minute deadline from the request, a deadline of one operation (`sync/policy#P2`), and reports that input when it passes with the request still pending. So a fetch that never drains never leaves a request that a much later, unrelated drain would start. Decided 2026-10-27: Optimize now is an explicit request like Sync Now, so its two fetches run also with Sync automatically off; its adopted result then waits for the next send (rule 6).
   - **A refused start.** The core can still refuse a `StartOptimizer` (O7: its view of the session, the cadence, `fsrsOk` or a job can be ahead of the policy's). `OptimizerStartRefused{start, trigger, reason}` with the recorded start id clears the `starting` job and its start mode (State). For trigger `optimizeNow` it emits `OptimizeNowRefused{reason}`, so the view shows the core's reason, with one mapping (decided 2026-10-27): `staleGuard` becomes `changed`, since the policy state moved on between the emission and the call (a `Binding` input, an account read, a replacement) and only a new request, with its own fetch, can start from the new state; `notDue` never applies to `optimizeNow` (O7). For `automatic` it emits nothing, and the next arming input runs again. While a processing task runs it also emits `EndProcessingTask{optimizer}` (rule 8).
5. **The gate.** At `OptimizerJob{AwaitingGate}`, with the mode the job started in from the policy state, and again at every later input while the policy holds the job in `AwaitingGate`:
   - a session has started (`SessionStarted`), or the mode is not the job's start mode (it changed, or became blocked), or, before the policy emitted `OptimizerGate`, an `EngineActivity{zone, fetch, ended}` that carries the gate's call id ended `failed`, for either zone (decided 2026-10-27: an offline device does not hold its results for the whole deadline): `AbandonOptimizer{jobId}`;
   - job started in mode local-only and the mode is still local-only: `OptimizerGate{jobId}` at once;
   - job started connected and the mode is still that connected mode: at `AwaitingGate`, `RequestFetch{root, collection}` with a new call id, the gate's call; then `OptimizerGate{jobId}` at the first input at which a `FetchDrained{collection}` of the gate's call has come, a `FetchDrained{root}` of the gate's call (either `fetched`) or a `RootConfirmed` has come since the policy emitted the gate's call, the applies have settled (rule 1) and the bound epoch is confirmed for the current engine instance (`sync/policy#P5`, P10.1 "Confirmed root"). The fetched records are thereby applied before the commit's checks, which then see them (O8). Decided 2026-10-27: P3 emits no drain for a zone whose zone fetch ended with an error, so the collection zone of a call can drain while its root zone fails; the root condition makes the gate wait for this call's read of `meguri-root`, or a `root_read` after it, and both drains come from one `fetchChanges` call, so it adds no wait in the normal case. ## O13. Two devices (R2052, KTD8)

- **One after the other.** When A's commit is on the server before B's gate call starts, B's gate fetch brings it (preset rows, `lastFsrsOptimize`, cards): the gate counts only the drain of its own call (O12 rule 5), which read the database changes after it started (U114 counts only the call's own will-fetch-changes and did-fetch-changes events, `sync/policy#P3`; O19 review, review of the O19 corrections). Those `CloudIncoming` writes touch O8's tables after B's `S`, so B's commit abandons with `inputChanged`, and B's cadence is then not due. B adopts nothing trained on a state that excludes an applied change of A. Records of A that wait in B's inbox (reasons `reference`, `generation`, `structure`, `format`, `asset`, `apply_failed`; O12 rule 1) do not hold B's gate back; they are the accepted race below.
- **A pending preset edit.** Decided 2026-10-27: K15.7 merges a preset's `config` as one part, so the one-after-the-other case can also meet a merge. When B holds an unsent edit of a preset that A adopted a list for (a daily limit, say), B's gate fetch merges the two: the later version's `config` wins whole, with A's adopted list or B's old one, and the other is kept in a conflict copy (`sync/cloudkit-records#K15.7`). B's commit abandons (`inputChanged`) and B is then not due. When B's version is the later one, B sends it and every device runs with the old list beside cards whose memory states A refreshed with its new list. Nothing refreshes memory states at a `CloudIncoming` preset change (`sched/memory-state#M7` has no such caller), so each card's state follows the list in force again at its next answer, and the whole preset at the next run, a deck options save (M7.1) or Check Database (M7.5). This is part of KTD8's accepted race: no data is lost, the other version stays in its conflict copy, which Review Conflicts lists (`sync/cloudkit-recovery#V17`), and scheduling stays valid. K15.7 is unchanged: making the parameter lists parts of their own would change an approved merge contract to save one conflict copy.
- **At the same time.** A fetch is not a lock: both may pass their gates and send. The CloudKit merge then decides (`sync/cloudkit-records#K15`): a preset's `config` changed on both sides takes the later version and keeps a conflict copy of the other (K15.7); `lastFsrsOptimize` keeps the later version's day (K15.8), which may differ by a day or so from the other device's (each computes its own day number, `sched/day-clock#D5`), and either value leaves both devices not due (O11); cards follow the card rule, so a card's memory state may come from the other device's parameters until its next answer or the next refresh. Every list kept is one a device adopted from its own reconciled state, so no data is lost and scheduling stays valid. This is KTD8's accepted race.
- **A stopped device.** Decided 2026-10-27: a binding isolated `stopped` is mode local-only (O12), so a device that stopped syncing optimizes on its local history, which may lack other devices' reviews since the stop. After a V9.2 Resume the merge treats its preset writes like the race above: K15.7 keeps the later version of each preset's `config` and a conflict copy of the other, which Review Conflicts lists (`sync/cloudkit-recovery#V17`), and the later `lastFsrsOptimize` keeps every device not due until 30 days after it. This is accepted as part of KTD8's race: no data is lost, the other list stays in its conflict copy for the user, and Optimize now runs at any time. Treating `stopped` as blocked would keep a device that stopped syncing for good from ever optimizing automatically (R692), against R699's local-only rule.
- Decided 2026-10-27 (data safety): a preset `config` conflict between two optimizer writes that differ only in `fsrs_params_6` keeps `sync/cloudkit-records#K15.7`'s conflict copy; nothing is dropped as a duplicate, and K15.7 is unchanged. So the accepted race may list one preset conflict per such preset in Review Conflicts (`sync/cloudkit-recovery#V17`).

The sidecar already holds device-only maintenance records with a durable atomic write.

`optimizerLog` is a JSON object:

| Member | Value |
|---|---|
| `lastRun` | object: `instant` (signed 64-bit epoch milliseconds: the instant of the run's end, when the end is recorded), `trigger` (`automatic` or `optimizeNow`), `end` (`done`, `cancelled`, `abandoned` with a `reason` member: `inputChanged`, `sessionActive`, `superseded`, `gateFailed` or `collectionClosed`, or `failed` with an `error` member, O7: a string, the error's kind name as `Failed{error}` carries it, `: `, then its message, so a panic gives `Internal: <panic message>`, `engine/jobs#J1`), `adopted` (array of preset ids as JSON integers, ascending, empty unless `done`) |

## O15. Progress, cancellation, suspend, budgets

- Progress (`engine/jobs#J5`): phases `Training` (preset k of n, the crate's iteration and total, the preset's review count), `Evaluating` (preset k of n), `HealthCheck` (preset k of n), `AwaitingGate`, then O9's `Committing`.
- Cancel: the token sets the crate's `want_abort`; the crate's `Interrupted` error ends the job `Cancelled` with nothing written (R698). The token is also checked between presets and between the steps of O4 to O6. `cancel_job` on a job in `AwaitingGate` ends it `Cancelled`; on a job in `Committing` it requests the cancel of the op, queued or running, which ends as O9's cancel points say (O19 review); on an ended job it does nothing. Decided 2026-10-27: once the op has passed its last cancel point, a job stays `Committing` until the op's observers have run (O7), and a cancel in that window has no effect: the job ends `Done`, which is what the collection holds, and has no second end. The same holds for suspend, `CancelOptimizer` (O12) and the session hooks (O10).
- Suspend (`engine/suspend` S1): the job is a `SuspendParticipant`. Its flush (`engine/lifecycle#L7` step 1, and `flush_for_background()` in S1) does nothing and returns at once: the optimizer holds no pending writes (a queued commit op is already the executor's). At its first step, with the jobs of J1's list (`engine/suspend` S1: "Cancel every ordinary job"), suspend calls `cancel_job` for the optimizer job when one has not ended (decided 2026-10-27, review of the O19 corrections; the job leaves J1's running list at `AwaitingGate`, O7, so that list alone does not reach it). `engine/suspend` S1 does not say this yet: it is O18 item 9, and this section decides until its owner makes it. Decided 2026-10-27 (fourth review of the O19 items): the participant's flush hook cannot make the request instead, because `flush_for_background()` runs the same hook while writes stay admitted, also while the optimizer's own processing task runs (`sync/policy#P11.2`), where the job must go on. So: a job in `Training` is cancelled, a job in `AwaitingGate` ends `Cancelled`, and a commit op, queued or running, has its cancel requested before suspend drains accepted ops, so the drain waits at most one batch of O9 step 2; the commit ends as O9's cancel points say (one past its last cancel point ends `Done`, above). The next arming input runs again; R1850's "resumed" means this new run.
