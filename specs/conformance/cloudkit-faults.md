# CloudKit fault points

Spec: conformance/cloudkit-faults
Requirements: R2051, R2054, R2055, R2056, R2057; supports R2002, R2003 (sync slice), R2015 (sync slice), R2066; AE92
Anki: none (Meguri design)
Scenarios: none (`core/crates/meguri-sync/tests/cloud_faults.rs`, through U250's child-process runner)

The catalog of named crash boundaries in Meguri's CloudKit sync, and what a device must look like after a fault at each one. `sync/cloudkit-recovery#V23.1` names the points the contract requires; this file is their catalog for U21's `faultpoint!` and U250's runner, adds the boundaries V23.1 leaves implicit (F7), and fixes the expected recovery per point (F5). The fake service, the device harness and the checks are `conformance/cloudkit-acceptance` (cited as Q…). U118 builds these runs; U250 owns the runner and its catalog, which must equal F5's table.

## F1. Terms

- **Point**: a `meguri_model::faultpoint!("<name>")` call (`core/AGENTS.md`) at a boundary of the CloudKit code, in `test-hooks` builds only. "After X" means right after X is durable and before the next step starts.
- **Hit**: the k-th time a point is reached in the child process (k ≥ 1). `@last` is the last hit of the class program, found by a counting run first.
- **Mode**: what happens at the hit (F3).
- **Variant**: a named arrangement of the class program or the fake for one row (F5).
- **Device under test** (D): the child process the runner arms. **Other device** (O): a second device bound to the same epoch, which the runner drives in its own process.
- **Restart**: the runner starts D's child again with the same data directory, offline first, then online.

## F2. What every fault leaves

After a fault at any point, in any mode, these hold, and the runner checks them (Q5's names in parentheses):

1. At the offline relaunch, the collection opens and `PRAGMA integrity_check` returns `ok`; the tracking file opens or follows `sync/cloudkit-recovery#V8.1` (`integrity`).
2. Every op whose `committed` line D's side journal holds is present (U250). In mode `power`, an op may be missing only when its commit came after the last completed flush of the collection file, which the child journals as a `flushed` line with the covered seq (`storage/open-and-connections#C9.2`, C9.3).
3. Tracking holds no fact about a collection commit the fault removed: no dirty mark, in-flight entry, acknowledgement, digest or settled intent for it (K10.1, K21 invariants 13 and 16).
4. No engine state is saved past a record or deletion that is not durably in the inbox, `refused` or applied (`cursor`).
5. No file in the cloud staging directory survives the start sweep unless an inbox row, blob row, `conflicts` row or recovery op names it (V6).
6. No unresolved conflict copy is lost, and none is made twice for one conflict (`copies`, K16 "Made once").
7. After the restart goes online and `drain(D, O)`: `converged`, `history`, `no-loss`, `no-resurrection`; no entity is saved as two versions of one change, no review row exists twice, and the service holds one `MGBlob` per content.
8. No record reaches a binding, account, container or environment other than D's (`isolation`), and no fact of the killed process's engine instance is accepted after the restart (`stale-refused`).
9. No decision, attention item or recovery op appears that the row does not name.

## F3. Modes

| Mode | At the hit |
|---|---|
| `kill` | SIGKILL of the child at the point. Returned commits survive (C9.3) |
| `power` | SIGKILL, then the runner restores every file and directory of D's data directory to what its last completed full fsync (`F_FULLFSYNC`) and its last directory fsync covered: the power-loss shim (below) |
| `io` | the point returns an I/O error to its caller; no kill |
| `nospace` | the point returns a full-disk error (`ENOSPC`, SQLite full) |
| `constraint` | the point returns a SQLite constraint error |
| `panic` | the core panics at the point, inside the call that reached it |

- **The power-loss shim** (decided 2026-10-27). In `test-hooks` builds, a VFS shim under every SQLite connection of D, and a file shim under the media store, the cloud staging writes and the collection replacement (`engine/collection-replace#R5`), record two things. For each file, the bytes written since its last completed full fsync (`F_FULLFSYNC`): the prior content of each overwritten range and the length before it grew. For each directory, the entry changes (create, rename, unlink) made since its last completed directory fsync, in order. At a `power` hit the runner kills D, then undoes the uncovered directory entry changes in reverse order (a rename goes back to its old name and the file it replaced comes back, a created entry goes, an unlinked entry comes back with the content it had), and then for each file restores the recorded ranges and truncates it to its synced length. So every data write that no full fsync covered and every entry change that no directory fsync covered is gone. SQLite then recovers to its last consistent state (C9.3). This models the worst power loss that C9.3 and the file system allow; a real disk may keep more of either kind, never less.
- Error modes are armed only at the tracking commit points (`cloud.tracking.commit.*`, F5) and model V3.3's failures; every other point takes `kill` or `power`.

## F4. The runner

- **Process model** (decided 2026-10-27). D is a `meguri-cli` child of U250's runner. The fake's service state lives in `fake-cloud.db` in the run directory (Q3.1), which D's process writes only through the service's transactional requests, so a kill of D never changes what the server holds. O and the scheduler run in the runner's process.
- **Arming**: `--arm <point>[@k|@last][:<mode>]` and `--variant <name>`. Default hit 1, default mode `kill`. Exactly one armed hit per run, which the row's checks judge.
- **Setup arming** (decided 2026-10-27): a class program or variant that needs an earlier fault to reach its row's point names it below as its setup, `--setup-arm <point>[@k]:<mode>`; a row never chooses one. The runner applies the setup fault first; when its mode killed D, it restarts D and checks F2 items 1 to 6 for it; only then it counts hits of the armed point. A setup's own row in F5 tests that fault; the setup only arranges the state. The counting run for `@last` includes the setup.
- **Classes** (U250's operation classes, added by U118). Each starts from `setup(D, O, small)` (Q4.2) and runs one program; the F5 rows of a class hit their points in it:

## F8. Decisions

- Decided 2026-10-27: the catalog is F5's table, and a test keeps U250's catalog and the code's `faultpoint!` names equal to it (F5).
- Decided 2026-10-27: the fake's service state is outside D's process (F4), so a kill models a device crash, never a server crash.
- Decided 2026-10-27: `power` drops every data write that no completed full fsync (`F_FULLFSYNC`) covered and every directory entry change (create, rename, unlink) that no directory fsync covered, through the shim of F3. A real disk may keep more of either, never less, so a point between a rename and its directory fsync (`replace.after_rename`) accepts both outcomes in mode `power`.
- Decided 2026-10-27 (data safety): Meguri needs a start that finds a moved-aside tracking file whose salvage did not finish to run the salvage from it before anything else, and a salvage that skips a conflict copy it already copied (by its copy id), so a kill at `cloud.tracking.after_move_aside` or `cloud.tracking.after_salvage` neither hides nor doubles a copy. The approved `sync/cloudkit-recovery#V8.1` does not say this: a moved-aside file is never read by sync again, and a start that finds no `meguri-cloud.db` takes its "missing" row with no salvage. The contract wins, so U113 and U118 build V8.1 as it stands, and the two rows are pending (F5) until the contract's owner changes V8.1 (`conformance/cloudkit-acceptance#Q13`). The change needs a durable marker that tells a salvage that did not finish apart from a file kept because some rows were unreadable. Proposed: the move aside names the file `meguri-cloud.db.damaged-YYYY-MM-DD-HH.MM.SS.salvaging` (with its `-wal`); once the salvage has committed, a rename drops `.salvaging` when some rows were unreadable, or the file is deleted when every row was read. A start that finds a `.salvaging` file runs the salvage from it into the current tracking file, skipping copy ids already there, and only a file without the suffix is the kept file that Needs attention names.
- Decided 2026-10-27: error modes are armed only at tracking commit points, where V3.3 defines the outcome; elsewhere a failure is a kill or a power loss.
