# meguri-engine

- Every write to `collection.anki2` is an op on the executor (`Collection::submit`/`run`; `specs/engine/op-model.md`). Only the writer thread holds the writer connection. Open collections only through `Engine::open_raw` from meguri-host (this crate's tests and benches may name it).
- Op closures and `ChangeObserver`s run on the writer thread: never submit an op and wait for it there (deadlock), never call Swift, keep them short. A write phase past ~200 ms must be a catalog op (`executor/catalog.rs` and spec O9 together).
- A write phase never writes a snapshot value over a row that may have changed: re-derive inside the op or use a `Precondition` (O7). Never mtime or `usn`: `Local` stamping has one-second resolution.
- Op seqs and event seqs are one counter. An op reserves its seq at commit and fills it after the observers; an unfilled `Reservation` holds back every later event, so let it drop (never `mem::forget`).
- Lock order: lifecycle state, then executor queue, then commit lock or stream. The writer thread never takes the lifecycle lock.
- `close` and a replace wait for every reader lease: an exclusive job drops its reader (and snapshot) before `Exclusive::replace`. That wait is what keeps the generation fixed while a lease is held, so check a handle's generation inside `Readers::lease`, never before taking the lease.
- A `SlotGuard` and its `Exclusive` belong to one collection: a close frees the slot, an open makes older guards stale. Whatever they do re-checks `check_held`/`check_active` under the state lock first.
- Every thread through `ThreadRegistry::spawn` (named, QoS, idle list for U32). No timed wake-ups while idle (R1854): wait on condvars without timeouts unless a caller asked for one or a WAL flush is pending (storage C9.2).
- `monotonic.rs` is the crate's only system-clock read; collection time comes from the `OpenConfig` clock.
- Tests open copies of `conformance/fixtures/storage/` (`tests/common`) and never name `CollectionBuilder` (layering-check). The 150k reader test and the tag rename over 150k notes use testkit's `bench::fixtures::profile_collection`, cached in `build/fixtures` (`tools/mg fixtures 150k` and `175k` make them; sizes count cards, not notes).
- Derived store (`derived_host.rs`): `DerivedHost::ports` puts its open step first; close the host after `Engine::close` so the drained ops are applied before it is marked clean. Its observer only captures and sends: never write the derived file or wait on the writer thread.
- A derived builder holds the maintenance reader for one snapshot and checks the lifecycle at every batch: an opening or exclusive phase defers it, a close or replacement ends it. Set a builder's abort flag under the lifecycle lock, then notify `changed`, or a builder waiting for the phase to end misses it.
- `CollectionCore.derived` holds a `Weak` to the host: the host keeps a `Collection`, so a strong reference would be a cycle.
- Component code that runs on the derived writer (apply, build batches) goes through `guarded`: a panic there would kill the one writer while readiness still says `Ready`. A running refresh's deltas are kept before the batch's transaction, so its failure cannot lose them.
- The derived host's `suspend` returns only after every builder sent `Done` (its snapshot released); the writer keeps serving messages meanwhile. Never call it holding the lifecycle lock: builders take it at each batch.
- C8 releases participant connections through `release_connections_until` only after engine readers close (their `derived` attachments must close before the derived writer). A failed flush closes admission but remains pending for retry. Close shares this protocol and cancels jobs before asking participants to quiesce.
- `Ready` is not freshness: consumers ask `DerivedHost::is_current` with their snapshot, before its first read of `derived`, which reads the stamp's `seq` through it. SQLite fixes a snapshot's view of `derived` at that first read, not at `snapshot()`, so the view can hold commits after the snapshot's seq: those are not current. Never pin `derived` eagerly in every snapshot: the long maintenance and sync snapshots would keep the store's `-wal` from resetting. Every derived transaction that lets a ready component hold more commits writes that `seq` (`set_seq`), and the observer raises `sent` before it sends.
- A snapshot can see commits whose observers have not run (they run after the commit lock is released), so a builder sends a finished refresh's `Done` only after `wait_settled` on its snapshot's seq: their messages then reach the writer first and `through` covers every commit the rows hold. The stamp's `seq` is the whole store's: never write a refresh's snapshot seq there.
- A component the writer holds not `Ready` must say `ready` 0 in the file before the stamp is written again (its `seq`, its mark, `clean`): otherwise its rows pass as current, and after a clean close as fresh. Write `ready` 0 in the transaction that makes it stale or in one of its own, and when that fails, `unbind` (never ignore the error).
- A file that says `clean` 1 (after `suspend`) must say `clean` 0 before ops can commit without reaching it: a `Raw` write moves no mark, so the next open would find stale rows fresh. A failed `resume` returns its error and unbinds. Let go of the file only through `release_file`: one still marked clean waits in `owed` until `pay_unclean` writes `clean` 0 (each commit, `suspend`, `resume`, close).
- Undo (`src/undo/`, `specs/engine/undo.md`): steps are recorded, restored and truncated only on the writer, in `run_op` after the commit and before the result is returned (`UndoManager::after_commit`); clears and a sync's `finish`/failure marks may come from any thread. Pending flags are set only through `OpContext::begin_sync_hold`, inside an op, so no undo runs between a sync's snapshot and its flags. A step's id is its op's seq: compare it with snapshot seqs. An undo or redo op picks its step, catalog variant and declared write on the writer as it takes the op (`writer::resolve_restore`, M4.1), never at submit: a step recorded meanwhile (a bulk op running at submit) is the one it restores.
- A step keeps its op's `Journal` (`Arc`): its spill file is unnamed and goes with the last reference. Undo and redo restore in `CallerSupplied` mode, set `col.mod` from the step's saved value (the one read when the op, undo or redo that made the step ran; A7), never from now, and compare `col` only on the columns the step changed other than `mod`: every op moves `col.mod`.
- Every `UserUndoable` op but undo and redo, and every skip-undo op, clears redo, changed or not (A2); other sources keep M2's effects. "Update Note" steps of one note row merge within 60 s of clock time (A3, `Entry::absorb`), redos included: step the test clock a minute between edits of one note that must stay separate steps. Step names come from `undo/names.rs` (V4).
- A new catalog op needs its `UndoClass` (M11); `tests/op_catalog.rs` lists the expected classes. A new `OpSource` needs its effect in `undo/reasons.rs`.
- `tests/undo_conformance.rs` plays every `conformance/scenarios/undo/` scenario against its golden until the runner's undo adapter does (`undo-ops.md` V6): a new undo scenario needs its `play` test there. Its stand-ins (new collection, setup, `edit_note`, `delete_notes`, `answer`) write exactly the rows the goldens show; a mismatch right after a stand-in is the stand-in's, one after an undo or redo is the engine's.
- The day clock (`src/sched/`, `specs/sched/day-clock.md` D8) belongs to every open collection: `open_raw` runs its first check after the registered open steps, a replace runs it inside the writer's replace task (before the readers open, `CollectionReplaced` is delivered or a `GenerationListener` is told: they would otherwise see the old collection's cached day; its error fails the replace), and `run_op` reports each change set to it before the observers and the stream hear of it (a check made on the event would otherwise take the cached day). Never call `check_rollover`, `today` or `next_day_at` inside an op: they wait for the writer (`InvalidArgument` there); run them first and pass the day in. A write that brings no change set (raw SQL, another process) must call `drop_cached_day`, or the check's fast path keeps the old day.
- Day clock writes are `Rollover` ops in `Raw` mode: `col.mod`, card stamps and the undo history stay (`SourceEffect::Kept`, D10); only the rollover op's `clear_undo_on_commit` clears (D9). Its events come from an `on_commit` hook, so a check nobody waits for (parked, or started by a change set) still reports. Tests that record observers or ops from open see that first check's op on the schema-18 fixture (it has buried cards and no `lastUnburied`): clear the record after open.
- Note types (`src/notetypes/`, `specs/notetypes/`): every add goes through `insert` and every save through `save_in` (N4 normalization, V3 checks, N6 requirements), then storage's `put_notetype`, which writes and stamps per row. `save_in` is the plain save and refuses structure changes (fields or templates added, removed, moved or renamed, template text, sort field, kind): U34 adds its own path, which must rewrite notes and cards and call the gate. A field or template is known by the `ord` it was read with and its id (optional, absent in legacy note types), never by position alone. A save takes a `Draft` whose `base` is the `AggregateDigest` of the note type as read; a draft whose base no longer matches the live rows is `Stale` (O7), so never build a draft's base from anything but the rows it was edited from. New field and template ids come from `OpContext::random` (R1875).
- The stock kinds' template text and CSS (`notetypes/stock/templates/`) are Meguri's own (R908, R1959): never Anki's text, and the similarity scan covers them. `tests/stock_kinds.rs` checks them against K5–K7; goldens compare only structure.
- Schema changes (`schema_gate.rs`): an op of G2's table calls `mark_schema_change` with its reasons after computing its effect and before writing; no other code sets `col.scm`. `run_op` runs the storage guard (G6) before every commit: a transaction that changes a kept note type's field or template count while leaving `scm <= ls` fails with `SchemaNotMarked`, except an undo that restores `scm`.
- Tags (`src/tags/`, `specs/tags/tags.md`): a note save stores `tags::note_tags_for_save` (T4); other note writes leave `notes.tags` to the tag ops. Names compare by `unicase` (T3, rows, the `tags` key) except matching (T5), which is `Matcher`'s simple folding: never mix the two. Each tag op has an engine form (planned on a snapshot under `TableUntouched{notes}`, one undo step) and an `_in` form for a scope the caller holds (the testkit's tags adapters); both call the same `apply_*`. T3 spells from implicit parents too (`registry::spelling_of`; the first row at or after `name::` in key order spells one). Rename and reparent remove the old rows before they spell (the `tags-*-spelling` deviations) and register the new rows themselves with the removed rows' columns (`Speller::spell_with`, T7 step 5). An op writing more than `tags::LONG_WRITE_ROWS` rows runs as `catalog::BULK_OP` with a declared write (`tags::op_spec`). The flag and mark toggles decide on the live row in their write phase.
- `flags::set_flag_in` refuses a scope that is not `KeepMtime`: a flag change keeps the card's `mod` (F2). `tests/tags_conformance.rs` plays every tags scenario against its golden until T0 has `add_note` and the setup (`conformance/scenarios/tags/area.yaml`): a new tags scenario needs its `play` test there.
- Browser config writes (`browser_config.rs`, `specs/browser/config-keys.md` K10.2): the saved-search writes are `UserUndoable` steps with their own names; every other write is `UserNonUndoable`, so a change clears the history and a write of nothing keeps it. Set Due Date and Reset store their inputs with the `remember_*_in` forms inside their own op, never as a separate op. `tests/browser_config.rs` covers the ops; the K tables are meguri-search's `tests/config_keys.rs`.
- Suspend (`src/suspend.rs`): control calls serialize on `control_lane`; never call one inside an op, participant, or while keeping a reader lease. Participants flush before admission closes; lengthy flush/quiesce methods must honor the absolute monotonic deadline. Owned threads use `spawn_owned` (or `register_current_owned`) with `writer`, `jobs`, `events` (value delivery only) or their registered participant's name; an unowned idle thread fails suspension. Success closes SQLite but retains the advisory process lock and undo. A failed attempt keeps admission closed until retry or resume.
- Whole-collection change sets (U32 external edits) invalidate every cache: they have no row deltas. Derived observers advance `sent` before queueing invalidation, so older attached rows cannot pass `is_current` while invalidation is pending.

- `start_job` and `start_continued_job` share the control lane: reentrant calls from an op, observer or suspend participant are refused while control is running. Never wait for a job there. Open holds the lane only for state transitions; close during Opening/Upgrading is refused. Suspend includes lane acquisition in its budget; resume bounds lane acquisition to five seconds.
