# app/

## Project

- Build settings live only in `Config/*.xcconfig`, never in `project.pbxproj`: target settings in `<Target>.xcconfig`, configuration differences in `Debug`, `Profile`, `Release`, `AppStore` (Profile and AppStore include Release and override a few lines).
- Folders are synchronized groups: add, move or delete files under `Meguri/`, `MeguriWidget/`, `MeguriUITests/`, `MeguriSnapshotTests/` without touching the pbxproj. A plist or entitlements file there is copied as a resource unless the folder's exception set in the pbxproj lists it. The pbxproj changes only for a new target, package product or capability.
- A fresh checkout needs `tools/mg core-xcframework` before any `xcodebuild`: package resolution fails without the binary target. After that the Meguri schemes' pre-action rebuilds the core for the configuration and platform (log: `build/xcode/core-pre-action.log`; it unsets `SDKROOT`, which is `auto` here and breaks xcrun tools). A build without the pre-action (another scheme, `-target`) is caught by the Meguri target's "Check core configuration" phase, which fails when the core stamp's configuration, features (`MEGURI_CORE_FEATURES`) or slice do not match.
- Local packages are both `XCLocalSwiftPackageReference`s and folder references in the Packages group; without the folder references test plans cannot see package test targets ("There are no test bundles available to test").
- Pass `-derivedDataPath` under `build/`; `xcodebuild -target` without it writes `app/build/`.
- `tools/mg xcode-check` checks this project end to end; extend it when you add a configuration-dependent setting, entitlement or capability.

## Configurations

| | Hooks | AnkiWeb | Ids |
|---|---|---|---|
| Debug | yes | yes | `.dev` |
| Profile | yes | yes | `.dev` |
| Release | no | yes | daily driver |
| AppStore | no | no | daily driver |

- Profile is Release plus `MEGURI_TEST_HOOKS` (so performance tests can load fixtures) and therefore the `.dev` ids. R1866's "Release configuration" for performance tests means Profile. Never archive or distribute it.
- Never launch a Release or AppStore build on the Mac: it would replace the daily-driver app. Run their UI tests on simulators only (`TestHooksTests` skips them on the Mac).
- Building Release or AppStore for the Mac is enough to harm it: Xcode registers the product (daily-driver ids, widget included) with LaunchServices and PlugInKit. Unregister and delete it once done (`lsregister -u`, `pluginkit -r`, as `tools/mg xcode-check` does).
- Packages never test app compilation conditions: SwiftPM sees only debug/release. `MEGURI_TEST_HOOKS` code lives only in `Meguri/TestHooks/`, `ANKIWEB_ENABLED` code only in `Meguri/AnkiWeb/` (KTD21). `App/MeguriApp.swift` is the one other file that names the hooks.
- Packages expose seams instead (`AppModel`: `LaunchConfiguration`, `AppClock`, `CollectionLocation`, `InitialPresentation`). Views read time through `@Environment(\.appClock)`, never `Date()`.
- On the Mac a sheet takes `\.locale` from its own window, not from its presenter: presented content gets the launch environment again (`RootView`).
- On the Mac, never present an alert while the app is hidden (launched with `open -j`, as agents must, or a login item set to Hide): the window closes and the app quits, with no crash report. Present launch-time alerts after `await NSApp.untilUnhidden()`, as `RootView` does.

## Shell (U150)

- `AppNavigation` (AppModel) is the only navigation state, above the layout switch; views read it and never keep their own section, selection, path or open sheet. A feature model that must survive a layout switch (drafts, a review session, Browse's search) is held by it (`featureState`, `ReviewPresentation.session`), never by a view.
- Features replace their placeholders in `ShellFeatures.standard` (`Shell/SectionDestinationView.swift`). Push only `Destination` cases; a section root's `ScrollView` takes `navigationScrollPosition(_:_:idType:)`. A bound `ScrollPosition` does not report user scrolling (its `viewID` stays nil), and a scroll view built hidden (a root under a pushed screen) neither scrolls to a position nor stays at it: the modifier tracks the rows on screen and scrolls back on appear.
- Sheets go through `AppNavigation.present(_:)` (`PresentationHost`); in the tab layout a review's full-screen cover presents them itself.

## Design system

- UI code takes colours, spacing, radii, motion and content widths (`ContentWidth`: a readable column, centred in wide windows) only from `DesignSystem/Tokens/`, text from system styles, icons from SF Symbols, glass only from `DesignSystem/Chrome/` (KTD20). `tools/mg lint-ui` enforces it on every Swift file under `app/` except tests and MeguriCore; inline `swiftlint:` comments fail it, and the only exemption is a reasoned entry in `tools/lint-ui/allowlist.tsv`. Lint is not a build phase: run it before building.
- A new colour token needs a colour set with light, dark and both increased-contrast variants and a `role` naming the backgrounds it is drawn on; `ContrastTests` and `TokenCoverageTests` (`tools/mg swift-test --package MeguriKit`) check them. Increase Contrast has no public environment setter: tests resolve colours with `EnvironmentValues._colorSchemeContrast`, and `NSAppearance`'s high-contrast names do not select the catalog's high-contrast variants.
- Reusable components go into `ComponentGallery.entries` first (route `designsystem/gallery`, identifiers `designsystem.gallery.<component>.<state>`); the gallery's VStack is deliberately not lazy so UI tests see off-screen entries.

## Test hooks

- Launch options are `-Meguri<Name> <value>` (table in `TestHooks/LaunchOptions.swift`); UI tests build them with `MeguriUITests/Support/MeguriLaunch.swift`. A bad option replaces the UI with `testhooks.error.message`.
- The Mac Debug app declares `LSUIElement`, so LaunchServices never shows a launch in the Dock before the app's code runs; `MeguriApp.init` then gives it the regular policy unless it is a test host (`XCTestConfigurationFilePath`) or got `-MeguriBackgroundLaunch YES` (`TestHooks/BackgroundLaunch.swift`, U8d). Those stay accessory: never in the Dock or active, windows still render and capture. Profile starts as a regular app and has no switch (it keeps Release's launch, R1866), so `tools/mg` launches only Debug on the Mac host. App-hosted tests therefore run in an app that is never active.
- On the Mac, SwiftUI keeps the window frame in the `NSWindow Frame main` default, which `-ApplePersistenceIgnoreState` does not reset. Hook launches therefore always set a size (`default` when `-MeguriWindowSize` is absent); a launch with no hook option keeps the previous run's frame.
- A running Mac hook build also resizes its window on the distributed notification `<bundle id>.testhooks.resizeWindow` (object: a `-MeguriWindowSize` value) and answers `<bundle id>.testhooks.windowResized` (`WindowHookView`; the agent driver's `resize` step). Post both with `deliverImmediately`: the receiver is usually not the active app. Sandboxed senders cannot attach a `userInfo`.
- Each UI area registers its routes (`area/screen[/state]`) in `RouteRegistry.standard`, from a `TestHooks/<Area>Routes.swift`, with literal paths: `tools/mg xcode-check` reads them from the source, launches the Mac app hidden on each and fails on a computed path. A `.screen` route shows its view on its own, without the shell; `registerShell` routes open the shell in a state with sample features (`ShellRoutes.swift`), and their probe `testhooks.shell.state`, a strip below the shell that covers none of it, prints the navigation.
- A launch with any hook option starts from a fresh UI state and saves none (`UIStateStore(defaults: nil)`); a launch with none restores the device's.
- `-MeguriSizeClass` forces the layout on iOS; the Darwin notification `<bundle id>.testhooks.toggleSizeClass` flips it at run time (also `presentAdd`, and `closeWindow` on the Mac, distributed). The override goes on the windows: one on the scene does not reach SwiftUI's size class on an iPhone. At regular width an iPhone's sidebar overlays the detail column and hides it from accessibility queries.
- Fixtures must sit inside the checkout: launched outside XCTest, the sandboxed Mac hook build can read only there (`-Dev` entitlements). The Mac UI-test runner is sandboxed too and cannot write them: create fixtures before the run (committed under `Fixtures/`, or by `tools/mg` jobs), never from a test. Keep them out of the synchronized folders, whose files are copied into bundles (a folder in an exception set is not excluded).
- Generated UI recipes (U11) are `tools/mg fixtures <recipe>` output in `build/fixtures/recipes/<name>-<seed>/`; pass that directory to `-MeguriFixture` with the manifest's `now_ms` and offset as `-MeguriNow`/`-MeguriTimeZone`. `RecipeFixtureTests` launches all of them in-process when `tools/mg fixtures-check` sets `MEGURI_RECIPE_FIXTURES`.

## Signing and entitlements

- `MEGURI_SIGNING` in `Config/Signing.xcconfig`: `adhoc` until the `xcode-account` user step, then `team`.
- Mac entitlements are `Meguri-macOS[-Dev][-AdHoc].entitlements`: `-Dev` (hook builds) adds read-only access to the checkout, `-AdHoc` drops the App Group. Keep the shared keys identical in all four. R2041/KTD22: no capability beyond sandbox, network client and server, user-selected files and app-scope bookmarks (plus the App Group when signed).

## Tests

- Accessibility identifiers: `area.screen.element[.id]`, element names lowerCamel (R1964).
- System alerts drop the identifiers of their buttons, on iOS and on the Mac. Tests reach them through the alert (`app.alerts` on iOS, `app.sheets` on the Mac) and the button's label; identifier audits must accept them.
- Run any UI test class with `tools/mg ui-test --platform iphone|ipad|mac --suite <Class>` (in the test VM).
- `XCUIApplication.open(_:)` relaunches the app before opening a URL: open deep links with `XCUIDevice.shared.system.open` (iOS) or `NSWorkspace` (Mac) to reach the running app.
- `MeguriSnapshotTests` is the app-hosted bundle: snapshots and in-process tests of app code (`@testable import Meguri`, Debug only). Swift Testing runs main-actor tests inside a main-queue block: wait for a notification suspended (`Task.sleep`), never by running the run loop, which then delivers nothing.

## Snapshots (U10)

- Run and record only through `tools/mg snapshots` (`--record <glob>`, `--rebaseline`): the tests compare and write results and new images to the job's output, never to baselines (the Mac test host is sandboxed). Outside the job they run in the default settings group and write to the temporary directory.
- Baselines live in `app/Snapshots/<model>-<OS build>/<subject>/<state>/<cell>.png`, outside `MeguriSnapshotTests/`: files in a synchronized folder are copied, flattened, into the bundle, so same-named PNGs collide.
- A screen joins the matrix by conforming to `PreviewStates` (DesignSystem) and being listed in `MeguriSnapshotTests/Support/MatrixRegistry.swift`; gallery components join through `ComponentGallery.entries`.
- System Liquid Glass is not the same twice. The iPad sidebar's grain fails the tolerance (so does the tab bar's in dark iPhone cells with Increase Contrast, Reduce Motion or a glass opacity extreme); with Reduce Transparency the glass turns opaque but the sidebar toggle's still differs by one level, which the perceptual comparison fails on near-black pixels only. A screen with system glass there takes `unstableGlassKeyVariants` (as `shell.root` on the iPad): its light `+rt` cells render and the rest stay listed as deferred, never dropped; the gallery shows `+rt` key variants too.
- The Mac's off-screen render (`cacheDisplay`) cannot draw an AppKit split view's materials (a black selection; in dark mode dark text and a white detail column): put `sidebarColumnChrome()` and `detailColumnChrome()` (DesignSystem/Chrome) on a split view's columns, which flat chrome draws opaque.
- Renders are 2x, 8-bit sRGB, opaque, after frames stop changing; Core Animation stands still in the snapshot window, so spinners render their first frame. iOS renders in a key window of their own: components with no safe area, screens with the window's own (the simulator's insets), never padded insets, which UIKit's scroll edge effects would not see; the Mac renders off-screen with flat chrome (`ChromeGlass.flat`: no glass off-screen) and one text size (SwiftUI ignores Dynamic Type there).
- A screen gets its simulator's safe area, so each device class renders on the pool kind whose screen it is (`DeviceClass.target`): the small iPhone class on `iphone-small` (iPhone 17e), with its own baselines directory. A test process renders only its target's cells (`MEGURI_SNAPSHOT_TARGET`, set by the job).
- On simulators, Reduce Transparency, Reduce Motion and glass opacity are device settings, one test run per settings group (`docs/design/decisions/s5-simulator-settings.md`); a cell's `systemGroup` decides which run renders it. Mac cells with any of them on are deferred: system chrome ignores a SwiftUI environment override. The settings probe renders in every group whatever the filter (captured, not compared, outside it).
- `StateCoverageTests` also writes where each screen is registered and every cell it renders there, whatever the filter (`registry.json` in the run); `tools/mg critic` refuses a run that lacks one of them.
- `MeguriUITests/Accessibility/`: audits go through `AccessibilityAudit` with `suppressions.json` (one identifier, one audit type, a reason); `tools/mg a11y` runs them (Mac: through the Mac UI gate). A screen's audit covers each of its states' routes in every variant, checks the variant's appearance is the one the app shows (the Mac sets the app's own with `-MeguriAppearance`: with `-AppleInterfaceStyle Light` it showed a dark workstation's), and reports per state. On the Mac, findings on the window's own elements (neither identifier nor label, `_XCUI:` controls) are listed as excluded, not failed (`AccessibilityAudit.systemElement`). The touch-target check leaves out buttons without an identifier in a navigation bar (the system's sidebar toggle and back buttons: their frame is the glass circle, not the hit region). VoiceOver runs on iOS simulators only, never on the Mac running the tests. Its service output is the utterance alone (no element, no wrap-around signal): a reading is never cut on a repeat, and one that stops at the step limit says so (`complete`).
- Xcode gives every Mac app it builds for testing, UI tests included, read access to `/` (plus testmanagerd lookups): no Mac test can catch a sandbox read denial. The `-Dev` fixture entitlement matters for launches outside XCTest; check entitlements on products of `xcodebuild build`, never of a test build.
- On the Mac another app is usually in front. XCUITest then reports its windows as interruptions before every tap and clicks right after activating the app, before its window is key. Call `app.bringToFront(bundleIdentifier:)` (`Support/FrontmostApp.swift`) before every Mac tap, key press or drag. Window screenshots (`app.windows.firstMatch.screenshot()`) draw the window as active either way; only a screen capture shows the real state.
- Shared UI tests use `clickOrTap()` (`Support/PlatformInput.swift`): mouse clicks on macOS, touches on iOS. Mac drags use `click(forDuration:thenDragTo:)`. On macOS 27.0.1, touch APIs (`tap`, `press`) take Recap's touch path, which WindowServer rejects because `testmanagerd` has an internal-only HID entitlement; native mouse events work. A failed run with Recap timeouts is queued only when dropped input explains every failure.
- Mac UI tests (`TestHooksTests`, `testMacWindowSize` included, and `AgentDriverTests`' resize test) run only through `tools/mg mac-ui`, in the test VM, never directly (root `AGENTS.md`). `tools/mg xcode-check` reports them as queued unless `MEGURI_ALLOW_MAC_UI=1`, so Mac-only coverage (window size, Mac routes) comes from `tools/mg mac-ui`.
- `MeguriUITests/AgentDriver/` is the agent driver behind `tools/mg drive` (U8). `AgentDriverTests` skips unless `MEGURI_DRIVE_SCRIPT` is set (`TEST_RUNNER_` prefix from xcodebuild). XCUITest reports keyboard focus on iOS only. The route `sample/defects` holds deliberate defects for `hierarchy-check`'s tests. It must keep them. `FrameSampler` (`MEGURI_DRIVE_FRAMES=1`) takes screenshots from a timer on the main run loop: XCUITest runs that loop while it waits on an action, so the frames cover the action. Crop and scale each frame as it is taken; a full Mac screenshot is tens of MB.
- Performance tests (U12, U241): subclasses of `MeguriUITests/Performance/PerfTestCase` naming registered intervals (`Instrumentation/IntervalNames.swift`) and, when they load one, their `fixture` (as `tools/perf/budgets.yaml` names it: the R1803 size rules need it); they fail at setup with an unregistered name or when `Support/PerfPreconditions` fails (R1866: not Profile, a debugger, coverage or sanitizer runtimes in the app or the runner, a parallel-testing clone). A budget's suite, interval and test names come from `tools/perf/budgets.yaml`: a new suite implements its cases there and removes their `pending`, after which `perf-gate --check` needs a `measure(app:)` call in the class, a base class or an extension of it, and every result of the suite must carry each case. A new class goes into the UI plan's `skippedTests`; the Performance plan selects nothing (`tools/mg xcode-check` runs `TestHooksTests` through it), so run them only through `tools/mg perf-ui`, which names its suites. `perf/probe` is the harness's own route.
- `CardSwapTimingSpikeTests` (U65) drives the `spike/*` routes (`TestHooks/SpikeRoutes.swift`). Run the whole class: one of its tests alone measures nothing, and perf-ui then fails it for having no perf result. For diagnosis after source or instrumentation changes, `tools/mg ui-test --config Profile --platform <iphone|ipad|mac> --suite Class/test` runs only functional assertions in the VM and produces no performance receipt; acceptance still requires the whole class through `tools/mg perf-ui`. Never rerun unchanged failures until green. In the test VM, `<audio>` never plays (no audio route; even a blob URL stalls) and Metal drawables report no presented time; the iOS simulator SDK has no `addPresentedHandler` at all. Frame timings there are display-link estimates (docs/design/decisions/s1-occluded-page-swap.md). `CardSwapTimingGate` picks strict or function-only from the environment (`kern.hv_vmm_present`, simulator), never from the samples; the audio test skips unless that sysctl says real hardware. S1(c) captures the app's own Mac window with ScreenCaptureKit (`SCShareableContent.currentProcess` needs no Screen Recording permission); anything it shows on screen per frame makes another frame. Web content footprints are readable in the iOS simulator (its processes are the VM's), not on a device or from the sandboxed Mac app.
- Allocation diagnosis: only `tools/mg ui-test --config Profile --platform mac --allocations --suite CardSwapTimingSpikeTests/testAThousandSwapsKeepTheSamePagesAndFlatMemory`. It attaches a bounded VM-only Allocations trace to the copied app's exact `spike/card-swap` launch; it leaves XCTest timing/teardown intact. Artifacts carry profiler overhead, no ordinary performance receipt and uncertified/partial coverage. Inspect the actual start notification and allocation stacks before attributing ownership or claiming burst coverage.
- Only that allocation diagnostic build enables development task access (`CODE_SIGN_INJECT_BASE_ENTITLEMENTS=YES`); ordinary Profile builds and performance acceptance remain unchanged.
- `measure(app:)` first asks the app for a warmed web content process (R1866) and fails without its answer: `TestHooks.WebContentWarmup` (notification `<bundle id>.testhooks.warmWebContent`, answer `.webContentReady`) keeps a loaded page for the app's run. When CardRendering's page pair exists (U67), warm through its shared configuration, so the process warmed is the reviewer's. A new harness-check class (no measurements) must join `MG_PERF_UI_CHECK_SUITES` (`tools/mg.d/perf.sh`), or perf-ui fails it.
- Test plans never retry failures (R1953). The UI plan keeps no system screenshots or screen recordings (`uiTestingScreenshotsLifetime: keepNever`, SystemAttachmentLifetime in the xctestrun): on the Mac they film the user's desktop. Attach what a test needs yourself (lifetime `.keepAlways`). A recorded test failure still attaches the app's UI hierarchy, which on the Mac includes the menu bar's recent files; the agent driver reports failed steps in its drive log instead of failing the test. The `Performance` plan's options are fixed by R1866, and the `Meguri-Profile` scheme runs it without a debugger.
- The `Unit` plan runs on the Mac: `CoreBridgeTests` expects the Mac slice.
